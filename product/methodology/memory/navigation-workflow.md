# Навигация — workflow доставки карты пространства

Текущая реализация [спецификации навигации](navigation-spec.md): какие компоненты собирают карту, на каких событиях они запускаются и как поставляются в рабочее пространство. Причины решений — в [методологии контекстной памяти](01_context-memory_new.md), код и проверки трека — в плане карты пространства.

## 1. Компоненты

| Компонент | Источник | Роль |
|---|---|---|
| Генератор | `product/plugin/hooks/space_map.py` | читает дерево и печатает корневую карту или подкарту узла |
| Хук доставки | `product/plugin/hooks/inject_space_map.py` | выбирает режим, получает событие платформы и добавляет карту в контекст |
| Стабильный блок | корневые `CLAUDE.md` и `AGENTS.md` | держит модель пространства и правила хода без динамического списка файлов |
| Профиль поставки | `dev/plugin-builder/profiles/svaib-space-map/` | ставит генератор, хук и регистрацию событий в репозиторий svaib |
| Скаут | `product/plugin/agents/svaib-scout.md` | задаёт стратегию и форму ответа отдельного поискового агента |

Канон кода находится в `product/plugin/`. Копия в `.claude/hooks/` — установленная версия для Claude Code; `.agents/hooks/inject_space_map.py` — ссылка, через которую тот же хук вызывает Codex.

## 2. Как собирается карта

1. Генератор находит корень пространства по `CLAUDE.md` или `AGENTS.md`.
2. Читает дерево, исключая служебные каталоги.
3. Для файлов берёт `title` из YAML, при его отсутствии — H1; необязательное `description` добавляет только если оно несёт новый смысл.
4. Для папки использует README, затем `01_overview.md`, чтобы получить её миссию.
5. Определяет наличие менеджмент-кита по каноническим именам файлов.
6. Из README берёт только маршруты чтения, которые добавляют логику сверх дерева, и отбрасывает битые цели.
7. Считает покрытие и печатает markdown-блок для подачи в контекст.

Генератор ничего не записывает в управленческое пространство. Карта существует только в контексте текущей сессии.

Текущая реализация помечает вложенную папку с менеджмент-китом как «юнит». Это технический признак «узел с управленческой панелью», а не каноническое определение юнита через ответственность, собственный контекст и регулярное внимание.

## 3. Как проходит сессия

### 3.1. Первый запрос

Режим `first-prompt` запускает генератор один раз на `session_id`.

- Если в корневом `CLAUDE.md` или `AGENTS.md` есть стабильный раздел карты, хук не повторяет его.
- Если есть свежий локальный кэш пользователя, генератор сразу добавляет подкарты его зоны.
- Если пользователя определить нельзя, приходит общая карта без предположения о личности.

### 3.2. Персонализация

В Claude Code и Cowork режим `post-whoami` получает ответ платформы, читает путь профиля и определяет зону сначала по полю `units:`, затем по описанию профиля. Результат сохраняется в локальном кэше на 24 часа с ключом «аккаунт + корень пространства».

В Codex отдельный стартовый хук сообщает личность из `.agents/identity.local`. Персонализация самой карты использует локальный кэш, ранее созданный по `whoami`; если кэша нет, карта остаётся общей. Codex не выдаёт пользователя за владельца пространства, если профиль не установлен.

Кэш живёт на машине, не коммитится и не синхронизируется с клиентской базой.

### 3.3. Первый вход в узел

Режим `node-enter` получает путь из инструмента чтения или shell-команды и находит ближайший к цели узел карты.

- Папка верхнего уровня считается границей безусловно, кроме `_inbox` и `zz_archive`.
- Вложенная папка становится границей при наличии `README.md`.
- В контекст подаётся только ближайшая подкарта, без всей цепочки родителей.
- Узел, уже раскрытый в этой сессии, повторно не подаётся.

После успешной подачи хук создаёт локальный маркер сессии. Маркеры хранятся вне репозитория и очищаются через семь дней.

### 3.4. Сжатие контекста

Режим `compact` заново собирает корневую и персональную части и снимает маркеры раскрытых узлов. Если событие платформы принимает дополнительный контекст, хук сразу подаёт собранную карту; независимо от этого подкарты снова приходят при первом обращении.

## 4. События платформ

| Результат | Claude Code / Cowork | Codex CLI |
|---|---|---|
| Первый запрос | `UserPromptSubmit` → `first-prompt` | `UserPromptSubmit` → `first-prompt` |
| Установление пользователя | `PostToolUse` на `mcp__.*__whoami` → `post-whoami` | `SessionStart` отдельного identity-хука + локальный профиль |
| Вход в узел | `PostToolUse` на `Read`, `Glob`, `Grep` или `Bash` → `node-enter` | `PostToolUse` → `node-enter`; путь извлекается из вызова shell-инструмента |
| После сжатия | `SessionStart` с `compact` или `clear` → `compact` | `PostCompact` запускает `compact`, но не принимает его `additionalContext` |

Если среда не поддерживает хуки, стабильный блок и корневая карта могут жить в корневом файле статически. Это сохраняет правила навигации, но требует ручного обновления динамической части.

В Claude Code режим `compact` возвращает корневую и персональную карты и снимает маркеры раскрытых узлов. В Codex событие `PostCompact` зарегистрировано и хук запускается, но платформа не добавляет его вывод в контекст. Стабильный блок из `AGENTS.md` остаётся доступен, а подкарты снова приходят при входе в узлы; динамическая корневая и персональная части после сжатия не восстанавливаются. Текущая реализация Codex поэтому не выполняет полностью раздел 4 [спецификации](navigation-spec.md).

## 5. Стабильный блок в корневых файлах

Генератор печатает стабильный текст командой `space_map.py --print-model`. Этот блок помещается в раздел `## Карта пространства` в `CLAUDE.md` и `## Space Map` в `AGENTS.md`.

В блоке нет списка юнитов: он приходит динамически. Поэтому стабильный текст не протухает при изменении дерева. Хук определяет наличие блока по заголовку раздела; отдельный HTML-маркер не используется.

Текст двух корневых файлов пока различается в одном месте: инструкция поиска в `AGENTS.md` адаптирована под встроенную коллаборацию Codex, а генератор печатает вариант Claude Code. До автоматической перегенерации `AGENTS.md` генератор должен научиться учитывать целевую платформу.

## 6. Маршруты из README

Генератор читает раздел `Маршруты чтения` и оставляет только строки, которые нельзя вывести из имён файлов и общего канона:

- цепочки из нескольких источников;
- переходы за пределы текущего узла;
- ссылки на конкретную секцию;
- условия и пометки «читать первым»;
- внешние ссылки.

Одиночный очевидный переход и битая цель в карту не попадают. В выходе указывается, сколько строк README принято и сколько отброшено.

## 7. Скаут пространства

Текст контракта скаута хранится в [спецификации](navigation-spec.md), а его канонический бриф — в [инструкции скаута](../../plugin/agents/svaib-scout.md).

- В Claude Code главный агент вызывает именованного субагента `svaib-scout`.
- В Codex главный агент запускает встроенного субагента и передаёт ему тот же бриф целиком.
- Строка, требующая передать широкий поиск скауту, включается в стабильный блок переменной `SVAIB_MAP_SCOUT=1`.

Скаут не получает карту автоматически, поэтому главный агент обязан передать уже известные адреса и границу поиска в задании.

В репозитории svaib правило вызова скаута включено. В клиентском пакете файл скаута поставляется, но `SVAIB_MAP_SCOUT` по умолчанию выключен; пока профиль клиента не включает флаг, широкий поиск остаётся на главном агенте.

## 8. Настройки и состояние

| Настройка | Значение по умолчанию | Назначение |
|---|---|---|
| `SVAIB_MAP_NESTED` | `nearest` | подавать ближайший вложенный узел; `0` и `chain` оставлены для стенда |
| `SVAIB_MAP_ROUTES` | `1` | добавлять отфильтрованные маршруты чтения README |
| `SVAIB_MAP_SCOUT` | `0` в пакете | добавлять правило вызова скаута; в репозитории svaib включено |
| `SVAIB_MAP_SKILLS` | `0` | добавлять реестр скиллов; нужен только в средах, которые не показывают его сами |

Состояние сессии и кэш пользователя лежат в локальном state-каталоге. Сбои записываются в `space-map-hook.log`; хук завершает работу с кодом 0, чтобы отказ навигации не блокировал основную сессию.

## 9. Поставка

Профиль карты поставляет три файла:

- `hooks/space_map.py` — генератор;
- `hooks/inject_space_map.py` — доставка по событиям.
- `agents/svaib-scout.md` — инструкция поискового субагента.

Сборщик `dev/plugin-builder/build-plugin.sh` копирует их по манифесту профиля и добавляет события из `settings.json` или `settings.merge.json`. Профиль `dev/plugin-builder/profiles/svaib-space-map/` используется для установки в наш репозиторий и как образец отдельного подключения.

Карта пока не включена во все клиентские профили автоматически: конкретный профиль определяет состав поставки.

## 10. Проверка реализации

Продуктовые способности, типы кейсов и правила оценки определяет [навигационный эвал](navigation-eval.md). Этот раздел указывает только на проверки текущей реализации.

Проверки трека находятся в `dev/space-map/engine/tools/tests/` и подтверждают:

- одинаковое поведение канона плагина и установленной копии;
- сборку корневой карты и подкарты узла;
- обработку событий Claude Code и Codex;
- восстановление карты после сжатия;
- фильтрацию маршрутов README;
- мягкую деградацию при ошибке.

Результаты экспериментов и ограничения измерений остаются в инженерном треке, а не в спецификации или методологии.
