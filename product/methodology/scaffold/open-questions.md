# Scaffold open questions

Нерешённые вопросы scaffold v4.1, которые требуют полевой проверки или отдельного решения. Закрытые решения переезжают в [01_architecture.md](01_architecture.md), спеки или [deployment.md](deployment.md).


### ⁉️ Lifecycle миграций живого scaffold

Открыт не стартовый рост `файл → папка`, а операции с уже живым scaffold: перенос, слияние, удаление, обратный переход `папка → файл`, split/merge узлов, архивация холодного контекста.

Текущее правило безопасности: агент не делает такие операции сам, а останавливается и просит подтверждения. Канон миграций наработаем по практике; возможно, отдельный `lifecycle.md`.

### ⁉️ Визуальный UX scaffold-документов

Открыт канон визуального оформления scaffold-файлов: эмодзи-маркеры, H2/H3-паттерны, отступы, плотность текста, визуальные статусы, читаемость для человека без потери машинной структуры.

Сейчас рабочие маркеры частично описаны в [02_file-spec.md](02_file-spec.md), но это временная фиксация. Нужно решить:
- остаётся ли визуальный UX частью `02_file-spec.md`;
- выделяется ли отдельный `visual-style.md`;
- какой набор маркеров считаем каноническим;
- где граница между полезной навигацией и декоративным шумом.

Не блокирует scaffold v4.1, но важно для качества клиентских документов.

### ⁉️ Finance в scaffold

Открыт вопрос, как в scaffold хранить финансовую управленческую систему клиента: центры финансовой ответственности, логику прибыли, рентабельность, статьи расходов, финмодель, бюджет, cash-flow, дивиденды и правила финансовых решений.

Уже ясно:
- финансовые показатели как числа и определения могут связываться с `03_metrics/`, но `finance` к metrics не сводится;
- размещение определяется общей логикой node: владелец → общий родитель → `01_company/` / корень.

Открыто:
- становится ли `finance/` отдельным management unit / объектом управления, если есть финансовая функция или владелец;
- живёт ли финансовая система как `01_company/finance.md` → `01_company/finance/`, если её ведёт CEO на уровне компании без отдельной функции;
- какие типовые файлы нужны: `financial-model.md`, `budget.md`, `cash-flow.md`, `cost-structure.md`, `profitability.md`, `dividends.md`, `financial-rules.md` и т.д.

Решаем по первому клиенту с живой финансовой работой.


### ⁉️ Механика доставки контекста агенту

Инвариант решён ([02_readme-spec § Доставка README агенту](02_readme-spec.md)): README — SOT навигации, базовый контракт — текстовая инструкция в корневой инструкции агента, вложенные нативные файлы узлам не требуются.

Открыта механика усиленной доставки, кандидаты: вложенные `CLAUDE.md` по узлам, `@`-импорты, хуки с `additionalContext`, плагин. Среды ведут себя по-разному и меняются — датированная матрица в [ai-system-files.md](../../../knowledge/context/ai-system-files.md).

На время разработки продукта механика не канонизирована: при развёртывании допускаются эксперименты (например, `CLAUDE.md` во всех units конкретного клиента) с ограничением «вложенный файл — только указатель на README, без локальных правил». Закрываем по полевой практике: способ, давший надёжную доставку у живых клиентов (включая Claude Cowork), канонизируем.
