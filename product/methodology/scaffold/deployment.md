# Scaffold deployment — развёртывание каркаса у клиента

Как scaffold ставится у клиента и растёт: стартовый минимум, триггеры расширения, выбор формы узла. Миграции — вне файла. Модель — [01_architecture.md](01_architecture.md); сущности — [management-unit.md](management-unit.md), [management-aspect.md](management-aspect.md), [management-kit.md](management-kit.md). Проверка узла перед выгрузкой — [deployment-node-review.md](deployment-node-review.md).

## 🔵 Принцип: разворачивать только живое

> **Разворачивай только живое. Пустые ветки не создавай.**
>
> «Живое» = появилась реальная работа: встреча, задача, человек, метрика, решение, материал или регулярный управленческий фокус.

Deployment — не установка фиксированного дерева. Это первичная сборка composable management architecture под реальную модель клиента.

**Стартовая рамка не равна пустой ветке.**
Пустая ветка — контейнер без управленческого сигнала: агент читает и получает ноль.
Стартовая рамка — файл или папка с моделью мышления, заголовками и подсказками для онбординга. Она учит CEO, какие управленческие вопросы нужно держать в поле.

Развёртывание сейчас ручное по этим правилам. Автоматизация — [../../plugin/skills/scaffold/](../../plugin/skills/scaffold/), после 2-3 успешных ручных развёртываний.

## 🔵 Три слоя и поставка

Scaffold живёт в трёх слоях.

| Слой                              | Где                                        | Что содержит                                                                                                                          | Едет клиенту                                     |
| --------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| Методология                       | `product/methodology/scaffold/`            | канон: зачем устроено, какие сущности, как работает развёртывание                                                                     | нет                                              |
| Стартовый каркас + папка шаблонов | `product/plugin/skills/scaffold/template/` | стартовый каркас (`01_company/`), корневые служебные папки и папка шаблонов `_templates/` (шаблоны файлов + шаблоны узлов в `nodes/`) | да: едет целиком как стартовая структура клиента |
| Живой scaffold                    | пространство клиента                       | развёрнутые узлы и файлы                                                                                                              | это и есть данные клиента                        |

### Язык слоёв scaffold

Граница языка проходит по слою, а не по отдельному термину.

- **Методология** может использовать точные термины модели: `Management Unit`, `Management Aspect`, `Management Kit`, `Node`.
- **Сборочный слой** (`_templates/README.md`) даёт словарь разворачивания: английский класс-термин + русское объяснение. Это нужно агенту-строителю, чтобы не потерять архитектурную точность.
- **Живой scaffold клиента** ведётся на русском рабочем языке: объект управления, управленческий ракурс, управленческая панель, папка, служебные папки, рабочие папки клиента.
- **Физические имена файлов, папок и форматов** не переводятся: `README.md`, `YAML`, `01_strategic/`, `03_metrics/`, `_inbox/`, `source/`, `extractors/`, `person.md`, `domain-metrics.md`.

При разворачивании агент отделяет физическое имя от рабочего имени в тексте. Физическое имя остаётся машинным: `sales/`, `marketing/`, `00_ceo/`. Рабочее имя в живых файлах пишется так, как его должен видеть клиент: `Продажи`, `Маркетинг`, имя руководителя. `title`, H1 и аннотация под H1 вместе задают миссию файла для человека, поиска и AI-навигации, поэтому все три специализируются под рабочее имя.

**Симметрия агентов.** Разворачивает на старте наш агент, через неделю — агент клиента. Действие одно — значит и знания одни: шаблоны под рукой плюс инструкция как разворачивать. Поэтому папка шаблонов `_templates/` едет клиенту внутри scaffold — постоянный источник шаблонов, а инструкция по ним — в [_templates/README.md](../../plugin/skills/scaffold/template/_templates/README.md). Методология остаётся у нас; её рабочая проекция (механика + заготовки миссий) — в README шаблонов.

**Узел — тонкий:** по умолчанию узел получает только `README.md`. Вложенные `AGENTS.md`/`CLAUDE.md` не обязательны; на время разработки продукта допускаются как экспериментальный механизм доставки — канон: [02_readme-spec § Доставка README агенту](02_readme-spec.md). Повторяющиеся шаблоны (kit, aspect-файлы) не дублируются в узлах — лежат один раз в папке шаблонов, README ссылается. Вход агента — корневые `AGENTS.md`/`CLAUDE.md`.

**Граница: общий шаблон файла vs шаблон узла.** Форма встречается в ≥2 типах узлов → общий шаблон файла в папке шаблонов (`management-kit/`, `aspects/`, `semantic-files/`), узлы копируют. Форма уникальна для одного типа узла → лежит шаблоном узла в `_templates/nodes/{type}/` (`nodes/ceo/01_profile.md`, `nodes/ceo/02_active.md`, `nodes/ceo/03_thoughts.md`, `nodes/ceo/04_decisions.md`, `nodes/product/profile.md`, `nodes/clients/client-name/company.md`, `nodes/clients/client-name/people.md`). Личные формы панели ceo (`02_active`, `04_decisions`) — уникальные формы этого типа узла, не дубли kit. Живое дерево scaffold содержит только реальные узлы — шаблонов в нём нет.

**Версия шаблона** живёт в README шаблонов, не в самом шаблоне. При создании `version`/`status` в клиентские файлы не переносятся — клиентский файл операционный ([02_file-spec.md § YAML](02_file-spec.md)).

## 🔵 README шаблона узла и живого узла

README узла несёт блок `🔧 Разворачивание` — потенциал роста папки (категории + узловые исключения). Блок **остаётся в клиентском README**: это рабочая инструкция агента клиента, как растить папку. Канон блока (появление и формат) — [02_readme-spec § 🔧 Разворачивание](02_readme-spec.md); механика и шаблоны — в [_templates/README.md](../../plugin/skills/scaffold/template/_templates/README.md).

Дефолтный разворот узла перечислен в `## Содержимое папки` с миссиями. 🔧 дефолт не повторяет — несёт только то, что может доразвернуться сверх него.

README шаблона узла описывает состояние свежеразвёрнутого узла: «Содержимое» и маршруты перечисляют дефолтный разворот — то, что реально создаётся вместе с узлом; остальное находится в 🔧. После дальнейшего разворачивания README поддерживает агент клиента: добавляет созданное в «Содержимое» и маршруты и удаляет соответствующий элемент из 🔧 ([_templates/README § Как развернуть файл или папку](../../plugin/skills/scaffold/template/_templates/README.md)).

**Связи:** ссылки только внутри scaffold (соседние узлы и папки). Пустой блок с плейсхолдером и запрет выдуманных связей — канон [02_readme-spec § Связанные контексты](02_readme-spec.md).

## 🔵 Что читать перед развёртыванием

Наш агент собирает контекст из методологии и шаблонов. Ядро — всегда; остальное — по ходу.

**Ядро:**
1. [01_architecture.md](01_architecture.md) — модель: unit / ракурс / панель / узел, правило размещения «сущность живёт там, где ею управляют».
2. Этот файл — процесс: стартовый минимум, порядок, триггеры, чего не делать.
3. [_templates/README.md](../../plugin/skills/scaffold/template/_templates/README.md) — механика сборки: копирование и переименование шаблонов, формула миссии, словарь разворачивания.

**Для решений о структуре (не для механики — она в `_templates/`):**
4. [management-unit.md](management-unit.md) — корневые и особые units: `00_ceo/`, `01_company/`, `product/`, `clients/`.
5. [management-aspect.md](management-aspect.md) — где физически живёт ракурс (`strategic`, `metrics`).
6. [02_folder-spec.md](02_folder-spec.md) · [02_file-spec.md](02_file-spec.md) · [02_readme-spec.md](02_readme-spec.md) — при создании нешаблонного файла или папки.

Сами файлы панели и ракурсов разворачиваются из шаблонов `_templates/` — методология для этого не нужна.

Агент клиента при доразворачивании методологию не видит (§ Три слоя и поставка) — опирается только на [_templates/README.md](../../plugin/skills/scaffold/template/_templates/README.md).

## 🔵 Порядок развёртывания

1. Снять управленческую модель клиента — включая имена объектов управления, продуктов и проектов. Имя сущности выясняется здесь, а не придумывается на разворачивании. Согласовать правило размещения встреч, проверив его на регулярных встречах клиента.
2. Выбрать корневые units: объекты с регулярным управлением.
3. Создать стартовый каркас `01_company/`; управленческую модель, снятую на шаге 1, зафиксировать в `operating-model.md`.
4. Создать units, по которым уже есть реальная работа.
5. В каждой созданной папке node создать `README.md` из README шаблона узла (см. § README шаблона узла и живого узла). Стартовый обзор — по пресету типа узла: у обычного узла вход `01_overview.md`; у `01_company/` он не создаётся (вход несут README, `operating-model.md` и ракурсы), у `00_ceo/` вход — `01_profile.md`.
6. Подключить aspects только там, где уже есть реальная работа в этом ракурсе. README создаётся только для aspects, чей шаблон уже содержит README; простые `01_strategic/` и `02_team/` README не получают.
7. Подключить kit под реальную работу.
8. Добавить infrastructure folders и client workspace folders по фактическим потокам. `meetings/` — по согласованному правилу встреч.
9. Проверить размещение: владелец → общий родитель → `01_company/` / корень.

## 🔵 Что ставится на старте

Старт — минимальная карта верхнего уровня, не полное дерево. Базу задаёт пакет `template/` — он едет целиком (§ Три слоя и поставка); поверх него создаются units под модель клиента.

- **Корневой `README.md`** — карта scaffold клиента.
- **Корневые `AGENTS.md` и `CLAUDE.md`** — вход агента: рабочая инструкция и её подключение. Состав — по набору агентов клиента, канон: [02_readme-spec § Доставка README агенту](02_readme-spec.md).
- **`_inbox/` и `zz_archive/`** — корневые infrastructure folders.
- **`_templates/`** — папка шаблонов: постоянный источник бланков для доращивания (§ Симметрия агентов).
- **`01_company/`** — обязательно: компания как целое и стартовый каркас управленческой модели.
- **`00_ceo/`** — если CEO ведёт личный управленческий контекст с AI. Раскладка — [management-unit.md § `00_ceo/`](management-unit.md).
- **`{management_unit}/`** — по одному на каждый реальный объект управления клиента. Стартует в форме файла `{unit}.md` или папки `{unit}/` по объёму живой работы.

Остальное — aspects, kit-файлы, дочерние units, `product/`, `clients/`, `projects/`, `processes/`, `knowledge/`, client workspace folders — только по триггеру.

### Стартовый каркас `01_company/`

Стартовый каркас нужен не для симметрии, а как управленческая рамка: CEO видит, что у компании должны быть курс, команда и метрики. Файлы стартового каркаса не пустые: в них заголовки и подсказки, что заполняется на онбординге.

```text
01_company/
├── README.md
├── operating-model.md
├── 01_strategic/
│   ├── vision.md
│   └── goal.md
├── 02_team/
│   └── 01_org-structure.md
├── 03_metrics/
│   └── business-metrics.md
├── _inbox/
└── zz_archive/
```

`01_strategic/` законна в стартовом каркасе, потому что стартует с двумя стратегическими файлами: `vision.md` и `goal.md`. Папка не создаётся ради одного файла.

## 🔵 Триггеры расширения

Расширение — переход сущности на следующую стадию по живой работе. Канон стадий и правило размещения — [01_architecture.md](01_architecture.md).

- **Unit: файл → папка** — у направления появилась регулярная операционная работа: задачи, встречи, решения, прогресс, команда, метрики или материалы.
- **Дочерний unit** — внутри узла появился самостоятельный объект управления со своим владельцем, контекстом и регулярным вниманием.
- **Aspect** — подключается под свой управленческий ракурс: стратегическая работа → `01_strategic/`, команда → `02_team/`, метрики → `03_metrics/`, проекты → `projects/`, процессы → `processes/`, знания → `knowledge/`.
- **Kit-файл** — подключается под свой слой состояния: обзор → `01_overview.md`, текущая работа → `02_active.md`, отложенное → `03_backlog.md`, хроника → `04_progress.md`, решения → `05_decisions.md`.
- **Infrastructure folder** — появляется по своему потоку: сырьё → `_inbox/`, встречи → `meetings/`, источник метрик → `source/` внутри ракурса метрик, извлечение значений → `extractors/` внутри ракурса метрик, холодный контекст → `zz_archive/`.
- **`_private/{владелец}/`** — появляется, когда участнику необходимо личное приватное пространство.
- **Client workspace folder** — появляется, когда у клиента есть рабочие материалы рядом с владельцем: `docs/`, `contracts/`, `pages/`, `drafts/` и другие удобные клиенту папки.
- **Person** — шаблон `person.md` копируется в `{unit}/02_team/` и переименовывается по человеку, например `ivan-petrov.md`; создаётся у операционного владельца при перечислении человека на онбординге, первой встрече или первом упоминании с явной ролью.

## 🔵 Особые объекты и ракурсы

На корне или внутри владельца — только по живому триггеру. Раскладки — [management-unit.md](management-unit.md) и [management-aspect.md](management-aspect.md).

| Форма | Триггер |
|---|---|
| `product/` | продуктом управляют как самостоятельным объектом (не отдел разработки); иначе продуктовый контекст живёт у владельца |
| `clients/` | клиентскими отношениями управляют отдельно: есть свой владелец, метрики и ритуалы; иначе клиенты живут внутри `sales/`, `support/` или account-management unit |
| `projects/` | есть временные инициативы с владельцем, горизонтом и завершением |
| `processes/` | есть повторяемая работа, регламент или операционный стандарт; канон в разработке |
| `knowledge/` | есть обработанное знание, которое unit переиспользует; канон в разработке |

`projects/`, `processes/` и `knowledge/` чаще являются aspects внутри владельца. В корень они выходят только если ими управляют как самостоятельными объектами.

## 🔵 Природа темы выбирает форму

Одна тема у разных клиентов имеет разную природу. «Маркетинг» может быть unit, проектом, процессом или частью продуктовой/коммерческой модели. Сначала определяется, как CEO реально управляет темой, потом выбирается место и глубина.

Размещение проверяется по правилу: операционный владелец → наименьший общий родитель → `01_company/` или самостоятельный корневой unit.

## 🔵 Чего deployment не делает

- Пустые ветки «на всякий случай».
- Полное дерево units/aspects при онбординге без триггеров; исключение — стартовый каркас `01_company/` как якорь управленческой модели.
- Все kit-файлы сразу ради симметрии.
- Файлы-плейсхолдеры под несуществующую сущность.
- Копии «под будущее подразделение».
- `source/` и `extractors/` вне ракурса метрик.

Миграции существующего scaffold — удаление, слияние, перенос, превращение папки обратно в файл — вне этого файла. См. [open-questions.md](open-questions.md) / будущий `lifecycle.md`.
