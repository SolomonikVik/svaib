# Scaffold file spec — канон md-файла scaffold

Канон md-файла scaffold: имя, YAML, шапка (H1 + аннотация), тело (H2-секции, текст внутри), правила файла/блока (опц.), связи. Канон README папки — в [02_readme-spec.md](02_readme-spec.md).

## 🔵 Принципы работы с файлом

1. **LLM + People centered.** Читаемо глазами, парсится моделью без потери смысла.
2. **Один файл — одна роль.** Не смешивать план и итоги, текущую работу и хронику.
3. **Компактность.** Лишнее = шум = потраченные токены.
4. **Лимит файла** — ориентир <300 строк. Оперативный файл (active, backlog, decisions) перерос — дробить на несколько с явными связями. Легитимно длинный справочный (методология, исследование) дробить не обязан — в начало `## Обзор`.
5. **Минимум дублирования.** У каждого факта одно каноническое место.

## 🔵 Миссия файла

У каждого канонического файла scaffold есть миссия: зачем этот файл существует, какую работу делает в узле. При поиске, чтении или маршрутизации новой информации (задачи, решения, мысли, факта) — в первую очередь сверяемся с миссией файла.

**Хорошая миссия файла:**
- описывает работу файла в системе;
- подсказывает, в каком случае файл стоит читать;
- помогает решить, ляжет ли сюда новый факт;
- отличает файл от соседей в той же папке (`active` vs `backlog` vs `progress`).

**Где живёт миссия файла:**
- универсальная миссия kit-файла (что вообще делает `active`, `decisions` и т.д.) — в [management-kit.md](management-kit.md);
- миссии файлов управленческих ракурсов (`vision.md`, `org-structure.md`, `business-metrics.md` и др.) — в [management-aspect.md](management-aspect.md);
- типовые смысловые файлы (`profile.md`, `architecture.md`, `setup.md`, `glossary.md`, `speech-aliases.md`) — в [01_architecture.md § Типовые смысловые файлы](01_architecture.md);
- миссии файлов отдельных units (`operating-model.md` в `01_company/`, `01_profile.md`, `03_thoughts.md` в `00_ceo/`, особенности `product/`, `clients/`) — в [management-unit.md](management-unit.md);
- адаптация миссии под конкретный узел — в колонке «Миссия» таблицы содержимого в `README.md` папки. Канон — [02_readme-spec.md](02_readme-spec.md);
- внутри самого файла отдельная секция `Миссия файла` не пишется: миссия считывается через путь, имя файла, `title` / H1 и аннотацию под H1.

## 🔵 Имя файла

**Принципы:**
- `filename` = поисковый запрос. Агенты ищут по именам файлов; имя передаёт миссию и сжатую суть.
- `filename` = id файла. Rename → точечная правка ссылок.
- `filename` называет роль файла, `path` называет субъект. Для типовых файлов (`01_overview.md`, `architecture.md`, `setup.md`) субъект не добавляется в filename по умолчанию.

**Общая формула:**

```text
{optional-prefix}_{semantic-name}.md
```

**Semantic-name:**
- `kebab-case` — строчные английские слова через дефисы, без транслита: `system-principles.md`, `weekly-progress.md`, `file-spec.md`.

**Optional-prefix:**
- **Числовой** двузначный + `_` (`NN_`) — см. § Нумерация и порядок ниже.
- **Датированный.** ISO 8601, всегда первый: `YYYY-MM-DD_{semantic-name}.md`. Используется там, где дата важна, например `decisions/`.

**Файлы папки встречи** — фиксированные имена по жизненному циклу: `agenda.md`, `transcript.md`, `summary.md`, `protocol.md`. Дата и тип встречи — в имени папки ([meeting-types.md](../ontology/meeting-types.md)); канон папки встречи — [02_folder-spec § meetings/](02_folder-spec.md).

### 🔹 Нумерация и порядок

Канон нумерации общий для файлов и папок — имя в scaffold не зависит от того, файл это или папка (`foo.md` → `foo/`).

- **`NN_` — только где порядок или группировка семантически важны.** Исключение, не дефолт. Дефолт — `kebab-case` без префикса.
- **Цифра — атрибут сортировки, не часть имени.** `decisions` и `NN_decisions` — один файл; ссылки в прозе дают по семантическому имени без цифры, перенумерация их не ломает.
- **Дубли запрещены.** Два одинаковых `NN_` в одном ряду ломают принцип «номер = адрес».
- **Дыры — норма.** Номер = адрес, не счётчик подряд. Ряд `01, 02, 04` валиден — отсутствие файла оставляет пропуск, это не дефект.
- **Совпадение номеров в разных рядах допустимо.** Файл `01_foo.md` и папка `01_bar/` уживаются: целевые среды сортируют папки и файлы раздельно.
- **Номер не гарантирует стабильность между контекстами.** Один тип файла может получить разный номер в разных пресетах, где состав соседей иной. Глобально-стабильный номер типа — возможно позже, пока не вводим.
- **Инвариант файл↔папка.** Папка наследует имя файла без расширения, префикс сохраняется.


## 🔵 YAML

**YAML** — стандартизированные метаданные для поиска. Агент не парсит YAML как базу данных — ищет текстовым поиском (`rg '^status: raw$'`). YAML работает потому что это конвенция: одинаковый формат, предсказуемое место, индустриальный стандарт.

### Два режима YAML

**Обычный scaffold-файл** — живой клиентский файл или README, где метаданные не должны создавать churn:

```yaml
---
title: "..."
---
```

Для такого файла обязательный YAML — только `title`. `created` / `updated` не ставятся: даты событий, решений и прогресса фиксируются в теле файла, рядом с самими записями.

**SOT / canon / spec / methodology / skills / template registry** — канонический файл, где важны версия, история формы или статус готовности. Здесь допустимы `created`, `updated`, `version`, `status`:

```yaml
---
title: "..."
created: YYYY-MM-DD
updated: YYYY-MM-DD
version: N
status: final
---
```

### Поля

- **`title`** — зеркало H1 для YAML-scan и карточки файла. Подробнее — § Шапка файла.
- **`created`** (`YYYY-MM-DD`) — дата создания канонического/SOT/spec/methodology/registry-файла, если она нужна для истории формы.
- **`updated`** (`YYYY-MM-DD`) — дата последнего смыслового обновления канонического/SOT/spec/methodology/registry-файла.
- **`version`** — только для SOT, spec, templates, skills, где важна версия канона. Не используется в операционных клиентских файлах.
- **`status`** (`raw` / `draft` / `review` / `final`) — стадия готовности канонического файла. `final` = редактирование агентом запрещено без согласования.

**Опциональные поля** `domain`, `tags`, `source` — добавляются при появлении живой потребности (поиск по доменам, knowledge-теги).

**Лимит — ≤8 полей.** Больше — бремя поддержки превышает пользу.

### Даты в операционных файлах

В операционных клиентских файлах дата — часть самой записи, а не глобальный `updated`.

- `progress` — дата события в H2 или строке события.
- `decisions` — дата решения рядом с решением.
- `active` / `backlog` — даты только если они относятся к задаче, дедлайну или событию.

Не обновлять YAML ради каждого смыслового изменения живого scaffold-файла.

## 🔵 Шапка файла

После YAML и до первой H2 тела идёт **шапка** — фиксированная последовательность элементов, передающая миссию и суть файла без чтения тела.

H1 виден человеку при открытии файла (Obsidian, IDE), `title` в YAML — машине при YAML-scan. По умолчанию `title` = зеркало H1 (см. § YAML).

**Что обязательно:**
- H1 — всегда.
- Одно из двух: **аннотация** (дефолт) или **`## Обзор`** (для длинных справочных файлов).

### H1

**Формула:**

```text
{домен/сущность} — {что внутри / зачем читать}
```

**Требования:**

1. **Информативность.** Отвечает на «что это и для чего», не метка. `Overview` — плохо. `Marketing — активная работа направления` — нормально.
2. **Лимит:** ≤120 символов, одна строка.
3. **`title` (YAML) = H1 по умолчанию.** Расхождение допустимо только если `title` нужен под отдельную задачу (редкий случай).
4. **Типовой filename требует явного субъекта.** Если файл повторяется в разных узлах (`01_overview.md`, `architecture.md`, `setup.md`, `glossary.md`), H1/title пишется как `{субъект} — {роль}`.

**Можно упростить,** если path + filename самодостаточны: `marketing/02_active.md` → `Marketing — активные задачи` хватает.

### Аннотация

**Дефолт для всех файлов scaffold.** Абзац сразу под H1, без `##`-заголовка.

**Что внутри:**
- Описание сути файла — что внутри и зачем.
- Inline-ссылки на соседние/связанные файлы — задают быструю навигацию.

**Лимит:** до 25-30 слов.

**Пример:**
```markdown
Грамматика папки scaffold: имя, миссия, жизненный цикл, канон служебных папок и место рабочих папок клиента. Управленческая семантика конкретных видов папок — в [management-unit.md](management-unit.md), [management-aspect.md](management-aspect.md).
```

### Обзор (опц.)

Расширенная сводка для длинных справочных файлов, где аннотации мало. **Заменяет аннотацию** — одно из двух.

**Когда нужно:**
- Длинный справочный файл, где суть не вмещается в 25-30 слов аннотации.
- Полезна и человеку, и LLM (исследование, длинная методология, аналитика).

**Когда не нужно:** операционные файлы (`active`, `backlog`), короткие справочные файлы, всё, что покрывается аннотацией.

**Формат:** секция `## Обзор`, 2-4 предложения, ≤100 слов.

## 🔵 Тело файла: H2-секции

H2 задают основную структуру файла: человеку дают навигацию, агенту — карту файла без чтения тела (`rg '^## '`) и семантические границы для выборочного чтения.

H2 также являются основной единицей чанкинга для RAG. Ориентир размера секции — 250-500 слов.

**Требования к H2:**
- **Самоописывающие.** `Бюджет проекта Alpha Q1 2026`, не `Бюджет`.
- **С контекстом.** Субъект, период или проект указываются в заголовке, если не очевидны из пути и H1.
- **Уникальные внутри файла.** Повторяющиеся H2 ломают навигацию.
- **Автономные.** Секция должна быть понятна без чтения соседних секций.

**Автономность секции означает:**
- повторять субъект, а не писать «он», «это», «там» без контекста;
- давать короткий контекст в начале секции, если он нужен;
- использовать конкретные термины, а не «сделали это».

**H3** — внутренняя детализация H2, не главный навигационный якорь.

## 🔵 Текст внутри секций

Текст внутри секции должен одинаково хорошо читаться человеком и агентом: без лишних токенов, скрытых смыслов и сложной вложенности.

### Когда параграф, когда список, когда таблица

- **Параграф** — для прозы, рассуждения, объяснения. Один абзац — одна мысль.
- **Маркированный список** — для дискретных элементов (правила, шаги, перечисление). Самая надёжная форма для LLM. Вложенность ≤2 уровня — глубже связи теряются.
- **Key-value список** (`**поле** — описание`) — для набора однотипных параметров с пояснением: поля YAML, атрибуты сущности, параметры. Лучший формат для извлечения LLM.
- **Простая таблица** — когда выполнено **любое** из двух:
  (а) данные идут по **>3 однородным осям на нескольких строках** в файле, который читает человек (клиентский overview: веха · срок · результат · статус) — визуальная сетка выигрывает у простыни буллетов;
  (б) **много строк (≥8-10) + сравнение по колонке** (читаешь «вниз по оси»). Все ячейки заполнены, лимит ≤20 строк; больше — заголовки «забываются».
- **Иначе — буллеты.** Перечисление по одной оси, навигация, чтение «по одному элементу» (нашёл → открыл). Агентские и навигационные файлы (README, спеки, deploy-списки) — буллеты по умолчанию: токены и парсинг важнее визуала.
- **Подписанные поля.** Если в строке несколько разных сущностей (что создать / зачем / откуда) — каждую подписывать явным полем (`Создать: …`), а не склеивать в один объект. Инструкции и данные разграничивать, поля именовать однозначно.

### Выделения

- **Жирный** — повышает вес термина для LLM и человека. Для ключевых слов, имён сущностей, важных ярлыков.
- *Курсив* — лёгкий акцент, цитата, термин в первом упоминании.
- Если жирно всё — не выделено ничего. Норма — несколько ключевых слов на абзац.
- **Без padding.** Не выравнивать таблицы или списки пробелами ради красоты в сыром md: выравнивание человек в рендере не видит, модель не использует, а лишние токены и сдвиг представлений реальны.

### Эмодзи-маркеры

Эмодзи — стабильные визуальные маркеры, если помогают навигации и используются последовательно. Не вводить новые ради украшения. Три **разных** слоя, не путать.

**1. Секционные маркеры H2 — тип раздела.** Эмодзи-префикс на заголовке для различения разделов в Obsidian и любом рендере. Один тип секции = один эмодзи, стабильно во всех файлах:

- 🎯 — Цель / Цели и КР
- 📈 — Метрики
- 👥 — Команда
- 🚩 — Дорожная карта / Вехи
- ✅ — Задачи / Активная работа
- ⁉️ — Открытые вопросы
- 📌 — Решения
- ❇️ — нейтральный дефолт: прочие смысловые H2 (Суть, Миссия, Для кого, Принципы…)

Формат строго `## <эмодзи> <Имя>`. Ссылка на секцию — по тексту заголовка, не по якорю с эмодзи (якоря с эмодзи бьются вне Obsidian). Применять: витрина узла (`01_overview`, `vision`, `goal`, `profile`) + `02_active` / `03_backlog`. Не применять: справочники-таблицы, хроники по датам (`progress`, `decisions`), README, infrastructure.

**2. Статусные маркеры — состояние пункта.** На пунктах списков, не на заголовках:

- ⭕️ в работе · ✅ готово · 🛑 блокер · ❗️ важно
- светофор: 🟢 по плану · 🟡 риск · 🔴 срыв

**3. Маркеры выверенности — служебные, для внутренних файлов методологии:** 🔵 выверено человеком · 🤖 правил агент, не выверено вручную.

✅ работает на двух уровнях — как маркер раздела «Задачи» (H2) и как статус «готово» (пункт). Уровень разводит контекст, это осознанно.

## 🔵 Пробелы и структура

Markdown — блочный формат: границу блока задаёт пустая строка. Пишем на пересечении CommonMark + GFM-таблицы — чтобы файл одинаково рендерился в Obsidian, VS Code, GitHub, чате.

**Обязательное (иначе ломается рендер или grep/чанкинг агента):**

- пустая строка до и после заголовка, списка, fenced-кода и **перед таблицей** (Obsidian требует, GitHub прощает → ставим всегда);
- пробел после `#` (`## Имя`) и после маркера списка (`- пункт`);
- code только в fenced-блоке с языком, не отступом;
- один H1 на файл, дальше `##`;
- файл заканчивается ровно одним переносом строки;
- только CommonMark + GFM — без `[[wikilinks]]`, `==highlight==`, callouts `> [!note]`; ссылки `текст`.

**Рекомендуемое (стиль):**

- максимум одна пустая строка подряд;
- только ATX-заголовки `##` (без `===`/`---`-подчёркивания);
- маркер списка всегда `-`; вложенность 2 пробела;
- tight-списки (без пустых строк между пунктами); нумерованные — все `1.`;
- без trailing-пробелов и табов;
- проза — цельными абзацами, не «предложение на строку»;
- длину строки в прозе жёстко не лимитировать.

Полный чек-лист с MD-кодами и источниками — в _inbox/subagents/md-formatting-standard/.

## 🔵 Правило работы с файлом и секцией (опц.)

Локальная инструкция агенту, которую нельзя вывести из имени, README или canonical templates.

**Когда нужно:**
- локальная специфика этого файла;
- локальное исключение из общего канона;
- предупреждение о типичной ошибке.

**Когда не нужно:** в каноническом файле узла, если правило работы понятно из имени.

**Синтаксис:**

```markdown
> **Правило файла:** {одно конкретное проверяемое правило, действующее на весь файл}

H2-секция

> **Правило секции:** {одно правило, действующее только на эту секцию}
```

**Требования к правилу:**
- конкретное и проверяемое: «новые записи в начало; старые не редактировать», не «будь аккуратен»;
- одно-два правила. Если больше — выносить в README, canonical templates, procedure или skill.

Правила файла и секции могут использоваться агентом или хуком перед редактированием. Если нужен жёсткий запрет, он фиксируется отдельным validator/procedure, не текстом правила.

Справочные блоки `Что сюда`, `Не сюда`, `Куда писать` внутри обычного рабочего файла не создаются. 

## 🔵 Связи между файлами

В обычных файлах scaffold связи живут inline в тексте через markdown-ссылки с контекстом перехода: `подробнее — [02_folder-spec.md](02_folder-spec.md)`.

Голая ссылка без объяснения, зачем переходить, бесполезна: агент не знает приоритета и причины перехода.

Для типовых файлов link label раскрывает субъект и роль: `Marketing overview`, `Product architecture`, `ACME setup`. Голые ссылки вроде `overview` или `architecture` не использовать, если из текста не очевидно, чей это файл.

Навигационный граф папки живёт в README, не в обычном файле. Канон README — в [02_readme-spec.md](02_readme-spec.md).

Если возможно, ссылку лучше давать на папку или README: они стабильнее при переименовании файлов внутри папки.
