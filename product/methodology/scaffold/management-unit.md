# Management units — объекты управления в scaffold

Management unit — объект управления в scaffold: направление, функция, подразделение, филиал, бизнес-юнит, продукт или портфель клиентов. Этот файл фиксирует, что считать unit и как он разворачивается. Общий закон node — в [01_architecture.md](01_architecture.md), управленческая панель — в [management-kit.md](management-kit.md), управленческие ракурсы — в [management-aspect.md](management-aspect.md).

## 🔵 Что такое management unit

Management unit — объект, за который кто-то отвечает и которым регулярно управляют.

Unit появляется, когда у сущности есть:
- **ответственность** — понятно, кто отвечает за объект;
- **контекст** — есть свои цели, задачи, решения, люди, метрики или материалы;
- **регулярное внимание** — к этому объекту возвращаются в работе, а не просто хранят справку.

Что именно становится unit, решает управленческая модель клиента. У одного клиента units — функции (`marketing/`, `sales/`, `finance/`), у другого — филиалы, у третьего — бизнес-направления.

## 🔵 Как разворачивается unit

Unit растёт от простого к сложному.

### 🔹 Стадия 1 — файл

Если сущность нужна как контекст, но ещё не требует отдельной операционной работы, она может быть одним файлом:

```text
marketing.md
```

Внутри — коротко: что это, кто отвечает, текущее состояние, важные ссылки.

### 🔹 Стадия 2 — папка

Когда у сущности появляется регулярная работа, файл превращается в папку с тем же именем:

```text
marketing/
├── README.md
├── 01_overview.md
├── ... файлы management kit
├── ... management aspects
├── ... infrastructure folders
├── ... client workspace folders
└── ... дочерние units
```

Что подключается:

| Блок               | Что даёт                                                                                 | Канон                                        |
| ------------------ | ---------------------------------------------------------------------------------------- | -------------------------------------------- |
| `README.md`        | карта папки и маршрутизация агента                                                       | [02_readme-spec.md](02_readme-spec.md)       |
| Management aspects | управленческие ракурсы: strategic, team, metrics, projects, processes, knowledge         | [management-aspect.md](management-aspect.md) |
| Management kit     | управленческая панель: overview, active, backlog, progress, decisions                    | [management-kit.md](management-kit.md)       |
| Infrastructure folders | inbox, private, meetings, source, extractors, zz_archive                             | [02_folder-spec.md](02_folder-spec.md)       |
| Client workspace folders | docs, contracts, pages, drafts и другие рабочие папки клиента                    | [02_folder-spec.md](02_folder-spec.md)       |
| Дочерние units     | вложенные объекты управления                                                             | этот файл                                    |

Ничего не создаётся ради симметрии. Подключается только то, что нужно для живой работы.

### 🔹 Стадия 3 - Родительский unit с дочерними units

Родительский unit нужен, когда несколько units управляются как один блок: `commercial/` = `marketing/` + `sales/`, `backoffice/` = `finance/` + `hr/` + `legal/`, филиал = продажи + операции + склад.

```text
commercial/
├── README.md
├── 01_overview.md
├── marketing/
├── sales/
└── partnerships.md
```

Родитель не дублирует дочернее. На уровне `commercial/` живёт только общее для всего блока: общая стратегия, общие решения, общие встречи, общие проекты, общие метрики. Локальное живёт в дочернем unit.

#### Правило общей родительской папки

Артефакт живёт в той папке, которая охватывает всех участников.

| Охват артефакта | Где живёт |
|---|---|
| Внутри одного дочернего unit | `{parent}/{child}/` |
| Между несколькими дочерними units одного родителя | `{parent}/` |
| Между несколькими верхними units / вся компания | `01_company/` |

Правило применяется к встречам, решениям, задачам, прогрессу, проектам и метрикам. Это частный случай общего правила размещения из [01_architecture.md](01_architecture.md). Место хранения встреч может не подчиняться общему правилу — см. [02_folder-spec § `meetings/`](02_folder-spec.md).

## 🔵 Особые units

Эти папки не являются отдельными классами scaffold. Но имеют рекомендуемую стартовую конфигурацию. Любая из них может подключать management kit, aspects, infrastructure folders, client workspace folders и дочерние units по общему закону node.

### 🔹 `00_ceo/` — личный контекст CEO

Личный управленческий контекст руководителя: ценности, стиль мышления, личные задачи, мысли и личные решения. Только то, что больше нигде не живёт. Опциональный unit — разворачивается, когда CEO работает с AI лично.

```
00_ceo/
├── README.md             ← карта папки
├── 01_profile.md         ← кто я, ценности, стиль работы
├── 02_active.md          ← личные задачи и открытые вопросы CEO
├── 03_thoughts.md        ← мысли впрок: идеи, рефлексии, тревоги, гипотезы
└── 04_decisions.md       ← личные твёрдые решения CEO
```

Особенность: `03_thoughts.md` — мягкая зона мыслей впрок (единственный файл, которого нет в других пресетах); CEO волен добрать management kit, `_inbox/` и другие рабочие папки.

### 🔹 `01_company/` — компания как целое

Company-level unit: курс компании, цели, стратегические решения, общая команда, целевые метрики, кросс-функциональные сущности. Это не контейнер всего бизнеса и не корзина для неразложенного.

Пример, не стартовый набор:
```text
01_company/
├── README.md       ← карта контекста уровня компании
├── operating-model.md ← система управления компании
├── _inbox/         ← входящее на разбор уровня компании
├── 01_strategic/   ← стратегия уровня компании: vision, цели, стратегия
├── 02_team/        ← команда уровня всей компании: оргструктура и люди
├── 03_metrics/     ← целевые метрики уровня всей компании
├── meetings/       ← встречи уровня всей компании (если есть)
├── docs/           ← или другие рабочие папки клиента для документов уровня компании (если есть)
├── processes/      ← кросс-функциональные процессы без более узкого владельца (если есть)
├── projects/       ← кросс-функциональные проекты без более узкого владельца (если есть)
└── zz_archive/     ← холодный и завершённый контекст уровня компании
```

**`operating-model.md`** — система управления компании: как устроено управление и как стратегия превращается в работу организации. Уникальная форма company-unit: один на клиента, обязателен в стартовом каркасе ([deployment.md](deployment.md)), always-read при управленческой работе ([02_readme-spec § Доставка README агенту](02_readme-spec.md)). Держит модель, а не её значения: цели — в `01_strategic/goal.md`, метрики и люди — в своих файлах.

Детальная анатомия этих aspects — в [management-aspect.md](management-aspect.md).

### 🔹 `product/` — продукт как объект управления

`product/` — unit для продукта компании: что поставляется клиентам, как устроено, куда развивается. На корне появляется, если продуктом управляют как самостоятельным объектом. Несколько продуктов разворачиваются вложенно: `product/saas-a/`, `product/saas-b/`. **`product/` — сам продукт, не подразделение.** Отдел разработки продукта — обычный unit (например `product-development/`).

```text
product/
├── README.md             ← карта продукта
├── 01_overview.md        ← состояние продукта и ближайшее направление
├── profile.md         ← паспорт продукта: позиционирование, ICP, границы, бизнес-модель
├── ... management kit    ← active, backlog, progress, decisions по потребности
├── ... aspects           ← strategic, team, metrics, projects и др. по потребности
└── architecture.md       ← внутреннее устройство продукта
```

Канон в проработке. Базово `product/` использует универсальную схему unit. Спец-файл `architecture.md` — внутреннее устройство (компоненты, связи, стек, интеграции), разворачивается когда устройство важно для управления. `profile.md` = паспорт продукта.

### 🔹 `clients/` — клиентский портфель

`clients/` — parent unit для портфеля клиентов. На корне появляется только если клиентскими отношениями управляют отдельно: есть свой владелец, метрики и ритуалы. Иначе клиенты живут внутри владельца: `sales/`, `support/`, account-management unit и т.д.

```text
clients/
├── README.md             ← карта клиентского портфеля
└── {client}/              ← конкретный внешний проект, папка названа именем клиента
    ├── ... management kit ← overview, active, backlog, progress, decisions по потребности
    ├── people.md         ← люди контрагента: роли, влияние, позиция, коммуникация
    ├── people-ivan-petrov.md ← подробный профиль человека, если `people.md` разросся
    ├── company.md        ← бизнес: продукт, цифры, стратегия; люди — ссылками на people.md, если он развёрнут
    ├── setup.md          ← техническая конфигурация: инструменты, подписки, структура
    ├── meetings/         ← протоколы встреч
    │   └── zz_archive/   ← сырые транскрибации и полный материал встреч
    ├── deliverables/     ← материалы для контрагента
    └── docs/             ← рабочая папка клиента для юридических и исходных документов
```
