# Scaffold node review — QA-гейт узла на соответствие канону v4.1

Проверка развёрнутого узла на соответствие канону scaffold v4.1 перед финальной выгрузкой клиенту. Прогоняется папка за папкой: каждый узел судится **по тем же файлам, что видел агент-сборщик** — клиентский агент методологию не видит, поэтому и ревьюер по ней не судит. Как разворачивать — [deployment.md](deployment.md).

## Когда запускать

Перед передачей пространства клиенту, когда узлы развёрнуты. Узлов несколько → один субагент, пути докидываются follow-up'ом: канон читается один раз, по каждому узлу — отдельный вердикт. Новый чат на каждый узел не нужен.

## Как запускать

Субагент general-purpose, свежий контекст. Подставь `{path}` — путь узла. Несколько узлов — продолжай того же субагента, не запускай новый.

## Промпт

```
Ты — независимый ревьюер scaffold v4.1. Оцени узел по адресу {path} на соответствие канону. Не правь — только отчёт.

Ты судишь ФОРМУ узла по канону, не наполненность данными и не право узла на существование. Пустой kit (02_active без задач, 04_decisions без решений) и стартовая рамка с подсказками — НОРМАЛЬНОЕ состояние свежесозданного узла, не нарушение: данные внесёт клиент в работе. Нужен ли узел и пора ли его наполнять — решает координатор с контекстом запроса клиента, не ты.

КАНОН (читай отсюда, это всё, что видит агент-сборщик у клиента):
- product/plugin/skills/scaffold/template/_templates/README.md — механика сборки, словарь, формула миссии файла
- product/plugin/skills/scaffold/template/README.md — карта пространства
- найди корень проверяемого клиентского пространства, содержащего {path}, и прочитай поставленную туда корневую рабочую инструкцию: AGENTS.md или, при Claude-only поставке, CLAUDE.md — правила агента: размещение, как писать
- product/plugin/skills/scaffold/template/_templates/ — сами шаблоны (management-kit/, nodes/, aspects/), сверь живые файлы с болванками
Нашу методологию (product/methodology/scaffold/) НЕ читай — её в клиентском пакете нет.

Затем прочитай все файлы узла {path}.

Проверь:
1. Миссия каждого файла (title + H1 + аннотация под H1) специализирована под субъект узла, если субъект известен. Незаменённые служебные плейсхолдеры в title/H1/аннотации ({node}, узел, unit, client-name) при известном субъекте — нарушение. Имя-slug (project-01) при ещё не полученном имени — допустимо.
2. README отражает реально созданные файлы (не полный дефолт шаблона), есть маршруты чтения/записи и связи. Лишний README в простом ракурсе (`01_strategic/`, `02_team/`) — расхождение: эти ракурсы навигируются родительским README и своими файлами.
3. Размещение: сущность живёт там, где ею управляют.
4. Нет мусора (.DS_Store и пр.).
5. Kit и ракурсы, если подключены, оформлены по канону. Полноты не требуй — состав определяется живой работой, а не симметрией.
6. Базовый file-spec: YAML title есть, аннотация под H1 есть, файл автономен.
7. В живой клиентский текст не попал технический язык scaffold и незаменённые плейсхолдеры: `узел`, `узловой`, `узловые`, `node`, `nodes`, `unit`, `management unit`, `aspect`, `management aspect`, `kit`, `management kit`, `scaffold`, `scaffold v4`, `шаблон`, `болванка`, `плейсхолдер`, `generic`, `slug`, `территория`, `{node}`, `{unit}`, `{topic}`, `{project-name}`, `{process-name}`, `{client-name}`, `{ceo}`, `{person}`.

Верни:
- Вердикт: соответствует / есть расхождения.
- Таблицу: файл → что не так → пункт канона (с именем файла канона) → как исправить.
```
