# Управленческие ракурсы — стратегия, команда, метрики, проекты, процессы, знания

Management aspects — подключаемые управленческие ракурсы внутри unit: strategic, team, metrics, projects, processes, knowledge. Общая модель — в [01_architecture.md](01_architecture.md); объекты управления unit — в [management-unit.md](management-unit.md); управленческая панель — в [management-kit.md](management-kit.md).

## 🔵 Что такое management aspect

**Management aspect** — управленческий ракурс внутри unit. Он отвечает на вопрос: **через какой управленческий ракурс мы сейчас смотрим на unit?**

Базовые aspects:
- **Стратегический ракурс** — зачем unit существует, куда идёт и за счёт чего достигает цели.
- **Команда** — кто ведёт unit и как распределена ответственность.
- **Метрики** — по каким цифрам видно состояние и движение.
- **Проекты** — через какие временные инициативы идёт изменение.
- **Процессы** — через какие повторяющиеся действия работает unit.
- **Знания** — на какой корпус знаний unit опирается.

## 🔵 Правила aspect

1. **Подключается только по живой работе.** Нет своих метрик — нет `03_metrics/`, нет проектов — нет `projects/`. Папка не создаётся ради симметрии.

2. **Ключевые aspects нумеруются.** `01_strategic/`, `02_team/`, `03_metrics/` поднимаются наверх и задают порядок чтения. Остальные (`projects/`, `processes/`, `knowledge/`) — без номера.

3. **Место — по общему [правилу размещения](01_architecture.md):** владелец → общий родитель → `01_company/`.
   - один unit-владелец → внутри него: `marketing/01_strategic/`, `{branch}/03_metrics/`
   - общий для дочерних units → у родителя: `commercial/03_metrics/`, `commercial/02_team/`
   - вся компания / без владельца → `01_company/`: `01_company/02_team/` (руководство), `01_company/03_metrics/` (целевые)

4. **Aspect может быть файлом или папкой.** Компактно — файл `{unit}/{aspect}.md`; разрослось — папка `{unit}/{aspect}/`. Для нумерованных aspects имя сохраняет префикс: `03_metrics.md` → `03_metrics/`. Стадии роста — [01_architecture.md](01_architecture.md). Для `01_strategic/` физическое правило описано ниже.

## 🔵 Канонические aspects

### 🔹 `01_strategic/` — стратегический ракурс unit

**Ракурс.** В стратегическом ракурсе фиксируется направление unit: зачем он существует, куда идёт и за счёт каких выборов достигает цели.

В нём различаются три типа стратегических файлов:

- **`vision.md`** — идентичность и видение: кто мы, зачем существуем, какое будущее строим, на каких принципах действуем.
- **`goal.md`** — цель и план: куда идём, к какому сроку, какие результаты и плановые метрики считаем успехом. Источник правды по целям, их плановым метрикам и владельцам.
- **`strategy.md`** — действующие выборы: где играем, как выигрываем, на что ставим и от чего отказываемся.

Если у unit нужен только один из этих файлов, он лежит прямо в unit. Например:

```text
{unit}/goal.md
```

Папка `01_strategic/` появляется, когда у unit есть несколько стратегических файлов или стратегическая работа стала отдельной регулярной зоной:

```text
01_strategic/
├── vision.md
├── goal.md
└── strategy.md
```

Не заводить `01_strategic/` ради одного `goal.md`, `vision.md` или `strategy.md`.

`strategy.md` может включать только нужные разделы:

- **Стратегия компании или unit** — какие направления, рынки или бизнес-линии ведём.
- **Конкурентная стратегия** — кто клиент, кто конкуренты, за счёт чего выигрываем.
- **Продуктовая стратегия** — что продаём, для кого, чем продукт отличается от альтернатив.
- **Go-to-market стратегия** — как доходим до клиента и доводим до повторной покупки.
- **HR-стратегия** — какие роли и компетенции нужны для выбранного курса.
- **Финансовая стратегия** — на какие деньги растём и какие финансовые границы держим.

Если один раздел стратегии стал самостоятельной регулярной работой, он выносится рядом с `strategy.md`:

```text
01_strategic/
├── strategy.md
├── strategy_competitive.md
├── strategy_product.md
└── strategy_gtm.md
```

Стратегический подфайл живёт у владельца темы. Например, продуктовая стратегия лежит в `product/01_strategic/`, если `product/` выделен как unit. В `01_company/01_strategic/` она остаётся только пока продуктовая логика не выделена в самостоятельный объект управления.

**Связка цель ↔ проекты (тонкая карта).** Проект живёт у владельца — `{unit}/projects/`; `goal.md` держит под каждой целью реестр проектов — ссылки на их карточки. Карточка ссылается обратно: вклад в какую цель; плановые метрики цели не дублирует — источник правды `goal.md`. Рамка целеполагания клиента (OKR, годовые цели) — содержимое `goal.md`, не отдельные папки scaffold; клиент может называть проект инициативой — фиксируй его язык, но сущность живёт в `projects/`. Как цели каскадируются в работу — модель управления клиента, `01_company/operating-model.md`.

**Граница:** `strategy.md` хранит действующие выборы; `05_decisions.md` хранит историю их принятия.


### 🔹 `02_team/` — кто ведёт unit

**Ракурс.** В ракурсе команды видны люди и ответственность внутри unit.

**Анатомия:**

```
02_team/
├── 01_org-structure.md   ← входная карта ролей и подчинения
└── person.md             ← профиль человека (живой файл — по имени человека)
```

`org-structure` получает префикс `01_`: это входная карта ракурса, которая должна оставаться выше профилей людей.

**Файлы ракурса команды:**

- **`org-structure.md`** — оргструктура этого unit: подразделения, должности/роли, ФИО людей и ссылки на их профили плюс ссылки на дочерние `02_team/`
- **`person.md`** — профиль человека: роль, зона ответственности, цели и приоритеты, стиль работы, сильные стороны, зоны развития. `person.md` — имя шаблона; живой файл называется по человеку (`ivan-petrov.md`).
- **Контракт человека** (опционально) — персональные обязательства (год/квартал): кратко — секцией в профиле; развёрнуто — отдельным файлом рядом с профилем, названным по человеку (`ivan-petrov-contract.md`). Отдельная contract-system не строится.

Пример `org-structure.md`:

- **CEO** — Иван Иванов
  - **COO** — Анна Смирнова
  - **Руководитель продукта** — Мария Петрова → Product team
    - **Product manager** — Павел Орлов
  - **Руководитель продаж** — Олег Сидоров → Sales team
    - **Руководитель отдела продаж 1** — Екатерина Морозова
    - **Руководитель отдела продаж 2** — Дмитрий Волков
    - **Руководитель телемаркетинга** — Наталья Кузнецова

**Как хранить команду и оргструктуру:**

Если CEO ведёт только руководителей, их профили и верхняя оргструктура живут в `01_company/02_team/`, даже если эти руководители управляют нижними units.

Если внутри unit появляется отдельная работа с командой, создаётся `{unit}/02_team/`. Туда переносится соответствующая часть оргструктуры и только те профили людей, которые теперь ведутся внутри этого unit.

Верхний уровень не дублирует нижнюю команду подробно. Он оставляет у себя руководителя, дочерний unit и ссылку на его `02_team/`.

Один человек = один профиль. В других местах ставятся ссылки.

Полная оргструктура не хранится в одном файле. Она собирается сверху вниз через `org-structure.md` и ссылки на дочерние `02_team/`.

### 🔹 `03_metrics/` — по каким цифрам видно состояние

**Ракурс.** В ракурсе метрик хранится семантика метрик unit: какие показатели важны, что они значат, где их источник и как по ним читать состояние.

Полная архитектура metrics-вертикали — [../metrics/architecture.md](../metrics/architecture.md). Формат metrics-файлов — [../metrics/metrics-spec.md](../metrics/metrics-spec.md).

**Анатомия:**

```
03_metrics/
├── README.md
├── business-metrics.md       ← только в `01_company/03_metrics/`
├── {domain}-metrics.md       ← по живой потребности
├── source/                   ← локальные источники клиента, если нужны
└── extractors/               ← per-client extractors
```

**Файлы ракурса метрик:**

- **`business-metrics.md`** — базовый файл ключевых бизнес-метрик клиента. Один на клиента, живёт в `01_company/03_metrics/`.
- **`{domain}-metrics.md`** — файл метрик одного бизнес-домена. Канонический список имён — [metrics-spec.md § Канонические имена domain-файлов](../metrics/metrics-spec.md#канонические-имена-domain-файлов). Живёт у владельца домена: например, `marketing/03_metrics/marketing-metrics.md`; если домен общий для нескольких units — у общего родителя.
- **`source/`** — локальные xlsx/выгрузки клиента, если источник хранится рядом со scaffold.
- **`extractors/`** — клиентские процедуры извлечения данных из источников.

**Граница:** `03_metrics/` хранит семантику и привязку метрик к источникам. Фактические значения живут в источниках клиента; расчёты и анализ идут по канону metrics-вертикали.

### 🔹 `projects/` — временные инициативы unit

**Ракурс.** В ракурсе проектов хранятся проекты unit: временные инициативы с владельцем, горизонтом, рабочей повесткой и завершением. Проект отличается от unit тем, что он конечен.

Канон в разработке — уточняется по мере работы с клиентами.

Базово проект собирается как обычный node: management kit по потребности + служебные и рабочие папки проекта.

Проект под цель ссылается в своём `01_overview` на цель: вклад в неё; плановые метрики цели не дублирует — источник правды `goal.md`.

**Анатомия:**

```
projects/
├── README.md
└── {project-name}/
    ├── README.md
    ├── ... management kit
    ├── meetings/
    └── ... рабочие файлы проекта
```

**Размещение проектов:**

- Проект внутри одного unit → `{unit}/projects/{project-name}/`.
- Проект между несколькими дочерними units → `{parent}/projects/{project-name}/`.
- Кросс-функциональный проект без более узкого владельца → `01_company/projects/{project-name}/`.


### 🔹 `processes/` — повторяемая работа unit

**Ракурс.** В ракурсе процессов хранится повторяемая работа unit: регламенты, правила, операционные стандарты, устойчивые процедуры.

Канон в разработке — уточняется по мере работы с клиентами.

**Анатомия:**

```text
processes/
├── README.md
└── {process-name}/ или {process-name}.md
```

Базово разворачивается минимально: один файл на процесс; папка — когда процесс обрастает версиями, чек-листами, материалами.

**Граница:** process — повторяемая работа без заданного конца. Project — временная инициатива с завершением. Внедрение нового процесса может быть project; работающий процесс живёт в `processes/`.

### 🔹 `knowledge/` — база знаний unit

**Ракурс.** В ракурсе знаний хранится знание, на которое unit опирается в работе: устойчивые материалы, объяснения, инсайты, выжимки и связи между темами.

Канон в разработке — уточняется по мере работы с клиентами.

Ориентир развития — LLM Wiki: сырьё сохраняется отдельно, AI компилирует из него структурированную markdown-базу, поддерживает связи и периодически проверяет целостность. Детали паттерна — [llm-wiki.md](../../../knowledge/context/llm-wiki.md).

**Анатомия:**

```
knowledge/
├── README.md
└── ... страницы и разделы базы знаний
```

**Граница:**  регламенты — в `processes/`; Здесь опыт весь ценный опат и полезные знания
