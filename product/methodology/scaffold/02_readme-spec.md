# Scaffold README spec — канон карты папки

Канон `README.md` как карты папки: миссия, содержимое, маршруты чтения/записи и связанные контексты. Парные спеки — [02_file-spec.md](02_file-spec.md), [02_folder-spec.md](02_folder-spec.md).

## 🔵 Миссия README

README — карта папки. Главная функция — маршрутизация AI-агента: что лежит, куда идти, что читать дальше и, при необходимости, куда относить новую информацию. Всё, что не помогает агенту принять решение о навигации, — режется.

**README клиентского scaffold — воплощение канона, не первоисточник миссий.** Канон миссий — в [management-kit.md](management-kit.md), [management-aspect.md](management-aspect.md), [management-unit.md](management-unit.md) и [01_architecture.md § Типовые смысловые файлы](01_architecture.md). README адаптирует канонические миссии под локальный контекст в колонке «Миссия».

## 🔵 Где нужен README

**Обязателен:** узел (unit / company / project) — объект управления с kit и под-узлами. README несёт карту папки.

**По необходимости:** management aspect и развернувшийся kit-файл. Простой aspect (2–3 самоописывающих файла — например `01_strategic/` с `vision`/`goal`/`strategy`) README не получает: навигируют родитель и имена файлов. Ракурсы с неочевидной навигацией — `03_metrics/`, `projects/`, `processes/`, `knowledge/` — получают README из своего шаблона при каждом развороте.

**Обычно не нужен:** infrastructure folders (`_inbox/`, `_private/`, `meetings/`, `source/`, `extractors/`, `zz_archive/`). README появляется только если без него агент теряет навигацию.

**Рекомендован по ситуации:** client workspace folders. Если папка верхнеуровневая, важна для AI или имеет сложную внутреннюю структуру, лучше дать короткий README или описать её в README родительского узла.

Три семьи папок — [02_folder-spec § Три семьи папок scaffold](02_folder-spec.md).

**Иерархия:** локальный README перекрывает корневой. В корне держим только универсальное и не дублируем информацию.

**Приватная зона:** родительский README может назвать `_private/`, но не раскрывает её содержимое. Детальная карта при необходимости живёт внутри самой приватной папки.

**README vs 01_overview.md:**

| Артефакт | Описывает | Главная роль |
|---|---|---|
| `README.md` | Папку как **контейнер** | Маршрутизация AI-агента |
| `01_overview.md` | Узел **как объект** | Состояние узла и направление |

Карта связей папки живёт в README, не в `01_overview.md`.

## 🔵 Структура README

Все блоки обслуживают маршрутизацию — каждый отвечает на конкретный вопрос агента. Состав не фиксирован: у каждого блока — твёрдое правило появления в его секции ниже. Содержимое и маршруты описывают только реально созданные файлы и папки; всё, чего ещё нет, живёт в 🔧 Разворачивание. Пустых блоков-заготовок README не держит; исключения названы явно. Исключение: минимальный README infrastructure-папки несёт только H1 и аннотацию, без блоков — связи такой папки тривиальны (родитель), рост не нормируется.

```markdown
---
YAML
---

# {имя-папки} — {короткий ярлык с указанием роли}

{Аннотация под H1}

## Содержимое папки
- [file](path) — миссия. Читать: когда…

## Маршруты чтения
- триггер задачи → что читать

## Маршруты записи
- тип информации → куда писать

## Правила работы
- операционное правило обращения с содержимым папки

## Связанные контексты
— другие папки, домены или стабильные файлы, которые нужны для правильного чтения этой папки и перехода к смежной информации. Связь определяется смыслом и задачей, а не расположением в файловом дереве.
- {связанная папка, домен или стабильный файл} — что там и зачем переходить
  
## 🔧 Разворачивание
- Management kit, Management aspects, Infrastructure folders, [profile.md](profile.md) — по живой работе
```

### YAML
По канону [02_file-spec § YAML](02_file-spec.md).

### Аннотация под H1
**Рабочая миссия папки живёт здесь, не в H1.** H1 несёт короткий ярлык с указанием роли, аннотация — полную миссию. До 25–30 слов, без заголовка секции. Содержательно — [02_folder-spec § Миссия папки](02_folder-spec.md). Формат — [02_file-spec § Аннотация](02_file-spec.md).

```markdown
# marketing — функциональное направление

Папка маркетинга: фокус, текущая работа, решения, прогресс, метрики и связанные разрезы. README помогает агенту понять, что читать внутри папки.
```

### `## Содержимое папки`
Буллет-список содержимого папки. Каждая строка: `- file — миссия. Читать: когда`. Filename = ссылка (файл существует и навигируем). «Миссия» = одна фраза зачем существует файл; «Читать:» подписано явным полем. Миссии универсальных kit-файлов — в [management-kit.md](management-kit.md), файлов управленческих ракурсов — в [management-aspect.md](management-aspect.md), файлов отдельных units — в [management-unit.md](management-unit.md), типовых смысловых файлов — в [01_architecture.md § Типовые смысловые файлы](01_architecture.md).

Порядок строк: управленческое содержимое (kit-файлы, ракурсы, дочерние узлы) → служебные папки → рабочие папки клиента; внутри группы — по сортировке имён.

### `## Маршруты чтения`
Буллет-список «триггер задачи → что читать».

**Появляется:** у папки есть устойчивые типовые запросы агента.
**Не создаётся:** типовых запросов нет — отсутствие блока значит «навигации по содержимому достаточно».

Ссылки в маршрутах должны быть понятны вне path-контекста: `Marketing overview`, `Product architecture`, `ACME setup`, а не просто `overview`, `architecture`, `setup`.

### `## Маршруты записи`
Буллет-список «тип информации → куда писать».

**Появляется:** миссии файлов и имена не дают достаточно надёжного адреса записи — интенсивная запись от агентов, частые ошибки маршрутизации, близкие границы соседних файлов, переходы между соседними узлами.
**Не создаётся:** имена и миссии дают адрес — отсутствие блока значит «адресация простая», это сигнал, а не пробел.

Это блок адресации, а не фильтра качества. Он отвечает на вопрос «куда положить уже выбранный факт», а не «что считать достойным записи».

### `## Правила работы`
Локальные операционные правила папки: как обращаться с содержимым — read-only источники, правила именования, границы ответственности.

**Появляется:** у папки есть операционные правила, не выводимые из миссий файлов и маршрутов.
**Не создаётся:** таких правил нет — отсутствие блока значит «обычное обращение».

### `## Связанные контексты`
Другие папки, домены или стабильные файлы, которые нужны для правильного чтения этой папки и перехода к смежной информации. В обычных файлах связи живут inline; в README это обязательный отдельный блок.

**Присутствует всегда** (единственное исключение — минимальный README infrastructure-папки, § Структура README). Связей пока нет — блок сохраняется с короткой подсказкой-плейсхолдером: шаблон учит агента, куда смотреть. Выдуманные связи (нейрослоп) запрещены — лучше плейсхолдер, чем ложная связь.

Link label в связанных контекстах должен называть контекст перехода, если filename типовой.

### `## 🔧 Разворачивание`
Служебный блок роста папки: что может доразвернуться сверх текущего содержимого. Дефолт не повторяет — только то, чего ещё нет.

Формат строки: `- {файл, папка или категория} — {когда разворачивается}`. Механика разворачивания в блоке не описывается — за ней агент идёт в README папки шаблонов.

При разворачивании README обновляется атомарно: созданное добавляется в `## Содержимое папки` и, при наличии устойчивых сценариев, в маршруты чтения и записи; соответствующий элемент удаляется из `## 🔧 Разворачивание`. Категория остаётся, пока в ней есть что разворачивать.

**README узла — несёт всегда:** узел растёт по закону композиции (kit, aspects, дочерние узлы, infrastructure и client workspace folders), потенциал роста есть у любого узла.
**README aspect — по триггеру:** у ракурса есть типовые сценарии доразворачивания (`03_metrics/` → `source/` + `extractors/`; `projects/` → `{project-name}/`).
**Не используется:** infrastructure и client workspace folders — их рост scaffold не нормирует.

## 🔵 Доставка README агенту

**Проблема.** Агент читает README при заходе в папку, но не гарантированно в момент работы. У каждого агента свой нативный файл инструкций (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`) и своя механика загрузки: автозагрузка вложенных файлов и `@`-импорты в разных средах работают по-разному или не работают. Датированная матрица сред — [ai-system-files.md](../../../knowledge/context/ai-system-files.md).

**Инвариант (не зависит от среды):**
- `README.md` — единственный источник навигации узла: миссия, карта, связи.
- Рабочая инструкция агента — одна, в одном корневом файле. Остальные корневые файлы входа только указывают на неё — вторая правда запрещена.
- Базовый контракт доставки — самодостаточная текстовая инструкция в корневой инструкции агента: «перед работой с узлом прочитай его README.md; если у вложенной папки README нет — опирайся на README ближайшего родительского узла и имена файлов». Канон не полагается на vendor-механику.
- `01_company/operating-model.md` — always-read управленческого контекста: корневая рабочая инструкция предписывает читать его первым при управленческой работе; корневой README ведёт к нему маршрутом.
- По умолчанию узел получает только `README.md` — вложенные `AGENTS.md`/`CLAUDE.md` не требуются.

**Вход в корне scaffold (дефолт):**

| Файл | Содержание | Зачем |
|---|---|---|
| `README.md` | карта scaffold | source of truth навигации |
| `AGENTS.md` | базовая рабочая инструкция AI-агента | общий вход для AGENTS-aware агентов |
| `CLAUDE.md` | одна строка: «Рабочая инструкция — @AGENTS.md. Прочитай её перед работой» | в Claude Code `@` импортирует; в остальных средах читается как текстовая команда |

Клиент работает только в Claude → допустим один `CLAUDE.md` с рабочей инструкцией напрямую, без `AGENTS.md`; рабочая инструкция при этом та же — меняется только файл-носитель. Вход собирается под реальный набор агентов клиента; набор выясняется при развёртывании.

**Усиленная доставка — не канонизирована.** Кандидаты — вложенные `CLAUDE.md` по узлам, `@`-импорты, хуки с `additionalContext`, плагин: канон их не нормирует и не запрещает, при развёртывании допускаются эксперименты. Жёсткое ограничение: вложенный нативный файл — только указатель на локальный `README.md`, никаких локальных правил. Режим действует на время разработки продукта: канон зафиксирует способ доставки по полевой практике — [open-questions.md](open-questions.md).
