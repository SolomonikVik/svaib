# Product Decisions

## Кратко

Реестр крупных продуктовых решений Second Value AI Brain. Здесь — выборы, которые меняют траекторию продукта: закрывают альтернативы, задают границы архитектуры, delivery-модели и эволюции. Операционные выборы внутри спринта сюда не выносим.

**Работа с файлом:** decision log — append-only. Новое решение добавляется в конец. Изменение статуса (accepted → superseded) записывается обновлением, оригинал решения не стирается. Формат каждого решения: статус → решение → контекст → альтернативы → следствия.

**Апгрейд до папки `05_decisions/`** — когда файл перестанет умещаться (>500 строк или одно решение >100 строк), выносим каждое решение в отдельный файл, этот файл превращается в индекс.

## Связанные файлы

- [01_overview.md](01_overview.md) — что за продукт и зачем (принципы, границы)
- [architecture.md](architecture.md) — архитектурные следствия решений

## Формат записи

Каждое решение:

- **Статус** — текущее состояние (`accepted`, `proposed`, `superseded by …`) + дата
- **Решение** — что именно выбрали
- **Альтернативы** — что рассматривали и почему не берём

## 3. Путь Claude skills: канон vs legacy delivery

**Статус:** Accepted (2026-04-14).

### Решение

1. **Канон:** `.claude/skills/` — единственный правильный путь для Claude-specific навыков. Использовать в product, methodology/ontology, architecture, plugin и прочих канонических документах.
2. **Legacy-исключение:** для текущих живых клиентских воркспейсов на Google Drive допускается временное развёртывание в `claude/skills/` без точки.
3. **Явная пометка:** каждый документ, где появляется legacy-путь, должен помечать его как временное client-specific исключение, не как норму продукта.
4. **Не смешивать оба пути в одном клиентском воркспейсе.** Для конкретного клиента выбирается один путь.

### Контекст

7 апреля 2026 разделили два слоя: `CLAUDE.md` — инструкция агенту, `.claude/skills/` — исполняемые навыки Anthropic runtime. После этого часть канона обновлена, но scaffold-шаблон и клиентский delivery остались на старом пути `claude/skills/`.

Почему legacy-путь пока не убираем у клиентов:
- Живые клиентские воркспейсы уже развёрнуты без точки.
- Текущая delivery-операционка завязана на этот путь.
- Для Google Drive / Finder dot-папки менее удобны в ручной работе и поддержке.
- Прямо сейчас важнее не сломать живую поставку, чем дожать миграцию пути.

## 7. Composable management architecture для scaffold

**Статус:** accepted (2026-05-12, переразложено 2026-05-19).

**Решение.** Главная модель scaffold — composable management architecture. Три ортогональные сущности: **management unit** (за что отвечаешь), **management aspect** (через какую оптику смотришь), **management kit** (как ведёшь работу). Закон композиции — **node**. Распределение сущностей — владелец первый, наименьший общий предок второй.

**Раньше.** Аспект > Домен (`01_ceo / 02_strategy / 03_team / 04_company / 05_metrics` на корне). Разноуровневое лежало рядом, «стратегия маркетинга» и «target metrics CEO» путались.

**Альтернативы.** Аспект>Домен (не различает уровни), Домен>Аспект (требует дублей для кросс-функции). Обе отвергнуты в пользу composable matrix.

**Канон:** [methodology/scaffold/01_architecture.md](methodology/scaffold/01_architecture.md).

## 8. Граница ответственности: хранение и права доступа — на стороне клиента

**Статус:** accepted (2026-07-28).

### Решение

svaib не проектирует и не поддерживает файловую инфраструктуру и права доступа клиента. Клиенту даётся меню вариантов хранения (Google Drive, Git, Dropbox, решение его IT-службы) с плюсами и минусами каждого; выбор и поддержку контура клиент несёт сам.

### Контекст

Попытка выдать команде клиента доступ «только на чтение» вскрыла: Git даёт либо весь репозиторий, либо отдельный репозиторий с ручной синхронизацией; Google Drive неудобен по тонкой настройке прав. Настройка прав под каждого клиента превращает команду в инженерный сервис по доступам вместо продукта, который вовремя присылает хорошую повестку.

### Альтернативы

Выстраивать права и синхронизацию под каждого клиента силами svaib — отвергнуто: делает нас поставщиком клиентской инфраструктуры вместо продукта, который присылает хорошую повестку вовремя.

## 9. Канал доставки = атомарный универсальный скилл (send-telegram)

**Статус:** accepted (2026-07-30, Эрик).

### Решение

Канал доставки — самостоятельный скилл стандарта Claude Code: source в `product/plugin/skills/channels/<skill>/` (SKILL.md + `scripts/`, без repo-путей и внутренних имён svaib), установка сборщиком в `.claude/skills/<skill>/` — и клиентам, и в монорепо svaib (профиль svaib). Один канал = один скилл; имя — глагол+канал (`send-telegram`, будущие — `send-email`, `send-slack`). Получатель — конфиг `.env`, не текст скилла.

### Контекст

До 30.07 канал жил двумя слоями: канон `channels/telegram/` с внутренними текстами svaib плюс ручная invocable-обёртка `.claude/skills/send-telegram/` с repo-путями — непереносимо, двойной источник правды (дефекты 2–3 сборщика).

### Альтернативы

Общий скилл «доставка во все каналы» — отвергнут: тянет в контекст правила всех каналов сразу, не режется по составу поставки клиенту, ломает точную маршрутизацию по description.

## 13. Рабочую версию скилла не убираем, пока новая не станет лучше

**Статус:** accepted (2026-08-03).

### Решение

Рабочая (старая) версия скилла остаётся в дереве папок, пока новая не станет лучше старой — даже если старая версия сохранена в истории git, её всё равно дублируют в дереве, пока от неё не откажутся окончательно.

### Контекст

Повод — старая версия meeting-analysis (v1) была удалена из репозитория при разработке v2, который ещё не отлажен.

## 12. Встроенная память приложений (Claude memory) — не запрещаем

**Статус:** accepted (2026-08-03).

### Решение

Встроенную память приложений (Claude memory и аналоги) клиентам не запрещаем — оставляем как рабочий инструмент.

### Контекст

Мы не можем рекомендовать клиентам не пользоваться встроенными функциями Клода; персонализированная память усиливает вау-эффект клиента.

## 10. Google Drive — дефолтная рекомендация хранения, Dropbox исключён

**Статус:** accepted (2026-08-03).

### Решение

Google Drive закрепляется как основная рекомендация клиентам для хранения данных. Git остаётся запасным вариантом для сравнения. Dropbox исключён из рассмотрения — платный аналог функционала.

### Контекст

Уточняет решение №8 (клиент выбирает контур сам): из меню вариантов Dropbox снят как практический кандидат.

### Альтернативы

Dropbox — отклонён: аналогичная приватность доступна только платно, продукт менее популярен, несмотря на более прозрачный API.
