# docs — документация продукта: как пользователь с ним работает

Пользовательское описание продукта: что клиент и его люди получают и как этим пользуются. Пара к [../methodology/](../methodology/): методология отвечает «как устроено», docs — «как пользователь с этим работает». Зона технического владельца продукта; методология — зона Виктора.

Формат — реестр описаний, почти инструкция (не юзер-стори и не архитектура): функционал по частям продукта пользовательским языком — MCP и его ручки, скиллы, SaaS-инфраструктура, управленческое пространство. Две задачи: ответить на любой вопрос клиента про продукт и служить основой для инструкций. Критерий полноты пары «методология + docs»: по ним агент может воссоздать продукт и породить спецификации.

## Правило для агентов

Пользовательское описание части продукта кладётся сюда — не в корень `product/` и не в методологию. Разграничение: «как устроено внутри» → [../methodology/](../methodology/); технические контракты и spec → `dev/`; целевой образ → [../vision/](../vision/).

Пошаговые инструкции настройки и работы пишутся в [instructions/](instructions/README.md). Это их единственный источник; playbook внедрения и скиллы используют его по правилам поставки. Описание возможности и инструкция её настройки — разные документы, между ними ставится ссылка.
