# Повестка к встрече

Собирает повестку к **ещё не состоявшейся** встрече: рамка объекта управления → задачи и прогресс → на чём сфокусироваться → что должно быть решено. Процесс ведёт `scripts/agenda_run.py`; твоя роль — исполнять шаги, которые называет драйвер, и показывать человеку то, что отрендерил код.

## Iron Law

**Числа не сочиняются и не считаются.** Значения метрик приходят из вертикали metrics через код и вливаются в повестку кодом. В своих формулировках цифр не пиши вовсе — только токены `{metric:<id>}` и `{count:<флаг>}`, которые подставит рендер. Токен ставится лишь на метрику со сверенным значением: скрытое статусом число рендер не раскроет, и токен на нём валидатор режет.

**Ничего не уходит человеку в обход драйвера.** Доставка — только команда `deliver`; канал напрямую не зови.

Пункт без опоры не проходит валидатор: нет источника с датой — нет пункта.

## Главное разграничение — фаза времени

ДО встречи — это сюда. ПОСЛЕ встречи (транскрипт, протокол, обновление базы) — `meeting-analysis`. Закрытие прошедшей недели — `weekly-planning`. Слово «планёрка» само по себе фазу не задаёт: смотри, готовятся к встрече или разбирают её.

## Вызов драйвера

```
python3 <каталог скилла>/scripts/agenda_run.py start --base <корень базы> --phrase "<фраза человека>"
python3 <каталог скилла>/scripts/agenda_run.py next
```

На Windows интерпретатор зовётся `python`, не `python3`.

Дальше процесс ведёт `next`: он называет шаг, скрипт, путь артефакта и команду приёма. Порядок шагов по памяти воспроизводить не из чего — источник правды машинный, и шаг вне очереди драйвер не примет.

- Ненулевой код возврата — названный блокер: маркер не встанет, пока причина не устранена.
- Пересборка любого артефакта снимает маркеры всех шагов ниже, поэтому после починки повестка показывается заново.
- Run привязан к машине (state-каталог вне базы). В облачных средах правило «одна повестка — одна сессия».

## Шаги

| # | Шаг | Что делаешь ты | Команда |
|---|---|---|---|
| 1 | `object_resolved` | `resolve_object.py map` → выбери объект по карте. Объект не назван — `rank` даёт кандидатов | `resolve --object … --kind … --date … --type …` |
| 2 | `sources_collected` | ничего: чек-лист и индекс встреч собирает драйвер | `collect` |
| 3 | `metrics_resolved` | ничего: перечень метрик получает драйвер | `metrics` |
| 4–5 | `drafted` | прогони каталог проверок (`references/agenda-contract.md`), напиши черновик по `prompts/compose-agenda.md`, влей машинные поля через `assemble_agenda.py` | `submit drafted --artifact …` |
| 6 | `validated` | ничего: форму проверяет драйвер | `validate` |
| 7 | `rendered` | ничего: текст собирает драйвер | `render`, затем **покажи человеку** и `ack` |
| 8 | `delivered` | ничего | `deliver` |

Единственный артефакт, который подаёшь ты, — черновик повестки. Всё детерминированное драйвер делает сам: собирает источники, получает метрики, валидирует, рендерит. Это не формальность — иначе достаточно подать правдоподобный на вид файл, и повестка уедет, ни разу не заглянув в базу.

Объект ты выбираешь по карте, но проверяет его код: места, которого в базе нет, драйвер не примет — карта строится обходом дерева, зашитых путей в скилле нет.

Провал валидации маркера не ставит: чинится черновик и подаётся `submit drafted` заново, что снимает всё ниже по цепочке. Счётчика попыток нет — **если чинить приходится третий раз, скажи об этом человеку, а не молчи.**

**Наличие метрик у кандидата — признак готовности данных, не критерий выбора объекта:** иначе выберешь не ближайшую встречу, а самую измеряемую.

## Чего не делать

Здесь только то, что **кодом не держится**. Остальное режет валидатор, и повторять его правила прозой незачем: пропавшую метрику, несверённое число, пункт без источника и перепутанный порядок блоков он поймает сам и скажет, что чинить.

- **Не читай транскрипты.** Никогда. Протоколы — по бюджету из `references/agenda-contract.md`.
- **Не пиши в базу.** У этого скилла нет write-path вовсе: повестка уходит сообщением. Нужно что-то внести (например строку `**Зона:**` в профиль) — отдай человеку готовую строку с указанием файла, внесёт он.
- **Не утверждай, что клиент чего-то не измеряет.** Статус говорит об источнике, а не о работе руководителя: «значений в источнике нет» — можно, «метрика не замеряется» — нельзя, в любом перифразе. Один раз продукт уже отчитался, что клиент не измеряет то, что тот измерял полгода.

Scaffold у каждого клиента свой: ракурс бывает файлом и папкой, встречи — централизованными и распределёнными, цель — файл внутри ракурса, а не узел. Поэтому карту мест строит код — выбирать по зашитым путям не из чего.

## Что показать человеку

**Покажи отрендеренный текст целиком до вызова `deliver`.** Что показ был, код проверить не может — он видит только маркер. Если человек торопит, доставка «сразу» возможна командой `ack --skip-preview`, но это его отдельное решение, а не твоё сокращение пути.

Вопрос о зоне ответственности (когда у человека в профиле нет строки `**Зона:**`) задаётся один раз на сборку — коротко, вместе с готовой строкой для внесения.

## Границы MVP

- **Значений метрик сегодня нет.** Вызываемого интерфейса вертикали metrics не существует, поэтому все метрики идут со статусом «сверка не выполнялась», а блок метрик собирается без чисел. Это честное состояние, а не поломка: перечень метрик и сигнал «измерить нечем» работают уже сейчас.
- **Повестка нигде не сохраняется** — место артефакта в базе не решено. Следующая повестка на предыдущую опереться не сможет.
- **Календарного триггера нет** — только по фразе человека.
- **Адресат доставки** — владелец настроенного канала, то есть руководитель, для которого развёрнута база. Отправка участнику встречи не поддерживается.
