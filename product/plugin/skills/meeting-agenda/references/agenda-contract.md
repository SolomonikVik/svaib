# Контракт повестки — то, чего нет в схеме

Справка узла сборки: каталог аналитических проверок, профили объекта встречи и бюджеты чтения. **Норматив каркаса живёт не здесь** — форму задаёт `schema/agenda.schema.json`, порядок блоков задаёт константа `BLOCK_ORDER` в `scripts/render_agenda.py`. Этот файл описывает то, чего в схеме нет, и второй нормой формы не является.

## Профили объекта встречи

Каркас один, меняется объект — то, вокруг чего собираются все блоки.

| Профиль | Объект | Разрез целей и метрик | Разрез задач |
|---|---|---|---|
| Регулярка по цели | одна цель / OKR-трек | цель + её метрики по ссылкам из файла цели | инициативы под целью |
| Регулярка направления | направление (узел) | цели, на которые направление работает | задачи направления |
| 1-on-1 | человек | цели его зоны ответственности | его задачи + его профиль |
| Старт недели | компания | все цели периода | по направлениям |

**Перечень метрик строится по-разному и это нормативно:** объект-узел — метрики всех `*-metrics.md` ракурса `metrics/` узла (для направления плюс дочерние узлы); объект-цель — **только по ссылкам из файла цели** на metrics-файлы с якорем на каноническое имя метрики, сопоставление по совпадению имён текстом запрещено; объект-человек — по зоне ответственности из его профиля (строка `**Зона:**`), а при её отсутствии зона спрашивается у человека и готовая строка отдаётся ему для внесения.

## Каталог аналитических проверок

Из каталога выбираются **≤3 самых острых** сигнала. Каждый — с опорой на факт, без «возможно стоит подумать». Пункт без опоры не пишется.

`check_id` попадает в `focus[].check_id`; проверка, которой не хватило данных, попадает в `flags.checks_skipped[]` с причиной — **молча пропустить проверку нельзя**, это деградация ядра ценности.

| `check_id` | Что сравнивает | Формулировка сигнала | Бюджет: на чём исполнима |
|---|---|---|---|
| `tasks-goals` | активные задачи ↔ цели периода | «N задач не привязаны ни к одной цели» / «у цели X нет ни одной задачи с владельцем» | файлы объекта |
| `goal-metric` | цели ↔ перечень метрик | «цель X нечем измерить — метрики нет» | файлы объекта; **работает и без значений** |
| `metric-agenda` | метрики с отклонением ↔ темы встреч | «метрика X красная три недели и ни разу не обсуждалась» | требует значений; без них → `checks_skipped` |
| `owner-due` | задачи | «N задач без владельца или без срока» | файлы объекта |
| `repeat-slip` | договорённости прошлых встреч | «обязательство X сорвано второй раз — вопрос не в сроке» | протоколы серии |
| `attention-skew` | частота тем во встречах | «обсуждаете следствие, причина не появлялась ни разу» | **кросс-серийный индекс** |
| `blind-spot` | направления ↔ встречи за период | «направление X не появлялось на встречах пять недель» | **кросс-серийный индекс** |
| `figure-mismatch` | одна метрика в разных источниках | «в одном источнике одно значение, в другом другое — где-то стадия не переведена» | требует значений; без них → `checks_skipped` |
| `decision-conflict` | новое обсуждение ↔ `05_decisions.md` | «это отменяет решение от {дата}, оно принималось из-за Y» | файлы объекта + решения |
| `people` | профили ↔ сигналы из встреч | «второй месяц перегруз у X, его задачи на критическом пути» | профиль + протоколы серии |

**Отсутствие данных само может быть сигналом.** `goal-metric` даёт содержательный пункт именно тогда, когда метрик нет: цель, которую нечем измерить, — управленческая проблема, а не пустая ячейка. Так же читается метрика со статусом «сверка не выполнялась» или «нет значения»: слепая метрика может оказаться самым острым пунктом повестки.

**Что проверками не является:** тема, не связанная ни с целью, ни с метрикой, ни с обязательством. Такие в повестку не попадают вовсе.

## Бюджеты чтения

| Что | Бюджет |
|---|---|
| Транскрипты встреч | **не читаются никогда** |
| Последний протокол серии | целиком |
| Протоколы серии | выжимки за последние 8 недель, не более 10 файлов |
| Все прочие `meetings/` базы | **только шапка** — до первого `##` либо первые 15 строк; из неё дата, объект, тема |
| Файлы объекта (цели, задачи, решения, метрики, профиль) | целиком |

Кросс-серийный индекс (строка «объект + дата + тема» на каждый протокол базы) существует ровно потому, что бюджет серии обнулил бы `attention-skew` и `blind-spot` молча. Индекс строится по шапкам; у протоколов без строки `**Объект:**` объект берётся из имени файла, и такие строки помечены — на них кросс-серийные выводы слабее, и это видно, а не спрятано.

## Правила формы, за которые отвечает не схема

- Повестка **всегда открывается рамкой объекта управления** — даже когда встреча чисто операционная и «все всё помнят». Разговор начинается с рамки, а не с домашки и не с цифр: всё ниже читается как ответ на вопрос «двигает ли это к цели».
- Рамка — **объекта встречи, не компании**. Цель и метрики берутся того объекта, вокруг которого собрана встреча.
- Красное и развернувшееся — вверху таблицы, зелёное — одной строкой (легальная свёртка).
- Под таблицей метрик — одна строка вывода: что требует решения на встрече, а что просто наблюдаем.
- Финал — не список тем, а то, **что должно быть решено**.
