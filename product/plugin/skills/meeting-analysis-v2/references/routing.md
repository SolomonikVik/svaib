# Маршрутизация

Справочник узлов пайплайна. Отвечает на вопрос «куда»: какие контуры затронула встреча, что читать в контуре, какой файл — дом сущности, что домом не является.

## Контуры

Контур — unit базы любого класса: у него свои файлы и свои миссии. Тип встречи не меняет процесс — меняются контуры и их файлы.

| Класс контура | Что это | Уровень |
|---|---|---|
| узел-направление | папка направления (`{node}/`) | `node` |
| группировка | папка-родитель нескольких узлов (`{parent}/`) — обычная единица со своими файлами управленческой панели на её уровне | `grouping` |
| компания | `01_company/` | `company` |
| личный контур руководителя | `00_ceo/` | `ceo` |
| карточка проекта | `{node}/projects/{project}/` | `node` |
| досье контрагента | папка клиента, партнёра, подрядчика (`01_overview.md`, `company.md`, `people.md`, `meetings/`…) | `node` |

Досье контрагента — такой же unit, как узел-направление.

## Что читать в затронутом контуре

- **Встреча внутри одного узла** (1-on-1, планёрка отдела): файлы `{node}/` + `01_company/02_team/{person}.md` каждого участника.
- **Кросс-функциональная встреча дочерних узлов одной группировки:** файлы группировки + файлы КАЖДОГО затронутого дочернего узла + профили участников. Обновляются и дочерние узлы, и те файлы уровня группировки, что у неё развёрнуты, — если кросс-функциональный контекст изменил общую картину.
- **Встреча верхушки разных направлений** (стратсессия руководителей): файлы КАЖДОГО затронутого направления + профили участников + `01_company/05_decisions.md`.
- **Встреча с контрагентом:** файлы досье, которые существуют.
- **Всегда, если развёрнуто:** `01_company/operating-model.md`; README целевых папок; `01_company/glossary.md` и `01_company/speech-aliases.md`; `00_ceo/04_decisions.md` — когда в выжимке есть личное решение или принцип руководителя как человека, не бизнес-решение; `01_company/05_decisions.md` — при кросс-функциональной встрече или стратсессии.
- **Живые карточки проектов** затронутых узлов: их `01_overview.md` + `02_active.md`.

Kit собирается по потребности: отсутствующего файла нет — не читаем и не создаём «для полноты». Профиля участника нет (внешний человек) — пропускаем, не создаём. `04_progress.md`/`05_decisions.md` бывают на десятки тысяч строк — читаем последние ~10–15 записей (свежее сверху, начало файла), не весь файл.

**Живая карточка проекта** = лежит вне `zz_archive/` и её `02_active.md` непуст.

## LCA: какой контур затронут

- **Правило наименьшей общей родительской папки применяется к СОДЕРЖАНИЮ встречи**, а не к формальной принадлежности участников: руководитель, обсуждающий чужую зону, LCA не расширяет.
- **`01_company/operating-model.md` — канонический закон размещения сущностей.** Задаёт маршрутизацию иначе, чем LCA (например, отдельный слой инициатив и карточек) → приоритет за operating-model; LCA — дефолт на случай его отсутствия.
- **README целевой папки — локальные правила маршрутизации узла** (секция «Маршруты записи»): при конфликте с общей таблицей домов приоритет у узла.
- Место протокола встречи этому правилу не подчиняется: его выбирает узел `locate-context` по карте встреч базы (каталоги `meetings/` + секции их README).

## Миссии файлов

Файл-центричный проход идёт по этим миссиям: по каждому существующему файлу затронутого контура задаётся вопрос «нужно ли обновить его с учётом новой информации из выжимки?».

### Класс «узел scaffold»

| Файл | Миссия | Тест-вопрос |
|---|---|---|
| `01_overview.md` | ЧТО это направление и КУДА идёт | Новое о целях, KPI, границах, команде, ключевых проектах? Тест: будет актуально через квартал? |
| `02_active.md` | ЧТО АКТУАЛЬНО сейчас, НЕ архив | Гейт как у overview/decisions: попадает только то, что в работе **прямо сейчас** — тест не «есть `owner`», а «руководитель вернётся к этому до следующей встречи». Новая задача (`owner` есть или нет — не критерий; без него помечай «owner не назначен»), открытый вопрос, риск, которые проходят этот тест? Повестку следующей встречи НЕ вносить (производный нарратив координатора) — только дата/статус следующей встречи, если прозвучали. Не проходит и не срочно → `03_backlog.md`, не сюда. Сначала сопоставь новое с существующим — связанные пункты объединяй, не дублируй. **Симметрично удаляй уже неактуальное:** вопрос этой встречи решён → убрать (решение → decisions); повестка этой встречи обработана → убрать; риск снят/реализовался → убрать; задача выполнена → `[x]` и сразу удалить (хроника — в `04_progress`, отдельной секции-накопителя не создавать) |
| `03_backlog.md` | БУДУЩАЯ работа: отложенное | Есть ли идея, гипотеза или задача, важная, но не проходит тест active (руководитель НЕ вернётся к этому до следующей встречи)? Не дублируй то, что уже ушло в `02_active` |
| `04_progress.md` | КАК ДВИГАЛИСЬ | Запись — ТОЛЬКО при значимом сдвиге узла: решение, веха, разворот, завершение крупного, важная обратная связь. Операционная текучка планёрки хроникой не является — значимого сдвига нет → запись НЕ создаётся (пересказ встречи живёт в выжимке/протоколе). Сдвиг есть → запись по [formats.md](formats.md) — **в начало файла**, свежее сверху |
| `{node}/05_decisions.md` | ПОЧЕМУ так решили (уровень узла) — если контур сущности конкретный узел, не группировка и не компания | Стратегические решения внутри единицы? Тест: через 3 мес спросят «почему так?» |
| `{parent}/05_decisions.md` | ПОЧЕМУ так решили (уровень группировки) | Только для кросс-функциональных встреч. Решения, охватывающие несколько дочерних единиц группировки, но не меняющие курс компании? Тест: затрагивает 2+ дочерних узла группировки, но не vision/goal/strategy компании |
| `01_company/05_decisions.md` | ПОЧЕМУ так решили (курс компании) | Решения уровня всей компании (pivot, стратегия, структура, принципы найма)? Только при стратсессиях или кросс-функциональных встречах |
| `00_ceo/04_decisions.md` | ПОЧЕМУ так решил CEO (личный уровень) | Личные решения руководителя как человека в роли (принципы работы, границы, как принимает решения)? Тест: про CEO как личность, не про бизнес-решение |
| `01_company/02_team/{person}.md` | КТО этот человек | Наблюдения о стиле, сильных сторонах, зонах развития? Коучинг? Тест: про ЧЕЛОВЕКА или про НАПРАВЛЕНИЕ? |
| `01_company/glossary.md` (или `speech-aliases.md`, если развёрнут отдельно) | КАК ЧИТАТЬ транскрипты | Новые имена, варианты произношения, ошибки транскрибатора, незнакомые термины/жаргон? Поправил пользователь имя или термин при вычитке — кандидат сюда. Есть `speech-aliases.md` → имена и ASR-ошибки туда, термины остаются в `glossary.md` |

### Класс «досье контрагента»

**Ориентируйся на фактический формат конкретного досье** — README узла и файлы, которые в нём реально есть. Таблица ниже — канонический дефолт шаблона scaffold, а не жёсткая адресация: базы бывают расширены под клиента. Миссию несёт файл, а не имя: в этом досье она у файла с другим именем или разложена иначе — пиши туда, где она живёт фактически. Подходящего файла нет вовсе — не заводи новый молча, оформи `home_question`.

**Создание нового досье (контрагент без узла в базе).** Каркас — по канону разворачивания, не «все файлы сразу»: ОБЯЗАТЕЛЬНО `README.md` — карта узла (кто контрагент, миссии файлов, маршруты — по образцу README существующих досье базы) + только те kit-файлы, для которых есть содержимое встречи (обычно `01_overview.md`, `people.md`/`company.md`). `04_progress.md`, `03_backlog.md`, `05_decisions.md` при создании НЕ разворачиваются без содержимого своей миссии; первая встреча-знакомство — не хроника сдвигов узла, запись в `04_progress` не создаётся (kit по потребности: хроника — со второй встречи).

| Файл (дефолт канона) | Миссия | Тест-вопрос |
|---|---|---|
| `people.md` (разросся — `people-{имя}.md` на человека) | КТО эти люди | Узнали новое о человеке контрагента (роль, влияние, позиция, стиль коммуникации, предпочтения, боли, принципы, язык)? Тест устойчивости: останется верным через год? Событие-иллюстрация уже записанного — не добавлять (мысль есть, эпизод протухнет); наблюдение контрагента о других людях — не его принцип (если за ним его боль → «Боли», иначе остаётся в выжимке) |
| `company.md` | ГДЕ он работает | Новые факты о бизнесе (цифры, люди, оргструктура, стратегия компании)? Тест: останется при смене руководителя? |
| `01_overview.md` | ЧТО мы делаем | Новые запросы на решения? Изменилась модель работы, метрики успеха, программа? |
| `05_decisions.md` | ПОЧЕМУ так решили | Были стратегические решения? Тест: через 3 мес спросят «почему так?» — это ответ? Новое решение отменяет прежнее → старую запись не переписывать, пометить `Статус: Superseded` (формат — [formats.md](formats.md)) |
| `02_active.md` | ЧТО АКТУАЛЬНО сейчас, НЕ архив | Гейт: попадает только то, что в работе прямо сейчас — тест «пользователь или контрагент вернётся к этому до следующей встречи». Сначала сопоставь новое с существующим — связанные пункты объединяй, не дублируй; задача, отменённая решением этой встречи, не остаётся и не возвращается. Новые задачи (по `owner`)? Открытые вопросы? Риски? Повестку следующей встречи НЕ вносить — только дата/статус следующей встречи, если прозвучали. **Симметрично удаляй неактуальное:** вопрос решён → убрать (решение → decisions); устаревшая повестка → убрать; задача выполнена → `[x]` и сразу удалить |
| `03_backlog.md` | БУДУЩАЯ работа | Идея, гипотеза, ожидание или запрос контрагента — важные, но не проходят тест active? Не дублируй ушедшее в `02_active` |
| `delivery-status.md` | ЧТО РАЗВЁРНУТО у клиента | Изменился статус блока плана доставки (развёрнуто, принято, оплачено, граница блока)? |
| `setup.md` | КАК настроено | Изменилась конфигурация (инструмент, структура, настройки)? |
| `04_progress.md` | КАК двигались | Запись — ТОЛЬКО при значимом сдвиге по контрагенту (веха, решение, сдвиг отношений/доставки); текучка без сдвига → записи нет. Сдвиг есть → 2–4 строки (что сделано, ключевой сдвиг, обратная связь) — **в начало файла**, свежее сверху |

## Таблица домов (тип × уровень → canonical)

| Тип | Уровень / условие | Canonical-дом |
|---|---|---|
| task / risk / question — предмет живой инициативы с карточкой (`card_home` Фазы A) | узел инициативы | `{node}/projects/{project}/02_active.md` — пометку `card_home` не пересматривай из узкого контекста; несогласие оформляй `home_question` |
| decision | компания | `01_company/05_decisions.md` |
| decision | узел / группировка | `{node}/05_decisions.md` / `{parent}/05_decisions.md` |
| decision | личное решение CEO | `00_ceo/04_decisions.md` |
| task — в работе сейчас | узел контура содержания задачи | `{node}/02_active.md` |
| task — не сейчас | узел | `{node}/03_backlog.md` |
| risk / question | узел, чью зону задевает — если предмет риска/вопроса не работа другого контура; предмет — работа другого контура (его инициатива, его функция) → canonical в контур ответственности, задетому узлу reference-проекция | `{node}/02_active.md` |
| fact устойчивый | узел | `{node}/01_overview.md` (или metrics-файл клиента) |
| observation о человеке | — | `01_company/02_team/{person}.md` |
| term / ASR | — | `glossary.md` / `speech-aliases.md` |
| хроника встречи — только при значимом сдвиге контура | каждый затронутый контур со сдвигом | `{node}/04_progress.md` — вне единственности |
| устойчивое о человеке-контрагенте (принципы, язык, боли, предпочтения) | досье | файл людей этого досье по его фактическому формату; дефолт канона — `{досье}/people.md` (разросся → `{досье}/people-{имя}.md`) |
| факт о бизнесе контрагента (цифры, люди, оргструктура, стратегия) | досье | `{досье}/company.md` |
| запрос, модель работы, метрики успеха, программа | досье | `{досье}/01_overview.md` |
| decision | досье | `{досье}/05_decisions.md` |
| task / risk / question | досье | `{досье}/02_active.md`, не сейчас → `{досье}/03_backlog.md` |
| статус блока доставки, приёмки, оплаты | досье | `{досье}/delivery-status.md` |
| конфигурация у клиента (инструмент, структура, настройка) | досье | `{досье}/setup.md` |

Решение (`decision`) НЕ получает canonical-дом в `02_active.md`: работа, которую решение порождает, — это либо отдельная task-сущность ростера со своим домом, либо `consequence` с owner.

Протокол встречи не маршрутизируется: это не сущность ростера и не дельта — файл протокола публикует spine из принятой выжимки в каталог, который определил узел `locate-context`.

## Card-routing: юнит-файл или карточка проекта

Если предмет задачи/риска/вопроса — инициатива с живой карточкой, дом дельты — `{node}/projects/{project}/02_active.md`, дельта помечается `card_home: {path}` с обоснованием одной строкой. Упоминание ≠ предмет; получатель/бенефициар ≠ предмет: «отчёт для узла X» не делает карточку X домом.

1. **Кандидаты — карточки ВСЕХ затронутых узлов.** Сопоставляй предмет сущности со списком живых карточек (path + строка «о чём»), а не только с карточками узла предполагаемого владельца; полностью читай только карточки-кандидаты. Отверг карточку одного узла → обязан пройти остальной список. Узел карточки-кандидата по построению затронут: сущность о предмете инициативы делает его затронутым.
2. **Owner-сигнал не выбирает дом.** «Это моя инициатива», «беру себе», «владелец цифры — я» выражается полем `owner` и reference-проекцией в юнит-`02_active` владельца — canonical-дом определяет ПРЕДМЕТ. Функциональный срез (продажи, маркетинг, найм) вокруг инициативы с живой карточкой — это работа ПО инициативе → canonical в карточку.
3. **Между карточками: меняемое > используемое.** Canonical — в карточку той инициативы, чьё состояние работа непосредственно меняет или продвигает; инициатива-канал или инструмент, который работа лишь использует, домом не становится. Пример: «продать продукт через дилеров, 8 сделок» продвигает запуск продукта (дилерская программа — используемый канал) → карточка продукта; «переработать дилерскую матрицу комиссий» меняет саму программу → её карточка. Фоллбэки: карточка меняемой инициативы мертва или архивна → юнит-файл узла (не чужая живая карточка); работа равносильно меняет две инициативы → canonical в одну + `home_question`.
4. Правила сужают выбор, но не отменяют дубль-механизм: осталось сомнение между юнит-файлом и карточкой (или двумя карточками) — создай ОБЕ дельты с одним `entity_id`, выбор оформит канонизация.

При маршрутизации в карточку владельцу юнита остаётся reference-проекция в юнит-`02_active.md` (≤240 символов, ссылка на карточку), чтобы задача не исчезла из поля зрения узла. `card_home` ставит только Фаза A — с обоснованием одной строкой.

## Общие правила раскладки

**Маршрут по содержанию, не по роли.** Canonical-контур сущности определяется её содержанием и контуром ответственности за неё, а НЕ должностью или ролью человека. Двойная роль владельца (и.о. руководителя одного контура + лид другого) маршрут не решает: задача про продукт остаётся в продуктовом узле, даже если её owner формально числится и в другом контуре. Роль — вспомогательный сигнал, содержание — решающий.

**Ответственность, не объект.** Canonical-дом сущности — контур, который владеет работой по ней (исполняет, решает, отвечает за следующий шаг), а НЕ узел, О КОТОРОМ она. Компенсации, грейды, вилки, обучение сотрудников любого узла — работа HR-контура, если он есть в базе: canonical туда, узлу-объекту — reference-проекция (строка-ссылка на canonical, ≤240 символов). Нет контура ответственности в базе → действуют обычные правила выбора дома по предмету/зоне. Это распространяется и на риски/вопросы О такой работе: риск «не поднимем вилку — потеряем людей поддержки» — риск HR-работы, canonical в HR, поддержке — проекция. Тест: «чья это работа?», не «про кого это?».

**Один аспект — одно место.** Одно событие может обновить несколько файлов, если затрагивает разные аспекты. «Решили сменить лидера направления» → `01_overview` (структура) + `01_company/02_team/{person}.md` (роль) + `02_active` (задачи по передаче). «Перешёл на новый инструмент» → `setup` (конфигурация) + файл людей досье (`people.md`, опыт человека). Разные файлы отвечают на разные вопросы — это не дублирование.

**Страховка.** Не можешь однозначно маршрутизировать — оставь в выжимке (`summary_only`). Действует только на Гейте A, при назначении disposition; после Гейта A сомнение оформляется doubtful-дельтой с `doubt_reason`, а не тихим отказом от записи. Лучше не разложить, чем разложить неправильно.

**Мимолётное упоминание чужого контура** без новой информации о нём и без его действия контур не затрагивает — сущность остаётся `summary_only`.

**Покрытие узла ≠ canonical.** Узел покрыт, если у него есть хоть одна recommended-дельта — любая, включая дельту хроники или глоссария (они вне единственности, поле `role` у них не заполняется). Хроника и глоссарий домом сущности не бывают: назначать такой дельте `role: canonical` ради покрытия узла — ошибка, покрытие она даёт и без роли. Покрыть узел нечем — снимай его явно: запись в `dropped_nodes` с причиной, его дельты → doubtful.

## Антипаттерны

### Класс «узел scaffold»

- Проблемы и задачи в overview → `02_active`
- Хроника в overview → `04_progress`
- Решение без why и альтернатив → не в decisions; дособери контекст или оставь в выжимке
- Коучинг в файлах направления → `01_company/02_team/{person}.md`
- Операционные выборы в decisions → остаются в выжимке
- Company-wide решения в `{node}/05_decisions.md` → `01_company/05_decisions.md`
- Личные решения CEO (принципы, стиль) в `01_company/05_decisions.md` → `00_ceo/04_decisions.md`

### Класс «досье контрагента»

- Конфигурация (инструмент, настройка) в файле людей (`people.md`) → `setup`
- Прогресс («разобрал 50 файлов») в файле людей или `company` → `04_progress` (в протокол попадёт автоматически через выжимку)
- Задачи в `01_overview` → `02_active`
- Решения без контекста в `01_overview` → `05_decisions` (нужны why + альтернативы)
- Конкретные события и даты в «Кратко» → `04_progress`
- Нет данных — не додумывать: факт не подтверждён источником (выжимка, явная правка пользователя) → вопрос пользователю
- Операционный шум в справочные файлы: `company.md` = ключевые люди и их роли, НЕ «сотрудник попросил фидбэк». Тест: поможет ли это при подготовке к следующей встрече через месяц? Нет → не записывать
- Переписывание принятого решения задним числом → только `Superseded`-пометка статуса, тело старой записи не редактировать
- Статус доставки или оплаты блока в `01_overview`/`02_active` → `delivery-status.md`

## Doubt-политика

- **В doubtful, `doubt_reason: dispute`:** спор о САМОМ контуре (нужен ли он этой встрече); спор о факте, формулировке или атрибуции сущности; дом-антипаттерн (решение в active, задача в decisions, хроника вне progress). Такая дельта в recommended не остаётся никогда.
- **В doubtful, `doubt_reason: unresolved`:** нарушения инвариантов, не починенные за отведённые попытки.
- **НЕ doubtful:** выбор между легитимными домами ОДНОГО типа внутри согласованного контура (юнит-`02_active` vs карточка проекта; active vs backlog по срочности). Дельта остаётся `canonical` в recommended с полем `home_question` — пользователь видит вопрос в сводке и решает без потери дельты.

## Даты-источники

Изменчивые данные (цифры, статусы, решения, люди) получают дату в строке `(YYYY-MM-DD)`. Стабильные факты остаются без дат.

## Правки пользователя при вычитке выжимки

Правки имён, терминов и ошибок транскрибатора, сделанные пользователем при вычитке, — кандидаты на обновление базы:

- **Узлы scaffold:** термины → `01_company/glossary.md`; имена и ошибки распознавания → `01_company/speech-aliases.md`, если он развёрнут, иначе туда же, в `glossary.md`.
- **Досье контрагента:** устойчивые термины и язык контрагента, имена людей и роли → файл людей досье по его фактическому формату (дефолт канона — `people.md`); оргструктура и факты о бизнесе → `company.md`.
- **Разовые ошибки распознавания** без устойчивой ценности остаются правкой выжимки и в базу не пишутся.
