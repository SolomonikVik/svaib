# Узел `build-deltas` — Фаза A

По принятой выжимке ты делаешь файл-центричный проход по файлам затронутых контуров и собираешь пакет дельт — предлагаемых обновлений базы.

**Твоя цель — покрытие, не дедуп.** Покрытие и назначение единственного дома разведены по фазам: ты собираешь дельты на максимум полноты (дубли разрешены), единственный canonical-дом каждой сущности назначает следующая фаза — канонизация. Не смешивай цели: здесь не дедуплицируй.

Справочники: миссии файлов, таблица домов, card-routing, антипаттерны, doubt-политика — [routing.md](../references/routing.md); форматы записей — [formats.md](../references/formats.md).

Вход `corrections` (правки пользователя при подтверждении выжимки), если подан, — обязательная часть принятой выжимки: ростер и дельты строишь по выжимке **с учётом правок**; правка пользователя — валидная опора `source_evidence`. Потерять corrections нельзя.

## Iron Law обновления

После обновления состояние проекта в файлах актуально. Выжимка остаётся как полная запись встречи. Не всё из выжимки должно попасть в файлы — это нормально.

**Выжимка щедрая, файлы строгие.** Выжимка сохраняет всё. Файлы базы — только то, что имеет устойчивую ценность: стратегические решения, факты о бизнесе, задачи с `owner`, изменения в целях и структуре. Операционная мелочь, разовые реплики, бытовые просьбы остаются в выжимке и в файлы не попадают.

## Гейт A: ростер и контуры

Выполни ПЕРЕД проходом по файлам, письменно. Это служебный артефакт — пользователю он не показывается.

1. **Ростер сущностей.** Пронумеруй сущности выжимки `E01, E02…` по секциям — КАЖДАЯ секция выжимки имеет тип ростера: Задачи → `task`, Решения → `decision`, Цели → `goal`, Запросы → `request`, Идеи → `idea`, Инсайты → `insight`, Факты → `fact`, Принципы → `principle`, Метрики → `metric`, Открытые вопросы → `question`, Риски → `risk`; наблюдение о человеке → `observation`, термин или ASR-ошибка → `term`. Сущность без типа в ростере существовать не может. Дома для всех типов ищутся одними и теми же вопросами миссий файлов ([routing.md](../references/routing.md)); дома первого приближения: идея/гипотеза → `03_backlog` узла; запрос контрагента → `01_overview.md` досье; принцип руководителя → `00_ceo/04_decisions.md`, устойчивый принцип человека контрагента → файл людей досье; цель — файл целей/обзора владеющего контура по его фактическому формату; инсайт без устойчивого дома-миссии остаётся `summary_only` — решением в ростере, не молчанием. Для каждой сущности: id, тип, короткий маркер, уровень (`company | node | grouping | ceo`). **Одна сущность = один id:** не дроби одно решение или задачу на несколько E-номеров.
2. **Список затронутых контуров** — выведи из ВСЕХ типов сущностей ростера, не только задач и решений: контур затронут и если задет лишь риском, открытым вопросом или метрикой. Мимолётное упоминание чужого контура без новой информации о нём и без его действия — не затрагивает (сущность остаётся `summary_only`). Плюс owner-map одной строкой на контур. Плюс список живых карточек проектов каждого затронутого узла (path + одна строка «о чём»).
3. **Disposition каждой сущности:** `write` (пойдёт в файлы) · `summary_only` (остаётся только в выжимке) · `unclear` (спорная — пойдёт в «Сомневаюсь»). После Гейта A disposition НЕ понижается до `summary_only`: передумал писать → дельта в doubtful с `doubt_reason`, решает пользователь. Повышение `unclear → write` разрешено только с пометкой `resolved_from_unclear: <причина>` в ростере.

### Протокол встречи

Протокол НЕ заводится ни сущностью ростера, ни дельтой. Файл протокола публикует spine на `apply` сам: это принятая на confirm выжимка verbatim (при правках пользователя — с приложением «Правки пользователя»), место определил узел `locate-context`. Дельта с типом `protocol` — ошибка валидации.

**Протокол — контейнер принятой выжимки, НЕ канал раскладки.** Существование протокола не отменяет ни одной дельты: ростер и дельты `E01+` строятся так, будто протокола нет; «сущность уже видна в протоколе» — не основание пропустить её дельту в целевой файл.

## Проход по файлам

Пройди по КАЖДОМУ затронутому контуру. По каждой строке справочника миссий, чей файл в контуре существует, задай вопрос по миссии файла: «нужно ли обновить этот файл с учётом новой информации из выжимки?»

**НЕ раскидывай сущности из выжимки по файлам.** Проверяй файлы — это принципиально другой алгоритм.

Отсутствующий файл kit не читаем и не создаём «для полноты». Файла нет, но в выжимке есть контент его миссии (первая запись хроники контура, первое решение) — предложи создать его дельтой `operation: create` с этой записью.

Одна сущность из выжимки может породить обновления в файлах разных контуров.

**Явно адресованная задача не теряется из-за границ контура.** Если в выжимке есть задача, решение или факт, явно адресованные конкретному человеку («это твоя», прямое поручение, атрибуция по имени с приоритетом цитаты, опора уже в выжимке), узел ЭТОГО человека всегда считается затронутым — независимо от того, как встреча классифицирована. Одноузловая по формату встреча (1-on-1, планёрка) не освобождает от переноса задачи в узел адресата. Иначе задача, извлечённая с верной атрибуцией, пропадёт на файл-центричном шаге, потому что узел адресата не открывался. У адресата нет своего узла в базе (владелец или CEO без отдельной организационной папки) — задача идёт в его личный файл (`00_ceo/02_active.md` или эквивалент); нет и такого файла — всё равно заведи дельту на него: пользователь увидит в показе пометку «адресат без файла». Молча пропадать задача не должна. Правило гарантирует ВИДИМОСТЬ узла адресата (минимум — reference-проекция в его active), но не canonical-дом: если предмет задачи — инициатива с живой карточкой, canonical идёт в карточку по правилам card-routing, адресату — проекция.

**Recall-max: дубли разрешены.** Задача этого прохода — ничего не потерять. Сомневаешься, в каком из двух контуров дом сущности, — создай ОБЕ дельты с одним `entity_id`; выбор дома сделает канонизация. Дубль здесь норма, потеря контура или сущности — ошибка. Не удаляй и не сливай дельты ради единственности.

**Задачи живого проекта → в его карточку — решаешь ты, не канонизатор.** Ты читал карточки, только у тебя есть контекст различить «задача — предмет инициативы» и «задача узла, упоминающая проект». Правила выбора — card-routing в [routing.md](../references/routing.md); пометь дельту полем `card_home` с обоснованием одной строкой и оставь владельцу узла reference-проекцию.

**Обратная проверка active обязательна.** Для каждого уже существующего пункта затронутых `02_active.md` отдельно проверь, нет ли в выжимке факта выполнения, отмены или закрытия вопроса. Найденное обязательно оформи отдельной дельтой удаления или переноса — ревью не восстановит пропущенную дельту.

**Предмет уже существует строкой — обновляй её, не дублируй.** Если задача или инициатива из выжимки уже записана в целевом файле (пусть другими словами), дельта — `update` этой строки (статус, подтверждение, уточнение), а не новая `add`-строка рядом. Записи нет нигде и предмет важен → новая дельта; важен, но непонятно, к какому юниту или проекту относится → doubtful с `doubt_question` «к какому юниту/проекту относится задача?» (адъюдикация 29.07).

**Намерение — не задача.** Выраженное желание или запрос («хочу», «хотела бы», «нам нужен») без зафиксированного решения или прямого поручения не становится recommended-задачей. Прошло фильтр важного → doubtful-дельта с `doubt_question` вида «Ставить задачу …? Или зафиксировать как открытый вопрос?»; не прошло → `summary_only` (адъюдикация 29.07).

**Решение без задач.** Из важного решения обычно вытекает работа: решение и вытекающая задача — разные сущности с разными домами (решение → decisions, задача → active), это не дубль. Решение принято, задач по нему в выжимке нет, и непонятно, нужна ли работа, — заведи doubtful-вопрос: «Решение X принято, задач не поставлено. Ставим?» (адъюдикация 29.07). Сам текст решения в `02_active.md` не дублируется никогда.

**Не додумывай.** Факт не подтверждён источником (выжимка или явная правка пользователя) — не достраивай его: дельта идёт в doubtful с вопросом пользователю в поле `doubt_question`.

**Отмена прежнего решения — только пометка статуса.** Новое решение отменяет или заменяет более раннюю запись → тело старой записи не редактируется, правится ровно строка статуса (`Superseded`, формат — [formats.md](../references/formats.md)); частичное устаревание отмечается «Superseded в части …».

## Поля дельты, требующие суждения

Полный контракт полей — `schema/delta.schema.json`. Суждения, которые делаешь ты:

- `source_evidence` — точная ссылка или цитата из выжимки либо явная правка пользователя. Дельта без опоры в ревью не идёт и сразу уходит в «Сомневаюсь».
- `entity_id` — id сущности из ростера. Обязателен для всех дельт, кроме записей хроники (`04_progress.md`) и глоссария.
- `entity_type` — тип из ростера.
- `role` — `canonical` (единственный дом сущности) · `reference` (проекция или ссылка на дом: кросс-ссылка, строка в overview; ≤240 символов) · `consequence` (реальная производная задача с СОБСТВЕННЫМ owner и действием, не пересказ исходной сущности). На этой фазе роль предварительная, финальную назначает канонизация. НЕ заполняется для дельт хроники, глоссария и team-профилей — они вне единственности.
- `owner` — владелец для task- и consequence-дельт.
- `canonical_external: true` — если дом сущности уже существует в файле вне этого прогона, а твоя дельта — проекция на него.
- `spec_id` — только для атомарной нарративной спецификации (архитектура, набор опор): все дельты одного `spec_id` — один связный блок в ОДНОМ файле, не дробить.
- `card_home` — путь живой карточки, если предмет дельты — её инициатива (ставишь только ты, с обоснованием одной строкой).
- `section` — `recommended` или `doubtful`; `doubt_reason` (`dispute | unresolved`) обязателен для каждой doubtful-дельты.
- `anchor` — точный дословный фрагмент целевого файла. Для `add` — после какого фрагмента вставить блок (обычно заголовок секции; без якоря блок допишется в конец файла). Для `update`/`merge` — заменяемый фрагмент: **без якоря spine не заменит, а молча допишет блок в конец файла** — для замены якорь обязателен. Для `delete`/`move` — удаляемый фрагмент: без якоря spine откажет. `source_file` — для `move`.

Вопрос о доме существует ТОЛЬКО как поле `home_question`: сомнение, изложенное свободным текстом или в обосновании, невидимо ни пользователю, ни проверке.

## Что вернуть

Пакет: ростер сущностей + ВСЕ дельты обеих секций (`recommended` и `doubtful`) + список затронутых контуров. Пакет только из recommended — неполный пакет.

## Самопроверка перед сдачей

Записав пакет, прогони его через валидатор инвариантов и чини до чистого — только потом сдавай:

```
python3 <каталог скилла>/scripts/validate_deltas.py --phase coverage < <файл пакета>
```

Exit 0 — сдавай. Exit 1 — почини названные нарушения в файле пакета и прогони снова: сдача с известными нарушениями сжигает rework-попытку всего узла и стоит минут полного перезапуска.

## Сдача артефакта

- Артефакт сдаётся ТОЛЬКО записью файла по абсолютному пути из задания (инструмент Write). Возвращать пакет текстом ответа нельзя — оркестратор читает файл, не твой ответ.
- Финальный текст ответа — короткий статус («артефакт записан: <путь>»), не содержимое артефакта.
- Запись не удалась — повтори запись по тому же пути. Другие пути, форматы и способы сдачи не изобретай.
