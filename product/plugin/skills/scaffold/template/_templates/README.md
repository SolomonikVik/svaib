# _templates — папка шаблонов scaffold

Единый источник шаблонов файлов scaffold v4.1. Узлы ссылаются на эти шаблоны из своих README; физические копии в узлах не дублируются.

## Словарь разворачивания

Эти термины нужны агенту-строителю, чтобы не потерять архитектурную точность при разворачивании. В живом scaffold клиента используем русский рабочий язык.

- **Management Unit** — объект управления: компания, направление, продукт, филиал, клиентский портфель.
- **Management Aspect** — управленческий ракурс: сторона, через которую смотрим на объект управления — стратегия, команда, метрики, проекты, процессы, знания.
- **Management Kit** — управленческая панель: обзор, актив, backlog, хроника, решения.
- **Node / узел** — управляемая сущность в дереве: файл или папка, которая может расти.

## Рабочее имя в живом файле

Перед копированием шаблонов определи рабочее имя субъекта: как этот объект должен называться в клиентском тексте и поиске.

- Источник имени — клиент, не агент. Имя неизвестно → спроси. Спросить нельзя → временный slug с нумерацией (`project-01/`, `project-02/`); агент имя не выдумывает. Slug переименовывается, когда имя появится.
- Физическое имя папки остаётся машинным: `sales/`, `marketing/`, `00_ceo/`.
- Живой текст пишется рабочим языком клиента: `Продажи`, `Маркетинг`, имя руководителя, название клиента или продукта.
- Класс-термин сущности («направление», «функция», «блок», «отдел») тоже бери из языка клиента, а не подставляй шаблонный: клиент называет всё «направлениями» — пиши «направление», не «функция».
- `title`, H1 и аннотация под H1 вместе задают миссию файла. Специализируй все три.
- Generic-слова из шаблона (`узел`, `unit`, `client-name`) не оставляй в живом файле, если субъект известен.
- Чистая автозамена плейсхолдера недостаточна: аннотация должна нормально читаться человеком и быть очевидной в поиске.

## Содержимое папки

- [nodes/](nodes/) — шаблоны узлов: `unit/`, `product/`, `clients/`, `ceo/`. Читать: когда нужно создать новый узел (направление, продукт, клиента, личный контур CEO).
- [management-kit/](management-kit/) — шаблоны управленческой панели узла: overview, active, backlog, progress, decisions. Читать: когда узлу нужен файл управленческой панели.
- [semantic-files/](semantic-files/) — шаблоны типовых смысловых файлов: profile, architecture, setup, glossary и др. Читать: когда узлу нужен устойчивый смысловой файл.
- [aspects/](aspects/) — шаблоны управленческих ракурсов. Читать: когда узлу нужен управленческий ракурс.
- [meetings/](meetings/) — шаблон служебной папки для памяти встреч узла. Читать: когда узлу нужен `meetings/`.
- [infrastructure/](infrastructure/) — шаблоны служебных папок `_inbox/` и `zz_archive/`. Читать: когда узлу нужен буфер сырья или архив.

## Как развернуть узел

Сначала выбери форму. Направление без регулярной операционной работы стартует одним файлом `{unit}.md`: что это, кто отвечает, текущее состояние, важные ссылки; файл вписывается строкой в `## Содержимое папки` README родителя. Появилась регулярная работа (задачи, встречи, решения, команда) → файл разворачивается в папку с тем же именем, обзорная часть переезжает в `01_overview.md` — дальше по шагам ниже.

Новый узел (направление, продукт, клиент, личный контур CEO) — копией из [nodes/](nodes/):

1. Скопируй папку нужного типа из `nodes/{type}/` на её место в дереве.
2. **Переименуй папку под сущность.** Имя шаблона ≠ имя живого узла:
   - `nodes/unit/` → имя объекта управления: `marketing/`, `sales/`, `branch-krasnoyarsk/`
   - `nodes/ceo/` → `00_ceo/`
   - `nodes/product/` → `product/` (или `product/{name}/` при нескольких продуктах) — не отдел разработки (тот — обычный unit из `nodes/unit/`)
   - `nodes/clients/` → `clients/`, внутри `client-name/` → именем клиента: `client-slug/`

   Для `nodes/ceo/`: `{ceo}` = имя руководителя; неизвестно и спросить нельзя — временно `CEO` как частный случай правила об источнике имени выше.
3. Поправь `title`, H1, аннотацию под H1, локальные ссылки и строки `## Содержимое папки` во всех файлах узла под рабочее имя (`sales/` → `Продажи`, `00_ceo/` → имя руководителя, `client-name/` → название клиента).
4. Создай стартовый `01_overview.md` узла — копией из [management-kit/01_overview.md](management-kit/01_overview.md), субъект → имя узла. Это точка входа узла; в шаблоне узла его нет (overview один в папке шаблонов). Исключение — `nodes/ceo/`: точка входа — `01_profile.md`, отдельный overview не создаётся. Второе исключение — `nodes/clients/`: у портфеля `clients/` overview не создаётся, его получает `client-name/`; разворот `clients/` создаёт два узла сразу — шаги 3–6 применяй к каждому. Блок «Статус, сроки и условия» в шаблоне overview — только для проектов и клиентских проектов; при разворачивании направления удали его.
5. Впиши узел строкой в `## Содержимое папки` README родителя.
6. Доразворачивай остальное содержимое узла (управленческую панель, управленческие ракурсы, служебные папки) по правилам ниже — только под живую работу.

Шаблоны узлов `nodes/` тонкие: README + узловые файлы, уникальные для типа узла (`ceo/01_profile`, `product/profile`, `clients/client-name/company`; у ceo также личные формы панели `02_active` и `04_decisions` — они уникальны для ceo, не дубли общего kit). Универсальные файлы (overview, остальная управленческая панель, управленческие ракурсы) берутся из папки шаблонов. По умолчанию `AGENTS.md`/`CLAUDE.md` в узлы не ставятся — вход агента живёт в корне пространства; в папке шаблонов их нет.

## Как развернуть файл или папку

Перед созданием `README.md` определи класс папки:
- Узел из `nodes/` получает `README.md`.
- Управленческий ракурс получает `README.md` только если его шаблон уже содержит README (`03_metrics/`, `projects/`, `processes/`, `knowledge/`).
- Простые ракурсы `01_strategic/` и `02_team/` README не получают: навигация живёт в родительском README и самих файлах ракурса.
- `_private/` создавай у ближайшего владельца; README нужен только при сложной внутренней навигации. Корневой `.gitignore` исключает такие папки на любой глубине; на Google Drive используй `private-<имя владельца>/` с ограниченными правами. Само имя папки не защищает данные: каждый другой способ синхронизации или публикации должен исключать её отдельно.

1. Найди шаблон в нужной группе выше.
2. Скопируй в узел. Папку-шаблон не копируй целиком: создай папку, скопируй её README и только фактически разворачиваемое содержимое; элементы, перечисленные в `## 🔧 Разворачивание`, не копируй до их триггера. Имя с `{...}` переименуй под сущность: `person.md` → `ivan-petrov.md`, `domain-metrics.md` → `sales-metrics.md`, `process.md` → `onboarding.md`. Переименовал файл — поправь и `title`/H1 внутри (`person` → `Иван Петров`).
3. Специализируй шапку файла под рабочее имя: `title`, H1 и аннотацию под H1. Затем заполни плейсхолдеры внутри (`{node}`, `{topic}` и даты событий там, где они стоят в теле файла) и поправь пути: записанные от корня scaffold (например, `01_company/03_metrics/business-metrics.md`) пересчитай под фактическую глубину узла. Данных для секции пока нет — напиши «секция будет заполняться по мере поступления данных» вместо плейсхолдера; секцию, не нужную узлу, удали.
4. Обнови README узла: добавь созданное в `## Содержимое папки` (`- file — миссия. Читать: когда`); добавь или обнови маршруты чтения и записи, если созданное вводит устойчивый сценарий; удали соответствующий элемент из `## 🔧 Разворачивание`. Если элемент входит в категорию, сохрани категорию, пока в ней остаётся что разворачивать.
5. Миссию построй по формуле ниже.
6. Создал новый узел (папку) — допиши его строкой в `## Содержимое папки` README родителя.

Без шаблона: рабочие папки клиента (`docs/`, `contracts/`) и уникальные узловые шаблоны (напр. `profile.md` — лежат шаблоном в самом узле). Нешаблонный md-файл собирается по общей форме: kebab-case имя, YAML `title`, H1, аннотация под H1; миссия — по формуле ниже. `AGENTS.md`/`CLAUDE.md` в узле (экспериментальный механизм доставки) — только указание прочитать локальный `README.md`, без локальных правил. Корневые `AGENTS.md`/`CLAUDE.md` — вход агента, не затирать.

Номера в именах: `NN_` — только там, где порядок важен. Файл и папка с одним номером (`01_overview.md` и `01_strategic/`) уживаются — папки и файлы сортируются раздельно; дыры в номерах — норма, соседей не перенумеровывай.

Профиль человека (`person.md`) создаётся у операционного владельца при первом появлении человека с явной ролью: онбординг, первая встреча, первое упоминание. Правило не касается руководителя пространства: его профиль — `00_ceo/01_profile.md` при развороте личного контура; до него CEO — строкой в оргструктуре.

Встречи размещаются по правилу встреч из корневого README; правило не даёт места → спроси руководителя. Подпапка внутри `meetings/` — когда протоколов много или в одной папке встречи разных типов.

## Миссия файла: формула + заготовки

Формула: **{субъект из имени узла} + {типовая роль файла}**.
Пример: `02_active.md` в `marketing/` → «Marketing — что в работе сейчас».

| Файл | Типовая роль |
|---|---|
| `01_overview` | обзор узла: что это, куда идём, где сейчас |
| `02_active` | что в работе сейчас |
| `03_backlog` | будущая работа, идеи, гипотезы |
| `04_progress` | хроника: что произошло во времени |
| `05_decisions` | журнал решений: что и почему |
| `vision` | идентичность и видение |
| `goal` | цель и план периода |
| `strategy` | действующие стратегические выборы |
| `org-structure` | карта ролей и подчинения |
| `{domain}-metrics` | метрики домена: семантика и источники |
| `person` | профиль человека: роль, зона, стиль |
| `profile` | паспорт сущности: что это по сути |
| `architecture` | как устроено внутри |
| `setup` | рабочая конфигурация: инструменты, доступы |
| `glossary` | словарь терминов |
| `speech-aliases` | словарь распознавания речи |
| `process` | регламент: как выполняется повторяемая работа |

Служебные папки (`_inbox/`, `zz_archive/`, `meetings/`) и карты управленческих ракурсов с README (`03_metrics/`, `projects/`, `processes/`, `knowledge/`) разворачиваются вместе со своим README — миссия уже в шаблоне, формула не нужна. Простые управленческие ракурсы (`01_strategic/`, `02_team/`) README не имеют: навигируют сами файлы и родитель.

## Правила папки шаблонов

- `_templates/` не является управленческой папкой, поэтому здесь нет `AGENTS.md` и `CLAUDE.md`.
- Шаблон хранится в папке шаблонов в единственном экземпляре; узлы не дублируют его, а дают markdown-ссылку.
- Файлы управленческих ракурсов живут внутри своих папок, а не в отдельной общей папке `aspect-files/`.
- Версия шаблона фиксируется здесь и в git, а не в YAML операционных клиентских файлов.

## Связанные контексты

README шаблонов самодостаточен: всё для разворачивания (механика + заготовки миссий) — выше; связей наружу у папки шаблонов нет.
