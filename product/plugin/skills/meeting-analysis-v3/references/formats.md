# Форма записей

Как выглядит запись, чтобы файл оставался читаемым через год. Держат канон контролёр (атака №5 — жанр и объём) и узел applier при записи.

## Датированные блоки

Датированными блоками ведутся файлы времени: хроника (`04_progress`), решения (`05_decisions`), идеи (`ideas`). Живые списки — active и backlog — блоков дат не получают: там запись встаёт пунктом в свою секцию.

Датированный файл ведётся блоками `## YYYY-MM-DD · Заголовок` — запись новой встречи идёт в блок **своей даты**; блока нет — applier создаёт его в канонической позиции файла (посмотри, как заведено: новые даты сверху или снизу; по одному блоку порядок не читается — новые сверху, канон kit). Заголовок нового блока — короткое имя встречи из выжимки, не выдумка. Дата берётся из даты встречи, а не из дня обработки: разбор недельной давности не переносит запись в сегодня.

Заголовки H2 уникальны целиком — вместе с именем встречи: две встречи одного дня дают два блока одной даты с разными заголовками, и это не дефект, а дефект — два блока с одинаковым заголовком. Блок своей встречи ищется по дате **и** имени: нашёлся — записи идут в его конец, в порядке пакета (так записи одной встречи не переставляются местами и не попадают внутрь чужого пункта); нашёлся блок той же даты с чужим заголовком — он чужой, рядом заводится свой.

## Парные правки

`done` — снять пункт из active (вместе с его подпунктами) и добавить строку в хронику блоком даты встречи; `deferred` — снять из active и добавить в бэклог; `dropped` — снять из active. Обе половины пары — одна судьба: снятие без записи и запись без снятия — дефект.

Правило пары — про существующий пункт active. Задача, сделанная прямо на встрече и не стоявшая в active, — одиночная строка в хронику: снимать нечего, и это не дефект.

## Компактность

- одна запись — один факт; список из трёх фактов — три строки, а не абзац;
- жанр файла держится: хроника пишется законченными фразами о сдвиге, active — короткими пунктами с чекбоксом, decisions — «решение + основание»;
- пересказ встречи в базу не едет: для него есть выжимка.

## Даты актуальности

Факт, который протухает (состав команды, цена, срок, статус переговоров), несёт inline-дату: «— на 06.08». Без неё через полгода читатель не отличит устаревшее от актуального.

## Обновление вместо дубля

Предмет уже стоит в базе, а встреча изменила факт или формулировку — запись **обновляется на месте**: новая формулировка встаёт вместо прежней. Двух версий одного предмета рядом не появляется: через месяц читатель не отличит действующую от отменённой, а агент прочтёт обе как факты и сведёт их в противоречие.

Единица обновления — запись, а не строка: пункт с подпунктами, задача со спецификацией, абзац с уточнениями — один предмет. Меняется в ней ровно то, чего касается новый факт: переписана формулировка — уходит прежняя, добавилась подробность — она вписывается в ту же запись. Соседние факты записи и её подпункты правка не задевает.

Заменяемое показывает поле `replaces.text` — первая строка прежней записи, как её видел редактор. Человек по ней понимает, что исчезнет, applier — с чего начать поиск. Строка названа, но в файле не нашлась или нашлась дважды — пункт едет на экран решений спорным. Само место правки определяет applier: файл он читает целиком и непосредственно перед записью. Однозначной записи не выходит — `failed` с причиной, и в файле не меняется ничего: угаданное место правки хуже ненаписанной строки.

Правило про замену, а не про дозапись. Не подпадают:

- **парные правки** (`done`, `deferred`, `dropped`) — запись переезжает между файлами: снятие из active плюс строка в хронике или бэклоге. Это перенос, и обе половины обязательны;
- **новый факт рядом с прежним** — прежняя формулировка остаётся верной, встреча добавила к ней ещё одну: это `new`, а не `update`. Проверка простая: не получается назвать строку, которую заменяешь, — значит ничего не заменяешь;
- **журнал решений** (`05_decisions.md` узла, `01_company/05_decisions.md`, `00_ceo/04_decisions.md`) — там замены не бывает вовсе. Канон панели узла: «Принятые решения не переписываются; если решение устарело, оно помечается как `Superseded` со ссылкой на новое». Пересмотр решения — новая запись; пометка к прежней — часть той же записи, её ставит applier. Решение и его основание живут в базе как история выбора, а не как текущее состояние дел;
- **файл, объявивший своё правило работы** — шапка многих файлов базы говорит, как их вести («Работа с файлом», «Правило файла», «Правило секции»): append-only, «не менять старые записи», «удалять выполненное». Объявленное правило сильнее этого канона: датированный блок, который файл велит не трогать, не трогается — новое идёт записью своей даты.

Факт, который протухает, обновляется вместе со своей inline-датой (см. «Даты актуальности» выше): дата показывает, на когда факт верен.

## Цифры

Метрики в scaffold не копируются: в базе — ссылка на источник правды. Скопированное число расходится с источником в первый же день и делает базу опаснее пустой.

## Чекбоксы и владельцы

Задача в active — `- [ ] текст — отв. И., до <срок>`; владелец не назначен — так и пишем: «отв. не назначен». Придуманный владелец хуже отсутствующего.

## Выжимка встречи

Отдельный файл `{дом протоколов}/{дата}_{тема}_summary.md` — его рендерит и кладёт в базу ядро, узлы к нему не прикасаются. Форма фиксирована: метаданные (дата, участники с ролями, длительность, тип встречи) → содержание встречи нарративом → извлечённые сущности секциями по типам (задачи — чекбоксами под именем владельца) → ключевые цитаты → требует уточнения → снятое на подтверждении. У каждой записи стоит опора — дословная реплика встречи. Порядок внутри секции — по темам; в задачах сначала владелец, внутри владельца — темы. Тема тегом не печатается: её работа — держать рядом то, что обсуждали вместе.

Шапка несёт `status` — этап, на котором стоит разбор, и `run_id` — прогон, который файл написал:

| `status` | Что это значит для читателя |
|---|---|
| `briefed` | выжимка сдана, человек её ещё не подтвердил |
| `confirmed` | выжимка подтверждена, предложения по базе готовятся |
| `review` | предложения проходят контроль |
| `decided` | решения приняты, записи в базу ещё не сделаны |
| `writing` · `applied` | записи применяются · применены |
| `done` | разбор доведён до конца, сводка сдана |

Всё, кроме `done`, означает оборванный разбор — файл говорит об этом и последней строкой, открытым текстом.
