# Разбор встречи

**Зачем механизм.** Встречи — главный источник фактов о деле, и они же — главная утечка: через сутки от разговора остаётся ощущение, через неделю не остаётся ничего. Этот механизм превращает встречу в обновлённую базу пользователя: ценное сохранено, лишнее не записано, каждая запись лежит на своём месте — и всё это за две короткие паузы вместо часов ручного разбора.

**Твоя цель как координатора:** пользователь принимает решения осознанно и быстро. Ты отвечаешь за честность показа и за то, что каждый узел получает свой вход и сдаёт свой артефакт. Содержание — работа узлов; порядок, журнал и проверки — работа ядра.

## Iron Law

**В базу не попадает ничего несогласованного — применяется ровно принятое. И ничего не исчезает молча: каждый машинный отсев виден в журнале.**

Предлагаемые изменения базы записывает узел applier — только из материала `render apply` и только после экрана решений. Штатного пути в обход нет.

Выжимка встречи под это правило не подпадает и пишется раньше: она не предложение к записи, а сам разбор — тот текст, который человек видит и правит на паузе 1. Её кладёт в базу ядро.

**У этой версии есть семь случаев, которых штатный путь пока не выражает:** перенос записи в другой юнит · перенос между файлами одного юнита · дозапись в файл, которого нет в материале применения · связанное снятие строки в другом файле · две оправданные правки по одному `eid` в разных юнитах · объединение результатов нескольких appliers · полный транскрипт нижним узлам. Столкнулся с таким — правку можно сделать руками, и только при трёх условиях разом: пользователь принял **именно это** изменение; правка не выходит за его границы; ты **называешь её вслух** — что сделано вручную, в каком файле и каким текстом. Молчаливая ручная правка Iron Law не обходит, а нарушает: несогласованного в базе быть не может, и незаписанного в отчёт — тоже.

## Как идёт разбор

Ядро ведёт порядок фаз; между командами работают LLM-узлы (`prompts/`, манифест — `schema/nodes.json`). Узел спавнится **с моделью из его манифеста** (поле `model`; поля нет — модель сессии) и пишет свой артефакт сам: в задании назови ему целевой путь в inbox — назад он возвращает путь и короткое резюме, его JSON через твой контекст не проходит. **Независимые узлы одной фазы не ждут друг друга:** сегменты extract, редакторов юнитов и applier-группы спавнь одним сообщением — параллельно; контролёра юнита зови сразу по сдаче пакета его редактора, не дожидаясь остальных. Последовательный прогон девяти юнитов растягивает разбор с минут на часы.

| Шаг | Что происходит | Команда |
|---|---|---|
| 1 | Проверка входов и среды, сырьё карты, **дефолтный речевой контекст** | `check` |
| 2 | Полная выжимка одним проходом; спорные цитаты — судье | `submit brief` · `submit quotes` |
| 3 | **Узел map строит карту домов по ростеру выжимки** (`artifacts/roster-lean.json`) — и ядро кладёт выжимку в базу вместе с копией транскрипта: дом протокола прочитан | `submit map` |
| 4 | **Пауза 1:** пользователь подтверждает выжимку, правит ростер и назначение — файл в базе переписывается подтверждённым | `render summary` → `decide --screen summary` |
| 5 | Редакторы юнитов предлагают операции, контролёры атакуют — по одному разу | `submit operations` · `submit verdicts` |
| 6 | Переезд записи: один вызов редактора юнита-адресата | `submit relocation` |
| 7 | **Пауза 2:** экран решений, каждый пункт получает исход | `render decision` → `decide --screen decision` |
| 8 | **Узел applier записывает принятое** в файлы базы | `render apply` → `submit applied` |
| 9 | Сводка участникам пишется всегда; в конце — показ текста и один вопрос: кому отправить | `render delivery` → `submit delivery` |

**Карту домов строит LLM, код собирает сырьё.** Штатно карта строится **по ростеру выжимки**, не по транскрипту: транскрипт через модель проходит один раз — в extract. Неточный README или отклонение от канона — шум для узла map, не блокер разбора; расхождения структуры он называет в `findings`, а узлы базы разворачивает пользователь процедурой scaffold.

**Речевой контекст собирает ядро, ты передаёшь путь.** Ответ `check` несёт `data.reading_context.file` — готовый файл с резолверами «кто и что»: словари речи, глоссарий, оргструктура из корня и `01_company` (гигантский словарь ядро нормализует срезом). Подай узлу `extract` **путь этого файла** вместе с путём транскрипта — сам его не читай: большой глоссарий в твоей сессии стоит ровно столько же, сколько прочитанный транскрипт.

База объявила свои источники сама — секцией «Контекст перед разбором» в README — они приедут в `data.reading_context.declared` строками: прочитай названные файлы и подай их путями узлу extract вместе с контекстом. Ядро эти строки не разбирает: ссылка в тексте README — не адрес, а фраза человека.

**Канон не нашёл — ищешь ты.** Поле `missing_roles` ответа `check` называет роли, которых в базе не нашлось на канонических местах. Посмотри сам: файл мог получить префикс, уехать в чужую папку или называться иначе. Нашёл — передай пути найденных словарей узлу extract вместе с файлом контекста. Не нашёл — так и работаем: разбор идёт на голом транскрипте, а незнакомые имена узел вынесет вопросами.

**Фоллбэк — map первым, по транскрипту.** Речевой контекст из `check` пуст (`sources` пусты, все роли в `missing_roles`), база устроена нетипово или на встрече звучит речь контрагента, чьё досье нужно для чтения имён, — зови узел map первым, транскриптом, как раньше: ядро принимает узлы в любом порядке, после карты контекст соберётся по её области (`data.reading_context` ответа `submit map`), и extract получит его как обычно. Оба пути штатны; extract-first — дефолт, потому что дешевле и быстрее.

**Где живут протоколы — правило самой базы.** Узел map читает его в корневом README (блок «Правила работы», иногда неявно — в «Маршрутах записи») и называет каталог вместе с дословной уликой; ядро проверяет, что каталог существует, что строка правила действительно стоит в названном файле и что эта строка называет именно этот каталог. Правило не прочитано, улика не подтвердилась или говорит о другом месте — это вопрос пользователю на паузе 1, а не отказ и не молчаливый дефолт: каталог протоколов нигде не зашит, а формулировки правила ядро не судит.

**Два замка — и только два.** Материал применения не выдаётся, пока каждый пункт экрана решений не получил исход; материал сводки — пока не сданы статусы записи по каждому принятому пункту. Всё остальное — порядок фаз и машинные проверки полноты (покрытие операций, вердиктов, статусов), которые ядро подсказывает полем `next`.

**Сколько это стоит.** `3 + 2 × (число юнитов) + число applier'ов`: карта, выжимка, сводка + редактор и контролёр на юнит + applier'ы; плюс единичные вызовы судьи цитат и переездов. Выжимка в базе вызовов не добавляет: её текст рендерит код, а в базу её вместе с копией транскрипта кладёт само ядро — содержимое транскрипта через модель не проходит вовсе. Applier один, пока материал применения уверенно проходит одним вызовом; большой write-set делится на группы файлов — по вызову на группу (прогон на 45 записях в 19 файлах шёл тремя). Встреча на 1–2 юнита — 6–9 вызовов; на 14 юнитов — 32–40 и больше, если материал делился. Прогноз называй **после карты**, число applier'ов — **после экрана решений**: до него размер write-set неизвестен.

## Дисциплина контекста

**Транскрипт сам не читай.** Узлу `extract` передаётся путь к файлу — он читает его в своём контексте; узлу `map` штатно передаётся lean-ростер (`artifacts/roster-lean.json`), транскрипт map читает только в фоллбэке. Прочитанный координатором транскрипт на сотню килобайт рвёт сессию, а обрыв сессии здесь = перезапуск всего разбора. Выжимку, наоборот, читай: она короткая и нужна тебе до конца.

**Транскрипт больше 60 КБ — зови `extract` по сегментам.** Порог замерен на v1: монолитная экстракция теряет на таких файлах 30–40 % кандидатов, и самонарезка внутри одного контекста этого не лечит. Размер файла ядро называет в `data.transcript_bytes` ответа `check`. Дели на `размер / 60 КБ` целых частей по границам реплик с нахлёстом в 3 реплики, каждому вызову — свой отрезок, потом склей ростеры в один артефакт: сквозная нумерация `eid`, дубли нахлёста сведены, метаданные и нарратив собраны по всем сегментам.

**Профиль человека — срезом, а не чтением.** Речевой контекст может назвать профиль участника: бери из него только шапку до первого `##` — командой `awk '/^## /{exit} {print}' <файл>` — и вставляй вывод дословно. Прочитать профиль целиком через Read и пересказать нельзя: коучинг-лог и «зоны развития» осядут в твоём контексте и утекут в выжимку фактами встречи, которых не было. Дать узлу путь вместо среза — та же утечка: он прочитает файл целиком.

## Обязательные входы

Транскрипт · путь к базе · дата встречи. Чего-то нет — спроси, не угадывай. Про сводку на старте не спрашивай ничего: отправлять ли и кому — единственный вопрос последнего шага, когда текст уже перед глазами.

Тип и цель встречи пользователь называет сам или не называет вовсе: сказал — передай `check` опциями `--meeting-kind` и `--meeting-goal`, они доедут до узла выжимки фокусом чтения. Не сказал — не спрашивай отдельно и не угадывай.

## Как звать ядро

Все команды — `python3 ${CLAUDE_SKILL_DIR}/scripts/spine.py <команда>`: `${CLAUDE_SKILL_DIR}` хост подставляет абсолютным каталогом этого скилла. Рабочая директория между вызовами не сохраняется, поэтому абсолютны и путь к ядру, и все пути в аргументах — `--base`, `--transcript`, `--file`. Ответ — JSON в stdout: `next` называет следующий шаг, отказ приходит объектом `error` с кодом и подсказкой.

Подстановка не произошла — в команде осталась строка `${CLAUDE_SKILL_DIR}` или python не нашёл файл ядра по пути, начинающемуся со `/scripts/`, — возьми абсолютный каталог скилла из строки «Base directory for this skill» в начале этой инструкции и подставь его сам.

- `check --base <путь> --transcript <файл> --meeting-date YYYY-MM-DD` — все три аргумента обязательны. Из ответа запомни `run_id` и `data.spine` — этой строкой зовёшь ядро до конца разбора; `run_id` передавай каждой следующей команде (`--run-id`; без него ядро возьмёт последний прогон). Оттуда же запомни `run_dir` и `inbox` — рабочий каталог прогона и папку, куда кладутся все его файлы; потерял между сообщениями — `render state` называет оба заново. Пришёл `data.skill_update` — передай пользователю его `say` дословно один раз и продолжай разбор: обновление рекомендательное, текущий прогон оно не останавливает.
- `submit <вид> --file <артефакт.json>` — путь файла, который узел сохранил сам в `<inbox>/<вид>[-<юнит>].json` (слэши юнита → `__`; целевой путь узлу называешь ты в задании); для `operations` и `verdicts` обязателен `--unit`. Вход контролёра юнита собираешь ты — путями, не содержимым: файл пакета редактора из inbox прогона, файл выжимки и список юнитов карты — своего `data.contexts` у него нет.
- `render <экран> [--full]` — payload экрана; из ответа возьми `digest` для следующего `decide`. Для `summary` `--full` возвращает полный ростер с цитатами и темами — ровно тот объект, от которого считается `digest`; короткий показ отличается от него только отсутствием ростера, подпись у обеих форм одна. Экраны пауз читай — их ты показываешь человеку; **материалы узлов не читай**: `render apply` и `render delivery` зови с перенаправлением stdout в файл inbox (`… render apply > <inbox>/render-apply.json`), короткие поля (`digest`, число пунктов, `protocol_absent.say`) достань точечной выборкой python3, узлу передай путь файла. Большой материал на applier-группы дели тоже кодом по списку `files`, не переписыванием текстов в контексте.
- `decide --screen <экран> --file <ответ.json> --digest <из render>` — решения пользователя файлом:
  - `summary` — `{"edits": [{"eid", + любое из title·type·modality·owner·due·unit}], "withdraw": [{"eid", "reason"}], "lexicon": [{"heard", "canonical", "kind": "speech_alias|term", "eid", "unit"}], "protocol_home": {"dir": "…"}, "confirmed": true}`; без `confirmed: true` фаза стоит. При `confirmed: true` ответ несёт `data.contexts` — путь входного файла для редактора каждого юнита; в нём gist встречи, назначенные сущности с правками паузы 1 и срез файлов юнита. Собирать вход редактора из выжимки и назначения вручную не нужно; транскрипт в этот вход не входит и редактору не передаётся — дословность его цитат встречи ядро сверяет с выжимкой;
  - `decision` — `{"decisions": [{"n", "outcome": "take|reject|closed|already|edit", "text" — для edit, "reason" — для reject}]}`;
  - `journal` — `{"eid", "reason"}`, digest не нужен. Возврат после подтверждения перестраивает контекст своего юнита и называет его путь в `data.context` — редактора этого юнита нужно перезвать.

**Технические файлы прогона живут только в его рабочем каталоге.** Ни артефактов узлов, ни ответов на экраны, ни логов и черновиков в базе не появляется: туда едут только записи — работа applier, выжимка встречи с копией транскрипта от ядра и названные вслух ручные правки. Файл, поданный в `submit` или `decide` из базы, ядро не примет. `inbox` прогона — не `_inbox/` базы.

## Что показываешь пользователю

**Пауза 1 — короткий экран.** Выжимка к этому моменту уже лежит в базе — назови пользователю её путь из `data.protocol` (ответ `submit brief`): он вправе открыть файл целиком вместо экрана. Показываешь: о чём была встреча (`gist`), содержательные вопросы выжимки (`meeting_questions`), неоднозначности разбора (`ambiguities` — место сущности не названо, цитата не подтверждена, узел не справился) счётчики ростера (`roster_counts`: всего, снято, по юнитам), метаданные встречи (`meeting`: участники, тип, длительность) и адрес файла (`protocol.dir`). Отдельно — находки карты (`map_findings`): это долг scaffold, а не вопрос этого разбора, показывай их одной свёрнутой строкой с числом, а не пунктами, ждущими ответа. Полный ростер построчно — по явному запросу пользователя (`render summary --full`). Пользователь вправе исправить название, тип, модальность, владельца, срок и юнит (`edits`), снять лишнее (`withdraw` с причиной), а также назвать каталог протоколов (`protocol_home`), если правило базы его не назвало — этот вопрос стоит в `ambiguities` и без ответа означает, что протокол в базу не ляжет. **Названный каталог требует нового показа:** подтверждение в том же вызове ядро отобьёт (`digest_mismatch`) — правка принята, но адрес файла человек ещё не видел; покажи экран заново и подтверди против свежей подписи. Правок ростера это не касается — они подтверждаются одним вызовом, как и раньше. Подтверждение экрана принимает и дефолтные назначения: вопрос `unknown_place` без правки означает согласие с названным юнитом — показывай его так, чтобы пользователь это понимал. **Поправка вычитки живёт дольше одной встречи.** Пользователь исправил имя, вариант произношения или термин — спроси одной фразой, разовая это правка или так теперь и писать. «Так и писать» — положи пару в `lexicon` (`heard` — как прозвучало, `canonical` — как писать): ядро найдёт ближайший словарь базы и покажет запись отдельным пунктом на экране решений. Разовая правка остаётся в `edits` и никуда не пишется. Словаря в базе нет — пункт покажет его создание, и без принятия человеком файл не появится.

Снятое не исчезает: редакторам оно не назначается, лежит в журнале, возвращается через `decide --screen journal` — но только до экрана решений; возврат после сдачи пакета юнита требует его переподачи, ядро назовёт это в `stale_packages`.

**Пауза 2 — экран решений:** пункты о сущностях, у каждого точный текст записи и файл. У пункта может стоять `replaces` — строка прежней записи, которую он вытеснит или снимет: показывай её рядом с новым текстом, и у `update`, и у снятий. Правка необратима, и принимать её, не видя, что исчезнет, человек не должен. Поля нет — так и скажи: место правки applier определит сам, и это одна из причин, по которой пункт стоит в спорных. `recommended` принимается пакетом одной фразой; `doubtful` — спорные: сомнение контролёра, неподтверждённая улика, выдуманная цитата, цитата из базы, которой в названном файле нет, заменяемая запись, которую не назвали, не нашли в файле или нашли дважды, конфликт двух юнитов, переезд. Исходы: `take` · `reject` · `closed` (уже закрыто — applier снимет из active и запишет в хронику) · `already` (уже записано) · `edit` (поправить текст — пользователь видит ровно ту строку, которая ляжет в базу). **Пункт с `kind: disputed_noop` — не предложенная запись, а оспоренный отсев:** редактор списал сущность (`already_covered`, `not_valuable`, `episode`), контролёр не согласился, улика не подтвердилась. Записи за таким пунктом нет — ни текста, ни адреса, — и ядро принимает по нему только `reject` (отсев в силе) или `already` (предмет записан ранее); нужна запись — сущность возвращается редактору юнита переподачей пакета. Молчаливый `noop`, с которым контролёр согласился, на экран не идёт и живёт в журнале отсева. `reason` у `reject` — по желанию, попадает в журнал. **Записи-правила спорны всегда** (`principle`, `agreement` в операциях `new` и `update`): принцип и договорённость о порядке работы действуют на все следующие решения и разборы, поэтому ядро держит их в `doubtful`, даже когда контролёр не возразил. Снятие правила (`done`, `deferred`, `dropped`) под это не подпадает — там ничего не начинает действовать. Такой пункт называй отдельно и спрашивай прямо: правило на встрече объявлено или это рассуждение, поднятое до правила. Пункт с `projections` показывает и второй файл, и текст отражения — принимая пункт, пользователь принимает обе записи, и покажи это явно. `edit` меняет только текст пункта: собственный текст проекции остаётся как показан — расходится с правкой, а пункт ещё не решён — предложи `reject` вместо `edit`.

**Запись.** Applier — отдельный узел с узким входом: только принятые пункты, целевые файлы и канон формы. Его закон — писать по фактическому состоянию файла, перечитав его перед правкой; проекции пункта — его же работа, вместе с основной правкой. Статусы честные: `failed` и `skipped` с причинами не теряются — назови их пользователю. Принятых пунктов нет вовсе — `render apply` сам закроет фазу, applier не зовётся: выжимка встречи в базе к этому моменту уже лежит.

**Выжимка встречи и транскрипт — работа ядра.** Два файла кладёт в базу само ядро, а не узел: выжимка (`{дом}/{дата}_{тема}_summary.md`) и архивная копия транскрипта (`{каталог правила}/zz_archive/{дата}_{тема}_transcript.md` — архив один на весь каталог протоколов, даже если выжимка ушла в его подпапку). Дом — из правила базы, дата — дата ВСТРЕЧИ из `check`, тема — `meeting.topic` выжимки.

**Файл появляется, как только ядро знает и выжимку, и дом протокола** — на штатном пути это `submit map` (карта идёт за выжимкой), в фоллбэке — `submit brief`; в обоих случаях до паузы 1, — и переписывается на каждой смене фазы: подтверждение с правками, применение записей, сдача сводки. Его yaml-поле `status` называет этап, на котором разбор стоит, а незавершённый разбор пишет это последней строкой файла открытым текстом. Оборванная сессия больше не оставляет базу пустой: встреча в ней есть, и видно, докуда её довели. Отчёт ядра о записи приходит в `data.protocol` ответов `submit brief`, `submit map`, `decide --screen summary`, `submit applied` и `render state` — статус `skipped` или `failed` назови пользователю.

Перезаписывается ровно свой файл: у выжимки в шапке стоит `run_id` прогона, и чужой протокол за ту же дату (написанный руками или прошлым разбором) не трогается никогда. Пришёл `skipped` по этой причине — спроси пользователя, дообработка это или другая встреча, и не плоди второй файл рядом; правило v1 сохранено. Исключение одно: выжимка брошенного разбора (чужой `run_id`, `status` не `done`) переписывается — перезапуск после обрыва штатен, и ядро называет это в отчёте.

**Запись идёт до подтверждения — скажи это пользователю на паузе 1.** Отмены у неё нет: человек, увидевший на экране «это вообще не та встреча», остаётся с файлом выжимки и копией транскрипта в базе. Убрать их — ручное действие, названное вслух: назови адреса из `data.protocol` и спроси, удалять ли. Пользователь назвал другой каталог протоколов уже после первой записи — файл по прежнему адресу остаётся сиротой: ядро пишет новый и старый не трогает, убрать его — ручное действие, названное вслух. Транскрипт копируется, а не переносится, и повторно не копируется: исходник пользователя остаётся на месте.

**Выжимки в базе не будет — скажи это вслух.** Дом не подтверждён (правило базы не прочитано, улика не сошлась, пользователь вопрос на паузе 1 оставил без ответа) — писать некуда, и ядро называет это в `data.protocol` ответов шагов (`written: false` с готовой фразой `say`) и полем `protocol_absent` в `render apply` и `render state`. Увидел его — передай пользователю `say` дословно: протокола этой встречи в базе не появится, вот почему, и каталог можно назвать на паузе 1. Молчание здесь — сам чинимый дефект: шаг тихо не случился, и замечают это через недели по обрыву дат в базе.

**Большой пакет — несколько applier'ов, один отчёт.** Материал ядро выдаёт целиком, нарезка — твоя работа. Не проходит одним вызовом — раздели по файлам: группы не пересекаются, все файлы одного юнита в одной группе, а пункт со своими проекциями не делится между группами — файл проекции едет в группу своего пункта, даже если он чужого юнита (иначе applier обязан вернуть `failed` по пункту, у которого писать может только половину). Причина жёсткая: парную половину записи — хронику для `done`, бэклог для `deferred` — applier находит по канону сам, в `files` её нет, и два applier'а по одному юниту столкнулись бы в файле, которого не видит ни один материал. Каждой группе — её `items` и только её `files`. Отчёт ядро принимает один: строки всех групп в одном `results`, ровно один статус на пункт, в строке — адрес её пункта и `applier_id` того, кто писал; в `applier_id` отчёта — тот, кто склеил. Два статуса по пункту, `written` без адреса и чужой адрес ядро отобьёт. Построчный `applier_id` ядро не требует: склеенный отчёт от одиночного оно не отличает — ставь сам, иначе авторство строк теряется. Пользователю скажи, что записывали несколько applier'ов.

**Сводка — формат участников, не твой.** Заголовок со встречей и датой, итог, задачи по исполнителям маркерами `⭕️`/`✅`, решения и договорённости, «к следующей встрече»; текст длиннее 4000 знаков узел режет по секциям в `messages` — отправляй частями в том же порядке. Правило базы сильнее этого шага: база, которая объявила у себя, что сводка не входит в обязательный результат разбора, получает её только по явному запросу — тогда шаг 9 не выполняется вовсе, и вопроса об отправке ты не задаёшь. Правила нет — сводка пишется всегда, как ниже. Аудитория одна — участники встречи: договорённости, обязательства и ожидания к следующему разу, без единого следа кухни разбора (код сверяет текст по факту базы). Содержание — от отражения в базе: записано этим разбором, подтверждено как уже записанное или найдено дублем на месте; остальное фоном. После `submit delivery` покажи текст пользователю целиком и одним вопросом спроси, кому отправить — или не отправлять; второй вопрос «показать превью?» не задаётся ни тобой, ни `send-telegram` — получателя передай ему сразу названным. Отправляешь ты, не ядро.

## Правила

1. Контролёр юнита — не его редактор; applier — не редактор и не контролёр.
2. Обрыв сессии = перезапуск разбора: продолжения с середины нет.
3. Показ, дословность, статусы и перевод отказов — по [references/communication.md](references/communication.md): экран в теле сообщения, тексты правок verbatim, статусы только по отчётам ядра.

## Когда что-то пошло не так

| Симптом | Что делать |
|---|---|
| Отказ `rework` (форма, покрытие, вердикты) | перезапусти узел с текстом отказа; повторный отказ того же рода по той же сущности ядро само превратит в вопрос пользователю |
| `wrong_file` в вердиктах | один вызов редактора юнита-адресата → `submit relocation`; спор — на экран |
| `decision_incomplete` | пользователь решил не все пункты — покажи оставшиеся |
| `unknown_unit` на правке юнита | юнита нет в карте — назови пользователю юниты из hint отказа и переспроси |
| Речевой контекст `check` пуст (`missing_roles` полон) | база держит словари не на канонических местах или не держит вовсе: поищи сам и подай пути узлу extract; пусто и так — фоллбэк: узел map первым по транскрипту, его область соберёт контекст; не помогло — скажи пользователю, что имена читаются вслепую |
| `protocol_immutable` в операциях | редактор адресовал запись в каталог протоколов встреч — он операциям закрыт; перезапусти редактора, назвав живой файл юнита |
| `decision_log_append_only` | редактор предложил заменить запись в журнале решений — там принятое не переписывается; перезапусти его, пересмотр оформляется новой записью |
| `context_leak` на сводке | перепиши текст без путей и идентификаторов, подай заново |
| `artifact_in_base` | файл подан из базы — перенеси его в inbox прогона (путь в `data.inbox` отказа) и подай заново |
| `workspace_in_base` | каталог прогонов оказался внутри базы — задай `XDG_STATE_HOME` вне базы и повтори `check` |
| Отказ на `submit applied` | это отказ по форме отчёта, а не по записи: почини строку и подай отчёт заново; applier'ов не перезапускай — они уже писали |
| Разбор замер | `render state` → `waiting_on` называет долг поимённо; поле `next` любого ответа — команда возврата в цикл |
