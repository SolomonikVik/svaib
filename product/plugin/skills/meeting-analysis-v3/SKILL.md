# Разбор встречи

**Зачем механизм.** Встречи — главный источник фактов о деле, и они же — главная утечка: через сутки от разговора остаётся ощущение, через неделю не остаётся ничего. Этот механизм превращает встречу в обновлённую базу пользователя: ценное сохранено, лишнее не записано, каждая запись лежит на своём месте — и всё это за две короткие паузы вместо часов ручного разбора.

**Твоя цель как координатора:** пользователь принимает решения осознанно и быстро. Ты отвечаешь за честность показа и за то, что каждый узел получает свой вход и сдаёт свой артефакт. Содержание — работа узлов; порядок, журнал и проверки — работа ядра.

## Iron Law

**В базу не попадает ничего несогласованного — применяется ровно принятое. И ничего не исчезает молча: каждый машинный отсев виден в журнале.**

Запись делает узел applier — только из материала `render apply` и только после экрана решений. Штатного пути в обход нет.

**У этой версии есть семь случаев, которых штатный путь пока не выражает:** перенос записи в другой юнит · перенос между файлами одного юнита · дозапись в файл, которого нет в материале применения · связанное снятие строки в другом файле · две оправданные правки по одному `eid` в разных юнитах · объединение результатов нескольких appliers · полный транскрипт нижним узлам. Столкнулся с таким — правку можно сделать руками, и только при трёх условиях разом: пользователь принял **именно это** изменение; правка не выходит за его границы; ты **называешь её вслух** — что сделано вручную, в каком файле и каким текстом. Молчаливая ручная правка Iron Law не обходит, а нарушает: несогласованного в базе быть не может, и незаписанного в отчёт — тоже.

## Как идёт разбор

Ядро ведёт порядок фаз; между командами работают LLM-узлы (`prompts/`, манифест — `schema/nodes.json`).

| Шаг | Что происходит | Команда |
|---|---|---|
| 1 | Проверка входов и среды, сырьё карты | `check` |
| 2 | **Узел map строит карту домов** по канону scaffold из сырья | `submit map` |
| 3 | Полная выжимка одним проходом; спорные цитаты — судье | `submit brief` · `submit quotes` |
| 4 | **Пауза 1:** пользователь подтверждает выжимку, правит ростер и назначение | `render summary` → `decide --screen summary` |
| 5 | Редакторы юнитов предлагают операции, контролёры атакуют — по одному разу | `submit operations` · `submit verdicts` |
| 6 | Переезд записи: один вызов редактора юнита-адресата | `submit relocation` |
| 7 | **Пауза 2:** экран решений, каждый пункт получает исход | `render decision` → `decide --screen decision` |
| 8 | **Узел applier записывает принятое** — и вместе с ним кладёт в базу протокол встречи и копию транскрипта | `render apply` → `submit applied` |
| 9 | Сводка участникам пишется всегда; в конце — показ текста и один вопрос: кому отправить | `render delivery` → `submit delivery` |

**Карту домов строит LLM, код собирает сырьё.** Неточный README или отклонение от канона — шум для узла map, не блокер разбора; расхождения структуры он называет в `findings`, а узлы базы разворачивает пользователь процедурой scaffold.

**Где живут протоколы — правило самой базы.** Узел map читает его в корневом README (блок «Правила работы», иногда неявно — в «Маршрутах записи») и называет каталог вместе с дословной уликой; ядро проверяет, что каталог существует, что строка правила действительно стоит в названном файле и что эта строка называет именно этот каталог. Правило не прочитано, улика не подтвердилась или говорит о другом месте — это вопрос пользователю на паузе 1, а не отказ и не молчаливый дефолт: каталог протоколов нигде не зашит, а формулировки правила ядро не судит.

**Два замка — и только два.** Материал применения не выдаётся, пока каждый пункт экрана решений не получил исход; материал сводки — пока не сданы статусы записи по каждому принятому пункту. Всё остальное — порядок фаз и машинные проверки полноты (покрытие операций, вердиктов, статусов), которые ядро подсказывает полем `next`.

**Сколько это стоит.** `3 + 2 × (число юнитов) + число applier'ов`: карта, выжимка, сводка + редактор и контролёр на юнит + applier'ы; плюс единичные вызовы судьи цитат и переездов. Протокол встречи вызовов не добавляет: его текст рендерит код из подтверждённого состояния, а в базу его вместе с транскриптом копирует тот же applier — и содержимое транскрипта через модель не проходит вовсе. Applier один, пока материал применения уверенно проходит одним вызовом; большой write-set делится на группы файлов — по вызову на группу (прогон на 45 записях в 19 файлах шёл тремя). Встреча на 1–2 юнита — 6–9 вызовов; на 14 юнитов — 32–40 и больше, если материал делился. Прогноз называй **после карты**, число applier'ов — **после экрана решений**: до него размер write-set неизвестен.

## Обязательные входы

Транскрипт · путь к базе · дата встречи. Чего-то нет — спроси, не угадывай. Про сводку на старте не спрашивай ничего: отправлять ли и кому — единственный вопрос последнего шага, когда текст уже перед глазами.

## Как звать ядро

Все команды — `python3 ${CLAUDE_SKILL_DIR}/scripts/spine.py <команда>`: `${CLAUDE_SKILL_DIR}` хост подставляет абсолютным каталогом этого скилла. Рабочая директория между вызовами не сохраняется, поэтому абсолютны и путь к ядру, и все пути в аргументах — `--base`, `--transcript`, `--file`. Ответ — JSON в stdout: `next` называет следующий шаг, отказ приходит объектом `error` с кодом и подсказкой.

Подстановка не произошла — в команде осталась строка `${CLAUDE_SKILL_DIR}` или python не нашёл файл ядра по пути, начинающемуся со `/scripts/`, — возьми абсолютный каталог скилла из строки «Base directory for this skill» в начале этой инструкции и подставь его сам.

- `check --base <путь> --transcript <файл> --meeting-date YYYY-MM-DD` — все три аргумента обязательны. Из ответа запомни `run_id` и `data.spine` — этой строкой зовёшь ядро до конца разбора; `run_id` передавай каждой следующей команде (`--run-id`; без него ядро возьмёт последний прогон). Оттуда же запомни `run_dir` и `inbox` — рабочий каталог прогона и папку, куда кладутся все его файлы; потерял между сообщениями — `render state` называет оба заново. Пришёл `data.skill_update` — передай пользователю его `say` дословно один раз и продолжай разбор: обновление рекомендательное, текущий прогон оно не останавливает.
- `submit <вид> --file <артефакт.json>` — ответ узла сохрани в `<inbox>/<вид>[-<юнит>].json` (слэши юнита → `__`) и подай путём; для `operations` и `verdicts` обязателен `--unit`.
- `render <экран> [--full]` — payload экрана; из ответа возьми `digest` для следующего `decide`. Для `summary` `--full` возвращает полный ростер с цитатами и темами — ровно тот объект, от которого считается `digest`; короткий показ отличается от него только отсутствием ростера, подпись у обеих форм одна.
- `decide --screen <экран> --file <ответ.json> --digest <из render>` — решения пользователя файлом:
  - `summary` — `{"edits": [{"eid", + любое из title·type·modality·owner·due·unit}], "withdraw": [{"eid", "reason"}], "protocol_home": {"dir": "…"}, "confirmed": true}`; без `confirmed: true` фаза стоит. При `confirmed: true` ответ несёт `data.contexts` — путь входного файла для редактора каждого юнита; в нём gist встречи, назначенные сущности с правками паузы 1 и срез файлов юнита. Собирать вход редактора из выжимки и назначения вручную не нужно; транскрипт в этот вход не входит и редактору не передаётся — дословность его цитат встречи ядро сверяет с выжимкой;
  - `decision` — `{"decisions": [{"n", "outcome": "take|reject|closed|already|edit", "text" — для edit, "reason" — для reject}]}`;
  - `journal` — `{"eid", "reason"}`, digest не нужен. Возврат после подтверждения перестраивает контекст своего юнита и называет его путь в `data.context` — редактора этого юнита нужно перезвать.

**Технические файлы прогона живут только в его рабочем каталоге.** Ни артефактов узлов, ни ответов на экраны, ни логов и черновиков в базе не появляется: туда едут только записи — работа applier и названные вслух ручные правки. Файл, поданный в `submit` или `decide` из базы, ядро не примет. `inbox` прогона — не `_inbox/` базы.

## Что показываешь пользователю

**Пауза 1 — короткий экран:** о чём была встреча (`gist`), содержательные вопросы выжимки (`meeting_questions`), неоднозначности разбора (`ambiguities` — место сущности не названо, цитата не подтверждена, узел не справился) и счётчики ростера (`roster_counts`: всего, снято, по юнитам). Отдельно — находки карты (`map_findings`): это долг scaffold, а не вопрос этого разбора, показывай их одной свёрнутой строкой с числом, а не пунктами, ждущими ответа. Полный ростер построчно — по явному запросу пользователя (`render summary --full`). Пользователь вправе исправить название, тип, модальность, владельца, срок и юнит (`edits`), снять лишнее (`withdraw` с причиной), а также назвать каталог протоколов (`protocol_home`), если правило базы его не назвало — этот вопрос стоит в `ambiguities` и без ответа означает, что протокол в базу не ляжет. **Названный каталог требует нового показа:** подтверждение в том же вызове ядро отобьёт (`digest_mismatch`) — правка принята, но адрес файла человек ещё не видел; покажи экран заново и подтверди против свежей подписи. Правок ростера это не касается — они подтверждаются одним вызовом, как и раньше. Подтверждение экрана принимает и дефолтные назначения: вопрос `unknown_place` без правки означает согласие с названным юнитом — показывай его так, чтобы пользователь это понимал. Снятое не исчезает: редакторам оно не назначается, лежит в журнале, возвращается через `decide --screen journal` — но только до экрана решений; возврат после сдачи пакета юнита требует его переподачи, ядро назовёт это в `stale_packages`.

**Пауза 2 — экран решений:** пункты о сущностях, у каждого точный текст записи и файл. `recommended` принимается пакетом одной фразой; `doubtful` — спорные: сомнение контролёра, неподтверждённая улика, выдуманная цитата, цитата из базы, которой в названном файле нет, конфликт двух юнитов, переезд. Исходы: `take` · `reject` · `closed` (уже закрыто — applier снимет из active и запишет в хронику) · `already` (уже записано) · `edit` (поправить текст — пользователь видит ровно ту строку, которая ляжет в базу). `reason` у `reject` — по желанию, попадает в журнал. Пункт с `projections` показывает и второй файл, и текст отражения — принимая пункт, пользователь принимает обе записи, и покажи это явно. `edit` меняет только текст пункта: собственный текст проекции остаётся как показан — расходится с правкой, а пункт ещё не решён — предложи `reject` вместо `edit`.

**Запись.** Applier — отдельный узел с узким входом: только принятые пункты, целевые файлы, канон формы и раздел `protocol`. Его закон — писать по фактическому состоянию файла, перечитав его перед правкой; проекции пункта — его же работа, вместе с основной правкой. Статусы честные: `failed` и `skipped` с причинами не теряются — назови их пользователю. Писать нечего вообще — ни принятых пунктов, ни протокола — `render apply` сам закроет фазу, applier не зовётся; но один только протокол уже повод его позвать.

**Протокол встречи и транскрипт.** Вместе с принятым в базу едут два файла: протокол (`{дом}/{дата}_{тема}_summary.md`) и архивная копия транскрипта (`{дом}/zz_archive/{дата}_{тема}_transcript.md`). Дом — из правила базы, дата — дата ВСТРЕЧИ из `check`, тема — `meeting.topic` выжимки. Текст протокола рендерит ядро из снимка состояния, подписанного на паузе 1 (что бы ни изменилось после подписи — возврат из журнала, например, — текст остаётся тем, который человек подтвердил); applier оба файла **копирует** — материал несёт пути, не тексты. Транскрипт копируется, а не переносится: исходник пользователя остаётся на месте. У протокола нет отдельного писателя: его кладёт тот же applier, тем же вызовом, что и принятые пункты. Протокол за эту дату уже существует — ядро скажет об этом в материале (`exists`), и applier обязан вернуть `skipped` с причиной: существующий протокол не перезаписывается никогда. Это держит ядро, а не дисциплина узла: `written` по адресу, который ядро видело занятым или на котором лежит не приготовленный им файл, отбивается кодом `protocol_overwrite`. Статусы по обоим файлам обязательны, и каждый называет свой адрес из материала — без них ядро отчёт не примет и сводки не выдаст.

**Протокола не будет — скажи это вслух.** Дом не подтверждён (правило базы не прочитано, улика не сошлась, пользователь вопрос на паузе 1 оставил без ответа) — раздела `protocol` в материале нет, а вместо него стоит `protocol_absent` с человеческой причиной; то же поле несёт `render state`. Увидел его — передай пользователю `say` дословно: протокола этой встречи в базе не появится, вот почему, и каталог можно назвать на паузе 1. Молчание здесь — сам чинимый дефект: шаг тихо не случился, и замечают это через недели по обрыву дат в базе.

**Большой пакет — несколько applier'ов, один отчёт.** Материал ядро выдаёт целиком, нарезка — твоя работа. Не проходит одним вызовом — раздели по файлам: группы не пересекаются, все файлы одного юнита в одной группе. Причина жёсткая: парную половину записи — хронику для `done`, бэклог для `deferred` — applier находит по канону сам, в `files` её нет, и два applier'а по одному юниту столкнулись бы в файле, которого не видит ни один материал. Каждой группе — её `items` и только её `files`. Отчёт ядро принимает один: строки всех групп в одном `results`, ровно один статус на пункт, в строке — адрес её пункта и `applier_id` того, кто писал; в `applier_id` отчёта — тот, кто склеил. Два статуса по пункту, `written` без адреса и чужой адрес ядро отобьёт. Построчный `applier_id` ядро не требует: склеенный отчёт от одиночного оно не отличает — ставь сам, иначе авторство строк теряется. Пользователю скажи, что записывали несколько applier'ов.

**Сводка.** Аудитория одна — участники встречи: договорённости, обязательства, открытые вопросы, без единого следа кухни разбора (код сверяет текст по факту базы). Содержание — от отражения в базе: записано этим разбором, подтверждено как уже записанное или найдено дублем на месте; остальное фоном. После `submit delivery` покажи текст пользователю целиком и одним вопросом спроси, кому отправить — или не отправлять; второй вопрос «показать превью?» не задаётся ни тобой, ни `send-telegram` — получателя передай ему сразу названным. Отправляешь ты, не ядро.

## Правила

1. Контролёр юнита — не его редактор; applier — не редактор и не контролёр.
2. Обрыв сессии = перезапуск разбора: продолжения с середины нет.
3. Показ, дословность, статусы и перевод отказов — по [references/communication.md](references/communication.md): экран в теле сообщения, тексты правок verbatim, статусы только по отчётам ядра.

## Когда что-то пошло не так

| Симптом | Что делать |
|---|---|
| Отказ `rework` (форма, покрытие, вердикты) | перезапусти узел с текстом отказа; повторный отказ того же рода по той же сущности ядро само превратит в вопрос пользователю |
| `wrong_file` в вердиктах | один вызов редактора юнита-адресата → `submit relocation`; спор — на экран |
| `decision_incomplete` | пользователь решил не все пункты — покажи оставшиеся |
| `unknown_unit` на правке юнита | юнита нет в карте — назови пользователю юниты из hint отказа и переспроси |
| `context_leak` на сводке | перепиши текст без путей и идентификаторов, подай заново |
| `artifact_in_base` | файл подан из базы — перенеси его в inbox прогона (путь в `data.inbox` отказа) и подай заново |
| `workspace_in_base` | каталог прогонов оказался внутри базы — задай `XDG_STATE_HOME` вне базы и повтори `check` |
| Отказ на `submit applied` | это отказ по форме отчёта, а не по записи: почини строку и подай отчёт заново; applier'ов не перезапускай — они уже писали |
| `protocol_overwrite` | applier заявил запись поверх существующего протокола (или файла, которого ядро не готовило): верни по этому файлу `skipped` с причиной и подай отчёт заново. Файл всё же перезаписан — скажи это пользователю прямо: восстановление идёт версионной историей его базы |
| Разбор замер | `render state` → `waiting_on` называет долг поимённо; поле `next` любого ответа — команда возврата в цикл |
