# Ревью предлагаемых правок перед показом согласующему

Общая стадия для ОБОИХ путей обработки встреч (внутренние встречи и встречи с контрагентом): предложенные L2 обновления файлов проверяются независимым ревьюером ДО показа согласующему. Согласующий — тот, кто утверждает правки в вызывающем оркестраторе: руководитель (внутренние встречи) или исполнитель (встречи с контрагентом). Цель — согласующий разрешает содержательные разногласия, а не делает машинную сверку предлагаемых правок с документом.

## Место в пайплайне

После файл-центричного прохода L2 (Шаг 3 L2-procedure-scaffold-update / L2-procedure-client-update), ПЕРЕД показом обновлений согласующему (Шаг 4).

- **Вход:** принятая согласующим выжимка целиком вместе с его явными правками при вычитке; по каждому затронутому файлу — текущий файл, его миссия (правило файла из шапки + маршрут записи из README узла/досье), список предложенных дельт.
- **Внутренний контракт дельты:** `id` · `target_file` · `operation` (`add|update|delete|move|merge|create`) · `proposed_text` · `source_evidence` (точная ссылка/цитата из выжимки либо явная правка согласующего при её вычитке, зафиксированная координатором).
- **Выход:** внутренние вердикты по каждой дельте `accept` · `revise` · `reject` · `escalate_insufficient_evidence` · `escalate_spec_gap`; при reject/escalate — обязательное поле `dispute_class` (`fact|node|placement_antipattern|placement_choice`, см. L2-review-prompt.md); компактный HITL-показ (human-in-the-loop — согласование человеком) без служебной разметки.

## Процедура (координатор)

1. Нормализуй дельты L2 по внутреннему контракту. Дельту без `source_evidence` не отправляй в ревью: сразу отнеси в «Сомневаюсь» с пометкой «нет зафиксированной опоры».
2. Для каждого затронутого файла запусти ОДНОГО независимого субагента-ревьюера с промптом из L2-review-prompt.md + пакетом: миссия файла, текущий файл целиком, дельты этого файла, принятая выжимка целиком вместе с явными правками согласующего как справочный источник. Если дельта ссылается на соседний канонический файл (перенос, supersession, маршрут) — приложи и его с пометкой «контекст, не редактируется». Если вызывающая L2-процедура типизирует дельты (`role`), пометь в пакете: `reference`-дельта — короткая проекция/ссылка на каноническое место в другом файле, оценивается корректность связи, а не полнота текста; краткость reference — не дефект; служебные поля `entity_id`/`role` ревьюер сохраняет как есть и не повышает `reference`/`consequence` до `canonical` — единственность размещения решается вне per-file ревью. Для дельты протокола встречи (`entity_type: protocol`, файл в каталоге протоколов) координатор САМ сверяет декларацию с фактом на диске непосредственно перед запуском ревью (Read/Glob по каталогу протоколов — ревьюер работает без инструментов) и прикладывает ревьюеру meta `protocol_required`/`protocol_path` + зафиксированный результат проверки одной строкой («протокол этой встречи на диске: есть/нет»); расхождение декларации с фактом ревьюер оформляет как `reject` с `dispute_class: fact`.
3. Все вызовы — синхронные (`foreground`). В интерактивной среде выполнения запускай ревьюеров всех затронутых файлов одновременно одним пакетом. Если среда ограничивает число параллельных вызовов — используй максимально разрешённую параллельность; последовательно запускай только в режиме без диалога (`headless`) или после фактического отказа параллельного запуска. Если инструмент `Agent` поддерживает выбор модели, для этой узкой задачи явно используй `sonnet`, а не наследуй более дорогую модель координатора.
4. Разбери YAML-ответы и собери один HITL-показ, сгруппированный по файлам:
   - **Советую обновить** — `accept` и безопасные `revise`; итоговый текст ревьюера уже встроен, если фактический смысл не изменился. Если координатор не может уверенно подтвердить, что `revise` сохранил фактический смысл, отнеси дельту в «Сомневаюсь».
   - **Сомневаюсь / placement_question — детерминированный маппинг по `dispute_class`** (не по свободному тексту reason):

     | Вердикт ревьюера | Действие координатора |
     |---|---|
     | `reject`/`escalate_*` + `dispute_class: fact` или `node` | → «Сомневаюсь», `doubt_reason: dispute` |
     | `reject`/`escalate_*` + `dispute_class: placement_antipattern` | → «Сомневаюсь», `doubt_reason: dispute` |
     | `reject`/`escalate_*` + `dispute_class: placement_choice` | дельта ОСТАЁТСЯ `canonical` в «Советую обновить» + поле `placement_question` (короткий вопрос согласующему) |
     | `reject`/`escalate_*` без валидного `dispute_class`, а также любой вердикт вне словаря | как `fact` (консервативный дефолт) → «Сомневаюсь», `doubt_reason: dispute` |

     `doubt_reason` проставляется В МОМЕНТ перевода дельты в «Сомневаюсь» — дельта без него не пройдёт валидатор (S6). Любое разногласие координатора о фактическом смысле (в т.ч. неуверенный `revise`) — тоже «Сомневаюсь» с `doubt_reason: dispute`.
   - Не показывай ID, служебные значения вердиктов, YAML, рассуждения координатора, полные обоснования и альтернативные варианты одной дельты.
5. Если вызывающая L2-процедура определяет code-валидатор дельт (двухфазный L2, `validate_deltas.py`) — после сборки HITL-показа верни управление координатору для повторного прогона `--phase final`: per-file ревью не видит межфайловую картину и могло молча создать пропуск или вернуть кросс-файловый дубль. Перед прогоном выполни чеклист-страховку протокола (координаторский чек, per-file ревьюеру недоступен): у каждой write-сущности ростера есть ≥1 дельта с `target_file` вне каталога протоколов (`meetings/`); сущность, оставшаяся только в тексте протокола, — пропуск покрытия (протокол — контейнер, не канал раскладки) → верни на доработку, не принимай тихо.
6. Решение всегда за согласующим: сохрани внутреннее соответствие показанных пунктов их `id`, примени только явно принятые дельты и ровно в принятом виде. Отклонённое согласующим не применяй и не предлагай повторно.

Целевая форма показа:

```markdown
## Советую обновить
### {путь к файлу}
- {итоговая правка}

## Сомневаюсь
### {путь к файлу}
- {итоговая правка} — Вопрос: {короткое разногласие}
```

## Рабочие заметки координатору

- **Цель слияния:** при вердикте «слить с существующим пунктом» проверь пункт-цель — ревьюер может выбрать не лучший; согласующему показывай цель явно.
- **Иерархия проверки:** миссия и канон файла решают, нужна ли дельта и куда она относится; принятая выжимка вместе с явными правками согласующего решает, что именно было сказано. `source_evidence` — точка трассировки, а не граница факта.
- **Ядро факта:** ревьюер может убрать эпизодическую иллюстрацию/шум или предложить слияние, если устойчивое утверждение не изменилось. Нельзя добавлять, удалять или смягчать ядро факта из-за узкой `source_evidence`: такое разногласие уходит в «Сомневаюсь», а не маскируется редактурой.
- Вердикты стохастичны: расхождение с ожиданием согласующего — нормальная работа HITL-стадии, не сбой.
