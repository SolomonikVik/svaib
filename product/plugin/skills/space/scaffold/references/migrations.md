# Версия и обновление каркаса

Версия пространства — `.svaib/space.json`, версия установленного каркаса — `version.txt`. Отсутствие space.json у прежнего пространства означает `4.0`. Обязательные начальные проверки и политика совместимости — операция «Проверить готовность» скилла; равные версии не отменяют незавершённый переход.

## Метаданные

```json
{
  "schema_version": 1,
  "scaffold_version": "4.2",
  "updated": "2026-09-18",
  "migrations_applied": ["4.1_svaib-folder", "4.2_root-files"],
  "package_skills": [],
  "custom_skills": [],
  "kept": [],
  "in_progress": null
}
```

`migrations_applied` — журнал фактически выполненных переходов, не основание выбрать цепочку: её определяет версия. У нового пустого пространства журнал пуст. `package_skills` хранит имена прежней поставки, `custom_skills` — клиентских скиллов, `kept` — согласованные дубли с `kind`, `name`, `path`, `sha`. При обновлении эти данные сохраняются; поля не обнуляются ради миграции. `in_progress` — имя начатого незавершённого перехода.

## Обновление

Сначала диагностическая сверка поставки. При равных версиях без незавершённого перехода обновлять нечего. Установленный scaffold старее пространства — не понижай и не строй обратную цепочку; верни необходимость более свежего плагина. Неизвестная схема или версия требует выяснения состояния, а не принудительной инициализации.

Собери непрерывную цепочку `from` → `to` от текущей версии до `version.txt`, сравнивая числа с нормализацией коротких номеров. Разрыв, незнакомая начатая миграция или отсутствующие материалы — остановись до записи. Для известного незавершённого перехода сначала установи фактически выполненное и оставшееся; равенство версий само по себе не закрывает его.

Прочитай переходы и действующие правила до согласования изменений. Применяй требования миграций о сохранении правил и данных до замены файлов. Можно согласовать итоговый пакет без установки промежуточных редакций по операции «Дополнить каркас»; это не отменяет требований и проверок каждого перехода. Ссылки, содержание встреч и пользовательские ограничения обрабатываются по соответствующим миграциям, не по предположениям о форме файлов.

До первой записи покажи чувствительные правки нумерованными вопросами с рекомендацией для каждого. Нужное точное согласие получено — исполни подтверждённое. Перед изменением файлов запиши `in_progress`; неизвестные поля и данные метаданных сохрани. После успешной проверки перехода обнови версию, дату и журнал, затем очисти `in_progress`. Для схлопнутого пакета версия поднимается до целевой только после проверки всех его обязательных итоговых эффектов; до этого `in_progress` обозначает ближайший незакрытый переход. Не помечай прошлые переходы как «уже применено» только по итоговой форме корневых файлов.

Согласованный пункт отменён до записи — ничего по нему не меняй. Отказ после частичного исполнения или ошибка — остановись, назови сделанное и оставшееся; `in_progress` сохраняется, версия не повышается за непроверенное. Продолжение требует согласия лишь на ещё не разрешённое или изменившееся. Пустой `in_progress` допустим только если нет начатого незавершённого перехода.

## Восстановление

Под git до изменения миграцией рабочее дерево должно быть чистым. Есть незакоммиченное — покажи и верни необходимость сохранить его; не коммить и не сбрасывай чужое автоматически. Без git используй историю версий и корзину хранилища; до деструктивного шага назови, что исчезнет и как восстановить. Самостоятельный молчаливый откат запрещён.

Обновление общего пространства выполняет один человек. Перед записью перечитай изменяемые файлы и метаданные; появились чужие правки — пересобери затронутую часть пакета и получи недостающее согласие, не затирай их.
