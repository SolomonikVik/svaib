# Оркестратор: полная обработка встречи

Процедура для координатора (основной чат). Руководитель говорит "была встреча, обработай" — координатор проводит полный цикл: выжимка → обновление scaffold → Telegram-сводка.

## Область применения

Встречи объектов управления (узлы-направления в корне) и кросс-функциональные встречи любого уровня, вплоть до уровня компании (`{target_unit}` = `01_company/`). Группировка обрабатывается как обычная единица — у неё свои файлы управленческой панели (те из 01_overview…05_decisions, что у неё развёрнуты) на её уровне.

Два разных вопроса, два разных правила (детали — Шаг 0):
- **Куда положить протокол/выжимку встречи** — по клиентскому правилу встреч, зафиксированному в корневом README (блок «Правила работы»). Правило не найдено/неоднозначно → уточнить у руководителя.
- **Какой узел считать `{target_unit}` для сущностей встречи** (active/backlog/progress/decisions, которые обновит L2) — по общему правилу наименьшей общей родительской папки, применённому к **содержанию** встречи, не к формальной принадлежности участников (детали — Шаг 0). Эти два места могут не совпадать.

Встреча с контрагентом — вне области применения этого файла (детали — Шаг 0).

Вне области применения этой версии: стратегические встречи, меняющие `01_company/01_strategic/` (vision, goal, strategy), — они требуют отдельного чеклиста. Поведенческий экстрактор пока не подключён: выжимка строится только экстрактором сущностей; каноническая сборка обоих выходов будет добавлена позже.

## Когда использовать

Руководитель просит обработать встречу / говорит что транскрипт готов / "сделай всё что нужно".

## Критические правила

1. **НЕ читай транскрипт сам.** Передай путь субагенту. Транскрипт большой и забьёт контекст.
2. **Выжимку — ЧИТАЙ.** После L1 прочитай выжимку — она ~100 строк, нужна для всех последующих шагов.
3. **Субагенты работают синхронно (`foreground`).** НЕ используй `run_in_background: true`.

## Шаг 0: Собери контекст

Спроси руководителя:
- Что за встреча? По какому направлению?
- Кто участвовал?
- Какая цель встречи? (если не сказали — записать "неизвестно")
- Где транскрипт? (путь к файлу)
- Дата встречи (если не назвал явно и не видно из транскрипта — уточни; не подставляй дату обработки)

По ответу определи путь к транскрипту и тип встречи — как назвал руководитель:
- **Внутренняя** (1-on-1, планёрка, стратсессия и т.д.) → продолжай этот файл
- **Клиентская** (с контрагентом) → останови этот файл и выполни целиком orchestrator-client-meeting.md

Зафиксируй:
- `{date}` = дата, когда встреча состоялась (формат `YYYY-MM-DD`) — не дата обработки
- `{topic}` = короткое название темы, snake_case, английский

Оба значения используются во всех путях ниже без изменений (конвенция полностью — Шаг 4).

### Целевой узел сущностей `{target_unit}`

Правило маршрутизации (один узел / группировка дочерних узлов / уровень компании — LCA по **содержанию** встречи, не по формальному членству участников) — целиком в L2-procedure-scaffold-update.md Шаг 1. Открой его и примени сейчас, на Шаге 0 (не жди Шага 2) — `{target_unit}` нужен раньше, для контекста L1 ниже. Не пересказывай правило по памяти здесь — источник один, в L2-файле.

**Уверенности в узле нет — не выдумывай.** Ставь `{target_unit}` = "неизвестно", проект-фон (ниже) не подавай, при необходимости уточни у руководителя. К Шагу 2 с `{target_unit}` = "неизвестно" не переходи — сначала уточни направление.

### Место протокола встречи `{target_dir}`

Прочитай корневой `README.md` → блок «Правила работы»: там должно быть зафиксировано клиентское правило размещения встреч — централизованно (например, всё в `01_company/meetings/`) или распределённо по узлам. Блока нет (у клиента ещё не приведено к канону v4.1) — правило может быть выражено неявно в «Маршрутах чтения/записи» того же README; ищи там. Правило не найдено или неоднозначно даже так — не выдумывай, уточни у руководителя.

`{target_dir}` = узел, в чьей папке `meetings/` живёт протокол по этому правилу (например `01_company`). Обычно совпадает с `{target_unit}`, но может отличаться (клиент централизует все протоколы в `01_company/meetings/`, а сущности встречи всё равно маршрутизируются по владельцам на Шаге 2). Путь строится как `{target_dir}/meetings/...` — не включай `meetings/` в само значение `{target_dir}`, иначе путь задвоится (`meetings/meetings`)

### Контекст транскрипта (обязательно)

Три секции для L1 — резолверы «кто и что», не содержание встречи. Файл или секция отсутствует (kit/глоссарий ещё не развёрнут) → пропусти эту секцию, ничего не создавай и не подставляй замену:

1. **Люди** — прочитай `01_company/02_team/01_org-structure.md`. Для вариантов имён/ошибок транскрибатора проверь `ls 01_company/` — файл `speech-aliases.md` есть → читай его; нет (сегодня так у всех клиентов, разделения ещё не внедрено) → читай секции "Люди" и "Люди за пределами оргструктуры" из `01_company/glossary.md`
2. **Глоссарий** — прочитай секцию "Термины и сокращения" из `01_company/glossary.md`
3. **Тип/цель встречи** — из ответа руководителя. Если цель не озвучена — "неизвестно"

### Контекст проекта (фон для классификации)

По типу встречи — **ровно один** источник-фон, обзор целевого объекта:

| Тип встречи | Подать (только это) |
|-------------|---------------------|
| По подразделению/направлению (планёрка, статус, разбор), `{target_unit}` ≠ `01_company/` | `{target_unit}/01_overview.md`, если развёрнут; не развёрнут → ничего |
| 1-on-1 с сотрудником | идентити-срез профиля сотрудника, не руководителя (ниже) + `{target_unit}/01_overview.md`, если развёрнут |
| `{target_unit}` = `01_company/`, не стратсессия (кросс-функциональная / вся компания) | `01_company/operating-model.md`, если развёрнут — компания канонически не держит `01_overview.md` |
| Стратсессия | `01_company/01_strategic/vision.md` + `01_company/01_strategic/goal.md` |
| `{target_unit}` = "неизвестно" | ничего (проект-фон не подаётся) |

#### Профиль участника — жёсткое правило идентити-среза

Профиль (`01_company/02_team/{person}.md`) идёт в пакет L1 **только** как срез до первого `##` — имя + роль / чем занимается. Глубокие секции (Стиль работы, Сильные стороны, Зоны развития, **Коучинг-лог**) в пакет L1 **не идут никогда**: это L2-контекст и производный нарратив, он течёт в выжимку. (YAML-шапка обычного клиентского файла по канону — только `title`, поэтому специально вырезать её из среза не нужно: там и так нечему течь.)

Механизм (обязателен — **не** Read, **не** ссылка на файл):

```
ls 01_company/02_team/                                     # не угадывай имя файла
awk '/^## /{exit} {print}' 01_company/02_team/{person}.md  # срез до первого ##
```

Вставь вывод второй команды дословно. Запрещено: (а) читать профиль через Read и пересказывать — глубокие секции осядут в твоём контексте и утекут в пакет; (б) давать L1 путь к профилю вместо среза — субагент прочитает файл целиком → та же утечка. Роль и так резолвится из org-structure; срез — дополнение, не замена. Профилей участников для L2 (Шаг 2 ниже) это ограничение не касается — там профиль читается целиком осознанно.

#### Что НЕ передавать в L1 (закрытый список)

Пакет L1 = ровно секции, собранные выше. Больше ничего:
- Не добавляй файлы «на всякий случай» и не выводи «полезное» из диалога — источники закрыты списком выше
- Не подавай производный нарратив: коучинг-логи, старые выжимки встреч, `{target_unit}/04_progress`, `{target_unit}/05_decisions`, любые пересказы файлов
- Не дампи файл целиком там, где указан срез или именованная секция
- Контекст = фон для чтения транскрипта, не источник содержания выжимки

## Шаг 1: Выжимка (L1)

Перед запуском проверь содержимое `{target_dir}/meetings/` (Glob/Read, не shell — `ls` может быть запрещён окружением) — протокол за `{date}` с похожим `{topic}` уже существует → это дообработка или новая встреча? Уточни у руководителя, не создавай второй файл рядом. **Существующий протокол не переписывать автоматически** ни в каком случае, включая «дообработку» — даже с явным упоминанием находки в выводе. Без ОК руководителя единственные допустимые действия: (а) остановиться и спросить, (б) назвать находку в выводе текстом, не трогая файл. Причина: автоматическая перезапись под видом «дообработки» уничтожает принятый протокол.

Запусти L1-субагента через Agent tool. По умолчанию используй Sonnet (`model: "sonnet"`); явно выбранная руководителем модель имеет приоритет:

```
Прочитай промпт из файла meeting-analysis/L1-prompt-entity-extractor.md в каталоге skills рабочего пространства (каталог скилла — `.claude/skills/meeting-analysis/` от корня пространства)
(секция "Промпт", содержимое внутри блока ```).

Подай контекстный пакет (собранный координатором на шаге 0):

## Контекст транскрипта
### Люди
{содержимое org-structure + glossary/люди}

### Глоссарий
{содержимое glossary/термины}

### Тип/цель встречи
{тип, цель, направление — или "неизвестно"}

## Контекст проекта
{ровно то, что предписано таблицей «Контекст проекта» на Шаге 0 для этого типа встречи — overview/operating-model/идентити-срез/vision+goal — или пусто, если {target_unit} = "неизвестно"}

Прочитай транскрипт: {path_to_transcript}

Примени промпт к транскрипту.

Результат ЗАПИШИ инструментом Write (не через bash, не через redirect) в файл: {target_dir}/meetings/{date}_{topic}_summary.draft.md
(это черновик — итоговое имя файл получит только после подтверждения руководителем)

Если нужен bash (например ls) - используй только simple, single bash commands - no &&, no ||, no pipes, no ;, no redirects. Это ограничение не касается записи результата — та идёт через Write.
```

После завершения субагента — прочитай выжимку.

Покажи руководителю:
- Где сохранена: ссылка на файл `{target_dir}/meetings/{date}_{topic}_summary.draft.md`
- Содержание встречи: из секции «Содержание встречи» выжимки
- Спроси: "Выжимка готова — посмотри, всё ли на месте. Двигаемся дальше?"

**Не переходи к шагу 2 без подтверждения руководителя.**

**Публикация — только после подтверждения.** Руководитель подтвердил → переименуй черновик в итоговый файл `{target_dir}/meetings/{date}_{topic}_summary.md` (перенос содержимого Write + удаление черновика, либо `mv`). Пока подтверждения нет, файла с итоговым именем в базе не существует — обрыв разбора оставляет максимум явный `.draft.md`. Разбор остановлен до подтверждения → удали черновик и скажи руководителю, что база не тронута.

**Если руководитель поправил имена, термины или ошибки транскрибатора** при вычитке выжимки — запомни эти правки. Они пойдут в L2 как кандидаты для обновления: термины → `01_company/glossary.md`; имена/ошибки распознавания → туда же, куда читали на Шаге 0 (`speech-aliases.md`, если он есть у клиента, иначе `glossary.md`).

## Шаг 2: Обновление файлов проекта (L2)

Выполни процедуру из L2-procedure-scaffold-update.md **с Шага 1**. `{target_unit}` уже определён на Шаге 0 — не пересчитывай его, но пройди Шаг 1 целиком: он определяет, какие узлы читать/обновлять для кросс-функциональных встреч и стратсессий (родитель + каждый затронутый дочерний узел, `01_company/05_decisions.md` и т.д.) — без этого шага L2 недочитает часть узлов.

Список чтения (README, kit-файлы, профили, glossary, decisions) — канонический, в самом L2-файле, Шаг 2; следуй списку из файла, не пересказывай его по памяти здесь.

После файл-центричного прохода (Шаг 3 L2) — стадия ревью предлагаемых правок: см. L2-review-procedure.md. Затем покажи руководителю компактные разделы «Советую обновить» и «Сомневаюсь», сгруппированные по файлам, без служебных ID/вердиктов; примени после ОК только принятые дельты.

## Шаг 3: Telegram-сводка (L2)

После завершения обновлений, предложи: "Сделать Telegram-сводку для отправки участникам?"

Если да — запусти субагент:

```
Прочитай промпт из файла meeting-analysis/L2-prompt-protocol-telegram.md в каталоге skills рабочего пространства (каталог скилла — `.claude/skills/meeting-analysis/` от корня пространства)
(секция "Промпт", содержимое внутри блока ```).

Прочитай выжимку: {target_dir}/meetings/{date}_{topic}_summary.md

Примени промпт к выжимке.

Результат выведи текстом (НЕ записывай в файл — координатор покажет руководителю для отправки).

Use only simple, single bash commands - no &&, no ||, no pipes, no ;, no redirects.
```

Когда сводка готова, спроси руководителя: **"Показать в чате или отправить в Telegram?"**

Выведи сводку в code block (```), чтобы руководитель мог скопировать одним действием.

### Вариант B: Отправить в Telegram

## Шаг 4: Финализация

1. Убедись что выжимка опубликована и **непуста**: `{target_dir}/meetings/{date}_{topic}_summary.md`. Файла нет, черновик есть — публикация после подтверждения (Шаг 1) не состоялась: опубликуй черновик сейчас и продолжи. Нет ни итогового файла, ни черновика — выжимка не состоялась: сообщи руководителю, транскрипт не архивируй. 0 байт — ошибка записи, сообщи руководителю и транскрипт не архивируй. Остался черновик `{date}_{topic}_summary.draft.md` при живом итоговом файле — удали черновик
2. Перемести транскрипт в zz_archive: `{target_dir}/meetings/zz_archive/{date}_{topic}_transcript.md`

`{date}`/`{topic}` — те же значения, зафиксированные на Шаге 0; не переопределяй их здесь.
