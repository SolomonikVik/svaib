# Обновление файлов проекта по выжимке встречи

L2-надстройка над выжимкой встречи. Получает готовую выжимку, делает файл-центричный проход по файлам проекта, предлагает обновления руководителю.

**Слой:** L2 (надстройка поверх выжимки встречи, категория «Обновление файлов проекта»).

**Архитектура шага — двухфазный L2.** Покрытие и дедуп — разные цели, они разведены по стадиям: Фаза A (Шаг 3) собирает дельты на максимум полноты, дубли разрешены; code-валидатор проверяет полноту; Фаза B (Шаг 3.3, отдельный субагент в узком контексте) назначает каждой сущности единственное каноническое место; code-валидатор проверяет единственность. Не смешивай цели фаз: на Фазе A не дедуплицируй, на Фазе B не расширяй покрытие.

## Вход

1. **Выжимка** — готовый файл `_summary.md` (результат L1-пайплайна)
2. **Контекст от руководителя** — ответ на вопрос: "Что за встреча? По какому направлению? Кто участвовал?"

## Выход

Список обновлений по файлам. Каждое обновление: какой файл → что добавить/изменить → почему (ссылка на выжимку). Применяется ТОЛЬКО после ОК руководителя.

## Область применения

Встречи объектов управления (узлы-направления в корне) и кросс-функциональные встречи любого уровня, вплоть до уровня компании (`{target_unit}` = `01_company/`). `{target_unit}` для файлов ниже выбирается по правилу наименьшей общей родительской папки (LCA) — детали в Шаге 1. Группировка обрабатывается как обычная единица — у неё свои файлы управленческой панели (01_overview…05_decisions) на её уровне.

Место самого протокола встречи (`meetings/`) — отдельный вопрос, не подчиняется этому правилу; определяется на Шаге 0 оркестратора клиентским правилом из корневого README.

Вне области применения этой версии: стратегические встречи, меняющие `01_company/01_strategic/` (vision, goal, strategy), — они требуют отдельного чеклиста по стратегическим файлам.

## Шаг 1: Определи область обновления

`{target_unit}` = "неизвестно" → не выполняй эту процедуру; сначала уточни направление у руководителя (см. orchestrator-meeting.md Шаг 0).

Если `{target_unit}` уже определён на Шаге 0 оркестратора — используй его как есть, не пересчитывай. При самостоятельном запуске (без оркестратора) определи его по ответу руководителя: узел, к чьей зоне ответственности относится содержание встречи — правило наименьшей общей родительской папки, применённое к содержанию, не к формальному членству участников (руководитель, обсуждающий чужую зону, LCA не расширяет).

Место протокола — отдельное клиентское правило (см. «Область применения»), на `{target_unit}` не влияет.

**Встреча внутри одного подразделения/направления** (1-on-1, планёрка отдела):
- `{target_unit}` = `{org_node}/` (или `{org_node}/{sub_node}/`)
- Читать: файлы `{target_unit}` + `01_company/02_team/` участников

**Кросс-функциональная встреча дочерних узлов одной группировки** (например, маркетинг + продажи внутри `commercial/`):
- `{target_unit}` = папка группировки, `{parent}/` (`commercial/`)
- Читать: файлы папки группировки + файлы КАЖДОГО затронутого дочернего узла + `01_company/02_team/` участников
- Обновлять: файлы дочерних узлов И файлы родительского уровня группировки (те kit-файлы, что у неё реально развёрнуты), если кросс-функциональный контекст изменил общую картину

**Встреча верхушки разных направлений** (стратсессия руководителей):
- `{target_unit}` = уровень компании `01_company/`
- Читать: файлы КАЖДОГО затронутого подразделения/направления + `01_company/02_team/` участников + `01_company/05_decisions.md`
- Обновлять: файлы затронутых единиц + при необходимости `01_company/05_decisions.md` (решения уровня компании)

## Шаг 2: Собери контекст

1. Прочитай выжимку
2. Прочитай README целевой папки (папок из Шага 1) — карта узла, локальные правила маршрутизации, если есть
3. Прочитай `01_company/operating-model.md`, если развёрнут — это канонический закон размещения сущностей клиента, always-read при управленческой работе. Задаёт маршрутизацию иначе, чем LCA из Шага 1 (например, отдельный слой инициатив/карточек) → приоритет за operating-model.md, LCA — дефолт на случай его отсутствия
4. Прочитай те файлы kit целевой папки (папок), которые реально существуют: `01_overview.md`, `02_active.md`, `03_backlog.md`, `04_progress.md`, `05_decisions.md`. Kit собирается по потребности — не у каждого узла развёрнуты все пять; отсутствующий файл не читаем и не создаём «для полноты». `04_progress.md`/`05_decisions.md` очень большие (десятки тысяч строк) → читай последние ~10-15 записей (свежее сверху, начало файла), не весь файл
5. Прочитай `01_company/02_team/{person}.md` для каждого участника встречи. Файла нет (внешний человек, профиль не заведён) → пропусти, не создавай
6. Прочитай `01_company/glossary.md`, если развёрнут. Проверь наличие `01_company/speech-aliases.md` (Glob/Read, не shell) — есть → прочитай и его
7. При кросс-функциональной встрече или стратсессии — прочитай `01_company/05_decisions.md`
8. В выжимке есть личное решение/принцип руководителя как человека, не бизнес-решение — прочитай `00_ceo/04_decisions.md`, если развёрнут
9. У затронутых узлов с папкой `{node}/projects/` — перечисли живые карточки проектов (карточка живая = лежит вне `zz_archive/` и её `02_active.md` непуст) и прочитай их `01_overview.md` + `02_active.md`: задачи живых инициатив маршрутизируются в карточку, не в юнит-файл (см. таблицу размещения Фазы B)

### Гейт A (до прохода): ростер сущностей и список затронутых узлов

Выполни ПЕРЕД файл-центричным проходом, письменно (служебный артефакт, согласующему не показывается):

0. **Протокол встречи.** Определи место протоколов по клиентскому правилу Шага 0 оркестратора (`{target_dir}/meetings/`, где `{target_dir}` — переменная Шага 0 orchestrator-meeting.md; правило клиента — единственный источник, дефолтного узла нет: правило не найдено → уточни у руководителя, как требует Шаг 0; путь НЕ хардкодится). Проверь наличие протокола ЭТОЙ встречи инструментами Read/Glob — НЕ через shell (`ls` может быть запрещён окружением). Протокола нет → заведи в ростере сущность `E00: протокол встречи` (тип `protocol`, вне ролевой единственности) — она обязательна; её дельта на Фазе A: `operation: create`, `target_file: <место протоколов>/<дата>_<slug>.md`, `proposed_text` = содержимое принятой выжимки («перенос» = create-дельта с её текстом, выжимка уже прочитана на Шаге 2 — shell-копирование не используется). Протокол уже есть → `E00` не создаётся, второй файл протокола не предлагается (дубль запрещён). Результат зафиксируй парой meta-полей для пакета валидатора (Шаги 3.2/3.4): `protocol_required: true|false` и `protocol_path: "<каталог протоколов>"`. **Протокол — контейнер принятой выжимки, НЕ канал раскладки: включение сущности в текст протокола НЕ отменяет её дельту в целевой файл (canonical/reference по обычным правилам). Ростер и дельты сущностей E01+ строятся независимо от существования протокола/E00; E00 — единственная сущность, которая размещается в протоколе.**
1. **Ростер сущностей.** Пронумеруй сущности выжимки `E01, E02…` по секциям: Задачи → `task`, Решения → `decision`, Факты → `fact`, Риски → `risk`, Открытые вопросы → `question`, Метрики → `metric`; наблюдение о человеке → `observation`, термин/ASR → `term`; протокол встречи → `protocol` (только `E00` из п.0). Для каждой: id, тип, короткий маркер, уровень (`company | node | grouping | ceo`). Одна сущность = один id: не дроби одно решение/задачу на несколько E-номеров.
2. **Список затронутых узлов** — выведи из ВСЕХ типов сущностей ростера, не только задач/решений: узел затронут и если задет лишь риском, открытым вопросом или метрикой. Мимолётное упоминание чужого узла без новой информации о нём и без действия этого узла — не затрагивает его (сущность остаётся `summary_only`). Плюс owner-map одной строкой на узел. Плюс список живых карточек проектов каждого затронутого узла (path + одна строка «о чём», из Шага 2 п.9). **Диета одноузлового пути:** если затронутый узел ровно один — owner-map и карточки собирай только для него; при ≥2 узлах диета не применяется, собирай полный список.
3. **Disposition каждой сущности:** `write` (пойдёт в файлы) · `summary_only` (остаётся только в выжимке) · `unclear` (спорная — пойдёт в «Сомневаюсь»). После Гейта A disposition НЕ понижается до `summary_only`: передумал писать → дельта в doubtful с `doubt_reason`, решает согласующий. Разрешённое повышение `unclear → write` — только с пометкой `resolved_from_unclear: <причина>` в ростере (Фаза B разрешила сомнение и обязана оставить след).

Пройди файл-центричный проход по КАЖДОМУ узлу из этого списка.

## Шаг 3: Фаза A — файл-центричный проход на покрытие (recall-max)

### Iron Law обновления

После обновления — состояние проекта в файлах актуально. Выжимка остаётся как полная запись встречи. Не всё из выжимки должно попасть в файлы — это нормально.

### Принцип: выжимка щедрая, файлы проекта строгие

Выжимка сохраняет всё (Iron Law L1). Файлы проекта — только то, что имеет устойчивую ценность: стратегические решения, факты о бизнесе, задачи с `owner`, изменения в целях и структуре. Операционная мелочь, разовые реплики, бытовые просьбы остаются в выжимке и не попадают в файлы.

---

Пройди по каждой строке чеклиста ниже, чей файл в затронутых узлах существует или был дочитан на Шаге 2 (пп. 7-8), и спроси по миссии файла: "нужно ли обновить этот файл с учётом новой информации из выжимки?" Файла kit нет, но в выжимке есть контент его миссии (первая запись хроники узла, первое решение) — предложи руководителю создать файл с этой записью на Шаге 4; без такого контента файл не создаём.

**Явно адресованная задача не теряется из-за области `{target_unit}` с Шага 1.** Если в выжимке есть задача/решение/факт, явно адресованные конкретному человеку («это твоя», прямое поручение, атрибуция по имени с приоритетом цитаты, опора уже в выжимке L1), узел ЭТОГО человека всегда считается затронутым, независимо от того, как Шаг 1 классифицировал саму встречу (одноузловая/кросс-функциональная/стратсессия). Одноузловая по формату встреча (1-on-1, планёрка) не освобождает от переноса задачи в узел адресата, если он не совпадает с `{target_unit}`. Иначе задача, явно извлечённая L1 с верной атрибуцией, пропадёт на файл-центричном шаге, потому что узел адресата не открывался. Если у адресата нет своего узла в scaffold (например, владелец/CEO без отдельной организационной папки), задача идёт в его личный файл (`00_ceo/02_active.md`/эквивалент) или, если такого тоже нет, явно называется на Шаге 4 как «требует адресата без готового файла», а не молча пропадает. Это правило гарантирует ВИДИМОСТЬ узла адресата (минимум — reference-проекция в его active), но не каноническое место: если предмет задачи — инициатива с живой карточкой, canonical идёт в карточку по правилам card-routing ниже, адресату — проекция.

**НЕ раскидывай сущности из выжимки по файлам.** Проверяй файлы — это принципиально другой алгоритм.

**Протокол — контейнер принятой выжимки, НЕ канал раскладки: включение сущности в текст протокола НЕ отменяет её дельту в целевой файл (canonical/reference по обычным правилам). Ростер и дельты сущностей E01+ строятся независимо от существования протокола/E00; E00 — единственная сущность, которая размещается в протоколе.** «Сущность уже видна в протоколе» — не основание пропустить её дельту: с точки зрения покрытия дельта протокола (E00) не покрывает никого, кроме самого E00 (валидатор считает так же — S11).

### Чеклист

| Файл | Миссия | Тест-вопрос |
|------|--------|-------------|
| 01_overview.md | ЧТО это направление и КУДА идёт | Новое о целях, KPI, границах, команде, ключевых проектах? Тест: будет актуально через квартал? |
| 02_active.md | ЧТО АКТУАЛЬНО сейчас, НЕ архив | Гейт как у overview/decisions: попадает только то, что в работе **прямо сейчас** — тест не «есть `owner`», а «руководитель вернётся к этому до следующей встречи». Новая задача (`owner` есть или нет — не критерий; без него помечай «owner не назначен»), открытый вопрос, риск, которые проходят этот тест? Повестку следующей встречи НЕ вносить (производный нарратив координатора) — только дата/статус следующей встречи, если прозвучали. Не проходит и не срочно → `03_backlog.md`, не сюда. Сначала сопоставь новое с существующим — связанные пункты объединяй, не дублируй. **Симметрично удаляй уже неактуальное:** вопрос этой встречи решён → убрать (решение → decisions); повестка этой встречи обработана → убрать; риск снят/реализовался → убрать; задача выполнена → `[x]` и сразу удалить (хроника — в 04_progress, отдельной секции-накопителя не создавать) |
| 03_backlog.md | БУДУЩАЯ работа: отложенное | Есть ли идея, гипотеза или задача, важная, но не проходит тест active (руководитель НЕ вернётся к этому до следующей встречи)? Не дублируй то, что уже ушло в 02_active |
| 04_progress.md | КАК ДВИГАЛИСЬ | Дописать запись о встрече (формат ниже) — **в начало файла**, свежее сверху |
| `{target_unit}`/05_decisions.md | ПОЧЕМУ так решили (уровень подразделения/направления) — если `{target_unit}` конкретный узел, не группировка и не компания | Стратегические решения внутри единицы? Тест: через 3 мес спросят "почему так?" |
| {parent}/05_decisions.md | ПОЧЕМУ так решили (уровень группировки) | Только для кросс-функциональных встреч. Решения, охватывающие несколько дочерних единиц группировки, но не меняющие курс компании? Тест: затрагивает 2+ дочерних узла группировки, но не vision/goal/strategy компании |
| 01_company/05_decisions.md | ПОЧЕМУ так решили (курс компании) | Решения уровня всей компании (pivot, стратегия, структура, принципы найма)? Только при стратсессиях или кросс-функциональных встречах |
| 00_ceo/04_decisions.md | ПОЧЕМУ так решил CEO (личный уровень) | Личные решения руководителя как человека в роли (принципы работы, границы, как принимает решения)? Тест: про CEO как личность, не про бизнес-решение |
| 01_company/02_team/{person}.md | КТО этот человек | Наблюдения о стиле, сильных сторонах, зонах развития? Коучинг? Тест: про ЧЕЛОВЕКА или про ПОДРАЗДЕЛЕНИЕ/НАПРАВЛЕНИЕ? |
| 01_company/glossary.md (или `speech-aliases.md`, если у клиента развёрнут отдельно) | КАК ЧИТАТЬ транскрипты | Новые имена, варианты произношения, ошибки транскрибатора, незнакомые термины/жаргон? Если руководитель поправил имя/термин при вычитке — кандидат сюда. Есть `speech-aliases.md` → имена и ASR-ошибки туда, термины остаются в glossary.md |

Проход по чеклисту — для КАЖДОГО затронутого подразделения/направления, не только при формально кросс-функциональных встречах (см. правило выше про явно адресованные задачи — оно уже требует открывать чужой узел и при однонодовой встрече). Одна сущность из выжимки может породить обновления в файлах разных единиц.

Затронутый узел = узел, чья любая сущность (задача, решение, факт, риск, открытый вопрос, метрика, запрос, цель, спецификация) фигурирует в выжимке — независимо от типа встречи по Шагу 1. Минимум — узлы, представленные участниками встречи; ДОБАВОЧНО — узел любого человека, которому в выжимке явно адресована задача/решение, даже если он не вёл встречу и не является объектом `{target_unit}`.

**Фаза A — recall-max, дубли разрешены.** Задача этого прохода — ничего не потерять. Сомневаешься, в каком из двух узлов каноническое место сущности — создай ОБЕ дельты с одним `entity_id`; выбор места размещения сделает Фаза B (канонизатор), не ты. Дубль на этой фазе — норма, потеря узла или сущности — ошибка. Дедуп-давления на этом шаге нет; не удаляй и не сливай дельты ради единственности.

**Задачи живого проекта → в его карточку (решает Фаза A, не канонизатор).** Если предмет задачи/риска/вопроса — инициатива с живой карточкой (Шаг 2 п.9), целевой файл дельты — `{node}/projects/{project}/02_active.md`; пометь дельту полем `card_target_file: {path}` с обоснованием одной строкой. Ты читал карточку — только у тебя есть контекст различить «задача — предмет инициативы» от «задача узла, упоминающая проект» (упоминание ≠ предмет; получатель/бенефициар ≠ предмет: «отчёт для узла X» не делает карточку X целевым файлом). Правила выбора места размещения:

1. **Кандидаты — карточки ВСЕХ затронутых узлов.** Сопоставляй предмет сущности со СПИСКОМ живых карточек из Гейта A (path + строка «о чём»), а не только с карточками узла предполагаемого владельца; полностью читай только карточки-кандидаты. Отверг карточку одного узла → обязан пройти остальной список. Узел карточки-кандидата по построению затронут: сущность о предмете инициативы делает её узел затронутым (правило затронутых узлов Гейта A).
2. **Owner-сигнал не выбирает место размещения.** «Это моя инициатива», «беру себе», «владелец цифры — я» выражается полем owner в тексте дельты и reference-проекцией в юнит-active владельца — каноническое место определяет ПРЕДМЕТ. Функциональный срез (продажи/маркетинг/найм) вокруг инициативы с живой карточкой — это работа ПО инициативе → canonical в карточку.
3. **Между карточками: меняемое > используемое.** Canonical — в карточку той инициативы, чьё состояние работа непосредственно меняет/продвигает; инициатива-канал или инструмент, который работа лишь использует, местом размещения не становится. Примеры: «продать Закупщика через дилеров, 8 сделок» продвигает запуск Закупщика (дилерская программа — используемый канал) → карточка Закупщика; «переработать дилерскую матрицу комиссий» меняет саму программу → её карточка. Фоллбэки: карточка меняемой инициативы мертва/архивна → юнит-файл узла (не чужая живая карточка); работа равносильно меняет две инициативы → canonical в одну + `placement_question`.
4. Правила выше сужают выбор, но не отменяют дубль-механизм: осталось сомнение между юнит-файлом и карточкой (или двумя карточками) — создай ОБЕ дельты с одним `entity_id`, Фаза B оформит выбор как `placement_question`.

При маршрутизации в карточку владельцу юнита оставь reference-проекцию в юнит-`02_active.md` (≤240, ссылка на карточку), чтобы задача не исчезла из поля зрения узла.

**Обратная проверка active обязательна.** Для каждого уже существующего пункта затронутых `02_active.md` отдельно проверь, нет ли в выжимке факта выполнения, отмены или закрытия вопроса. Найденное обязательно оформи отдельной дельтой удаления/переноса — ревью не восстановит пропущенную L2 дельту.

Каждую предлагаемую правку фиксируй во внутреннем формате — это служебный контракт дельты, обязательный везде, где дельта сериализуется (ревью, машинный вывод, структурированный выход); согласующему служебные поля не показываются:

- `id` · `target_file` · `operation` (`add|update|delete|move|merge|create`) · `proposed_text` · `source_evidence` (точная ссылка/цитата из выжимки либо явная правка руководителя) — как раньше;
- `owner` — владелец для task/consequence-дельт (валидатор требует его у consequence — B4);
- `canonical_external` — пометка reference-дельты, чьё каноническое место уже существует в файле вне этого прогона (см. Шаг 3.4);
- `entity_id` — id сущности из ростера Гейта A. Обязателен для всех дельт, кроме записей хроники (`04_progress.md`) и глоссария;
- `entity_type` — тип из ростера (`task|decision|fact|risk|question|metric|observation|term|protocol`); дельта `protocol` (E00) — вне ролевой единственности, `role` не заполняется;
- `spec_id` — только для атомарной нарративной спецификации (архитектура, набор опор): все дельты одного `spec_id` — один связный блок в ОДНОМ файле, не дробить;
- `role` — `canonical` (единственное каноническое место сущности) · `reference` (проекция/упоминание со ссылкой на каноническую запись: кросс-ссылка, строка в overview) · `consequence` (реальная производная задача с СОБСТВЕННЫМ owner и действием, не пересказ исходной сущности). На Фазе A роль предварительная, финальную назначает Фаза B. НЕ заполняется для дельт хроники (`04_progress`), глоссария и team-файлов (`01_company/02_team/`) — они вне единственности;
- `section` — `recommended | doubtful`;
- `card_target_file` — путь живой карточки проекта, если предмет дельты — её инициатива (ставит только Фаза A, с обоснованием одной строкой);
- `placement_question` — короткий вопрос согласующему о выборе между легитимными местами размещения одного типа (ставят Фаза B или координатор ревью; см. doubt-политику). Вопрос о размещении существует ТОЛЬКО как это поле: сомнение, изложенное в свободном тексте или обосновании без заполнения поля, невидимо согласующему и валидатору — это нарушение процедуры;
- `doubt_reason` — ОБЯЗАТЕЛЕН для каждой doubtful-дельты: `dispute` (спор об узле/факте/антипаттерн размещения) · `unresolved` (не починено за cap валидатора).

## Шаг 3.2: Code-валидатор покрытия (Фаза A → проверка)

Собери JSON `{meeting_nodes, entities, deltas, protocol_required, protocol_path}` (ростер, списки и meta протокола из Гейта A, дельты по контракту выше) и прогони валидатор — скрипт `validate_deltas.py` лежит в одном каталоге с этим файлом; вызывай его по фактическому пути установки скилла.

**Состав пакета:** пакет валидатора = ростер сущностей + ВСЕ дельты ОБЕИХ секций (`recommended` И `doubtful`) + meeting_nodes + meta протокола (`protocol_required`, `protocol_path` из Гейта A п.0) — на каждом вызове, на всех фазах. Пакет только из recommended — нарушение процедуры: инварианты doubt видят лишь то, что в пакете. Вызов безусловен: пустой recommended (rec=0) не освобождает — валидатор проверяет видимость каждой write/unclear-сущности в doubtful; дельты-хроники затронутых узлов при этом существуют всегда, фиктивные дельты для прохождения не нужны. **Пакет не пересказывается в тексте до heredoc:** не выписывай дельты/JSON в обычный вывод перед вызовом — собирай payload сразу внутри heredoc вызова валидатора.

**Одноузловой путь:** отдельный coverage-вызов на этом шаге НЕ выполняется — Шаги 3.2 и 3.4 объединяются в один вызов `--phase both` ПОСЛЕ инлайн-канонизации (см. Шаг 3.3); до канонизации `both` не вызывается.

```bash
python3 <каталог скилла meeting-analysis>/validate_deltas.py --phase coverage <<'VDEOF'
{ ...JSON... }
VDEOF
```

Валидатор проверяет: у каждой сущности есть disposition; у каждой `write`-сущности ≥1 дельта; у каждого затронутого узла ≥1 дельта; у каждой дельты есть `entity_id` из ростера.

**Дисциплина вызова (cap фазы — 2 вызова).** Вызывай валидатор ОДИН раз на ПОЛНОМ пакете дельт по итогам прохода — не валидируй инкременты, отдельные дельты или «на всякий случай». Нарушения → дособери недостающее и прогони второй (последний) раз. Непочиненное за 2 вызова — сущность/узел в «Сомневаюсь» с пометкой `doubt_reason: unresolved`, НЕ тихий пропуск.

## Шаг 3.3: Фаза B — канонизатор (один субагент; одноузловая встреча — инлайн)

**Одноузловая встреча — канонизация инлайн, без субагента (одноузловой путь).** Если затронутый узел после Гейта A и Фазы A ровно один (правило явно адресованных задач учтено: кросс-поручение делает встречу двухузловой, и этот шорткат не применяется), субагента НЕ запускай — выполни канонизацию сам, строго по этому же разделу: роли по таблице размещения, уважение `card_target_file`, дедуп внутри узла, `dropped_nodes`. Пропускается только спавн субагента — сама канонизация не пропускается никогда. Инлайн-канонизация работает по уже собранным дельтам Фазы A: файлы узла повторно НЕ перечитываются.

**Вызовы валидатора на одноузловом пути.** После инлайн-канонизации Шаги 3.2 и 3.4 объединяются в ОДИН вызов `--phase both` на полном пакете (обе секции + meta протокола + `phase_a_nodes`): `both` гоняет инварианты обеих фаз (ошибки несут префикс `[coverage]`/`[final]`) и засчитывается контрактом и как coverage, и как final. До канонизации `both` не вызывается. При нарушениях: `[coverage]`-нарушение (полнота) → вернись к сборке дельт, переканонизуй затронутое и повтори `both`; `[final]`-нарушение → почини канонизацию и повтори (cap — 2 вызова, как на Шагах 3.2/3.4; непочиненное → doubtful с `doubt_reason: unresolved`). Вызов после ревью (Шаг 3.5) остаётся обязательным и на одноузловом пути.

Иначе — запусти ОДНОГО субагента-канонизатора (синхронно, `foreground`). Пакет — ТОЛЬКО:

1. ростер сущностей + JSON дельт Фазы A (после Шага 3.2);
2. список затронутых узлов + owner-map из Гейта A и одна строка на узел об уровне (узел / группировка / компания) + список живых карточек проектов (path + строка «о чём») — узкий контекст не значит пустой: без owner-map, уровней и карточек канонизатор выбирает место размещения вслепую;
3. принятая выжимка — как справочный источник для спорной атрибуции owner/контура;
4. таблица размещения (ниже) + правила ролей из контракта дельты;
5. правило маршрутизации «по содержанию, не по роли» (см. Правила маршрутизации).

ЗАПРЕЩЕНО подавать канонизатору транскрипт и файлы узлов — узкий свежий контекст без coverage-давления обязателен, в этом смысл фазы.

Задача канонизатора: для каждого `entity_id` выбрать РОВНО ОДНУ `canonical`-дельту по таблице размещения; каждое прочее вхождение либо перевести в `reference` (короткая проекция/ссылка на каноническую запись, ≤240 символов; создаётся только там, где узлу нужна эта связь для работы — не «упоминание ради упоминания» и не копия текста сущности), либо в `consequence` (только если в дельте уже есть собственный owner и действие, отличное от пересказа исходной сущности — иначе это не consequence), либо в `doubtful`. Канонизатору запрещено: добавлять новые сущности и дельты, менять фактическое содержание canonical-дельт, тихо удалять дельты и узлы. Разрешено: (а) объединить две записи ростера, которые описывают одну и ту же сущность (дробление Фазы A): дельты переходят на выжившую сущность, поглощённая запись ростера остаётся в пакете с пометкой `merged_into: <id выжившей>` (валидатор освобождает её от требования дельт); (б) при смене канонического места адаптировать формулировку под целевой файл, сохраняя факт без искажения; (в) разрешить сомнение unclear-сущности в уверенно выбранное место — с пометкой `resolved_from_unclear: <причина>` в ростере.

**Снятие ложного узла.** Узел, попавший в покрытие Фазы A по ошибке (мимолётное упоминание чужой метрики/риска без новой информации и без действия этого узла), канонизатор снимает ЯВНО: узел в `dropped_nodes` с причиной, все его дельты → `doubtful` (согласующий видит снятие, ничего не исчезает молча). Настоящую копию сущности так снимать нельзя — только заменять ссылкой/следствием.

Возвращает тот же JSON с финальными `role`/`section` (+ `dropped_nodes`, если есть).

### Таблица размещения (тип × уровень → canonical)

| Тип | Уровень / условие | Канонический файл |
|---|---|---|
| task / risk / question — предмет живой инициативы с карточкой (`card_target_file` Фазы A) | узел инициативы | `{node}/projects/{project}/02_active.md` — пометку `card_target_file` не пересматривай из узкого контекста; несогласие оформляй `placement_question` |
| decision | компания | `01_company/05_decisions.md` |
| decision | узел / группировка | `{node}/05_decisions.md` / `{parent}/05_decisions.md` |
| decision | личное решение CEO | `00_ceo/04_decisions.md` |
| task — в работе сейчас | узел контура содержания задачи | `{node}/02_active.md` |
| task — не сейчас | узел | `{node}/03_backlog.md` |
| risk / question | узел, чью зону задевает | `{node}/02_active.md` |
| fact устойчивый | узел | `{node}/01_overview.md` (или metrics-файл клиента) |
| observation о человеке | — | `01_company/02_team/{person}.md` |
| term / ASR | — | `glossary.md` / `speech-aliases.md` |
| хроника встречи | каждый затронутый узел | `{node}/04_progress.md` — вне единственности |
| protocol (`E00`, протокол встречи) | место протоколов по Гейту A п.0 | `<protocol_path>/<дата>_<slug>.md` — вне ролевой единственности (exempt), создаётся только при `protocol_required: true` |

Решение (`decision`) НЕ получает каноническое место в `02_active.md`: работа, которую решение порождает, — это либо отдельная task-сущность ростера со своим каноническим местом, либо `consequence` с owner.

### Doubt-политика (что в «Сомневаюсь», а что — вопрос о размещении)

- **В doubtful, `doubt_reason: dispute`:** спор о САМОМ узле (нужен ли узел этой встрече); спор о факте, формулировке или атрибуции сущности; антипаттерн размещения (решение в active, задача в decisions, хроника вне progress) — такая дельта в recommended не остаётся никогда.
- **В doubtful, `doubt_reason: unresolved`:** нарушения валидатора, не починенные за cap вызовов.
- **НЕ doubtful:** выбор между легитимными местами размещения ОДНОГО типа внутри согласованного узла (юнит-`02_active` vs карточка проекта; active vs backlog по срочности). Дельта остаётся `canonical` в recommended с полем `placement_question` — согласующий видит вопрос в сводке Шага 4 и решает без потери дельты.

## Шаг 3.4: Code-валидатор финала (Фаза B → проверка)

```bash
python3 <каталог скилла meeting-analysis>/validate_deltas.py --phase final <<'VDEOF'
{ ...JSON с phase_a_nodes... }
VDEOF
```

`phase_a_nodes` — точный список узлов, получивших ≥1 дельту (любой секции) по итогам Фазы A после Шага 3.2; по нему валидатор ловит тихое сужение множества узлов канонизатором (B3). Узел записывается тем же идентификатором, что и в `meeting_nodes`.

Состав пакета — тот же, что на Шаге 3.2 (ростер + ОБЕ секции целиком + meta протокола; финальный пакет без `entities` — нарушение E1), плюс `phase_a_nodes`. На phase `final`/`both` поле `protocol_required` ОБЯЗАТЕЛЬНО: его отсутствие — нарушение `S10_meta_missing`. Вызов безусловен, включая rec=0. **Одноузловой путь:** отдельный вызов этого шага объединён с Шагом 3.2 в `both`-вызов (см. Шаг 3.3); после ревью вызов выполняется как обычно. инварианты размещения (единственность, антипаттерны, длина reference, owner у consequence) применяются к recommended-дельтам; doubtful — легитимное место альтернатив и спорных вариантов размещения, ждущих решения согласующего, но каждая doubtful-дельта обязана нести `doubt_reason`, а каждая write/unclear-сущность — быть видимой в пакете.

Валидатор проверяет: ОДНО каноническое место на сущность суммарно по core-файлам (active/backlog/decisions/overview — проекция в другой класс это reference, не второй canonical); решение без canonical в active; множество recommended-узлов не сузилось против Фазы A (снятый узел — только через `dropped_nodes` с причиной и doubtful-дельтами); consequence имеет owner; reference ≤240 символов и указывает на canonical этой сущности в наборе (если каноническое место сущности уже существует в файле вне этого прогона — пометь дельту `canonical_external: true`); `spec_id` не раздроблен по файлам; `placement_question` стоит только на canonical-дельте в recommended; дельта с `card_target_file`, чей целевой файл не совпадает с пометкой, несёт `placement_question`; протокол встречи (S10): при `protocol_required: true` в recommended есть create-дельта протокола под `protocol_path` с `proposed_text` ≥ 200 символов (санитарный минимум; doubtful не применяется apply и не считается), при `protocol_required: false` дельта под `protocol_path` даёт warning возможного дубля; протокол — контейнер (S11): дельта под `protocol_path` обязана иметь `entity_type: protocol`, а protocol-дельты не считаются покрытием сущностей E01+ (сущность «только в протоколе» = пропуск покрытия A2/S8).

**Дисциплина вызова (cap фазы — 2 вызова):** один вызов на полном финальном пакете; нарушения → верни канонизатору ОДИН раз со списком нарушений и прогони второй (последний) раз; повторное нарушение → спорные дельты в «Сомневаюсь» с `doubt_reason: unresolved`, не тихое удаление.

## Шаг 3.5: Ревью предлагаемых правок

Обязательный шаг и при самостоятельном запуске (без оркестратора): собранный список обновлений вместе с принятой выжимкой проходит стадию ревью — см. L2-review-procedure.md.

После ревью прогони валидатор ещё раз (`--phase final`; на одноузловом пути допустим и `--phase both`) — минимум ОДИН обязательный вызов, ВСЕГДА, в том числе когда кажется, что ревью ничего не меняло и когда recommended пуст: per-file ревью не видит межфайловую картину и могло создать пропуск или вернуть дубль. Вызов нашёл нарушения → почини и прогони повторно (cap — 2 вызова, как на Шагах 3.2/3.4; непочиненное → doubtful с `doubt_reason: unresolved`). Дельты, переведённые ревью в doubtful, к этому моменту обязаны нести `doubt_reason` (маппинг вердиктов — в L2-review-procedure.md); пакет — обе секции целиком (+ meta протокола).

**Итог по вызовам валидатора (минимум, безусловный — контракт):** валидных вызовов `coverage` ≥1 и `final` ≥2, где вызов `--phase both` засчитывается И в coverage, И в final, а валидный вызов = payload распарсен (exit ≠ 2; exit 1 — валидный вызов, нарушения чини и повторяй). Полный путь: coverage (Шаг 3.2) + final (Шаг 3.4) + final после ревью (этот шаг). Одноузловой путь: both после инлайн-канонизации (Шаг 3.3) + final|both после ревью. Ни один вызов не пропускается ни при rec=0, ни при одноузловой встрече. Контракт задекларирован машинно в `validation-contract.json` (тот же каталог, что и валидатор) — среда исполнения вправе блокировать завершение работы, пока контракт не выполнен.

## Шаг 4: Покажи обновления руководителю

Если есть дельты с `placement_question` — начни вывод сводкой: «❓ вопросы о размещении: N — проверь перед ОК», затем перечисли эти дельты отдельным подсписком (вопрос + предлагаемое место + альтернатива). Только после этого — основные разделы.

Покажи два компактных раздела по формату L2-review-procedure.md: «Советую обновить» и «Сомневаюсь», внутри сгруппируй итоговые дельты по файлам. Не показывай служебные ID, значения вердиктов и рассуждения.

Применяй ТОЛЬКО после ОК руководителя. Если руководитель отклоняет обновление — не спорь, оставь в выжимке как страховку.

## Правила маршрутизации

**Маршрут по содержанию, не по роли.** Узел-владелец сущности определяется её содержанием и контуром ответственности за неё, а НЕ должностью/ролью человека. Двойная роль владельца (напр. и.о. руководителя одного контура + лид другого) не решает маршрут: задача про продукт остаётся в продуктовом узле, даже если её owner формально числится и в другом контуре. Роль — вспомогательный сигнал, содержание — решающий.

**Один аспект — одно место.** Одно событие может обновить несколько файлов, если затрагивает разные аспекты. "Решили сменить лидера направления" → 01_overview (структура) + `01_company/02_team/{person}.md` (роль) + 02_active (задачи по передаче). Разные файлы отвечают на разные вопросы — это не дублирование.

**Страховка.** Не можешь однозначно маршрутизировать — оставь в выжимке (`summary_only`). Действует только на Гейте A, при назначении disposition; после Гейта A сомнение оформляется doubtful-дельтой с `doubt_reason`, не тихим отказом от записи. Лучше не разложить, чем разложить неправильно.

**Антипаттерны:**
- Проблемы/задачи в overview → active
- Хроника в overview → progress
- Решение без why/альтернатив → не в decisions; дособери контекст или оставь в выжимке
- Коучинг в `{target_unit}/` → `01_company/02_team/{person}.md`
- Операционные выборы в decisions → остаются в выжимке
- Company-wide решения в `{target_unit}/05_decisions.md` → `01_company/05_decisions.md`
- Личные решения CEO (принципы, стиль) в `01_company/05_decisions.md` → `00_ceo/04_decisions.md`

**Даты-источники.** Изменчивые данные (цифры, статусы, решения) получают дату в строке `(YYYY-MM-DD)`. Стабильные факты остаются без дат.

## Форматы записей в log-файлах

**04_progress.md** — новая запись вставляется **в начало файла** (сразу после H1/аннотации, перед существующими записями), свежее сверху:
```
## YYYY-MM-DD: {тема встречи}

**Участники:** {кто был}
**Ключевое:** {2-4 строки — что обсудили, что решили, что сдвинулось}
**Следующий шаг:** {главное действие}
```

**05_decisions.md / 01_company/05_decisions.md / 00_ceo/04_decisions.md** — новое решение тоже в начало файла, свежее сверху. Если новое решение отменяет/заменяет более раннюю запись — не переписывай старую: пометь её `Статус: Superseded` со ссылкой на новую:
```
## YYYY-MM-DD: Название решения
**Статус:** Актуально
**Решение:** Что решили
**Почему:** Контекст
**Альтернатива:** Что рассматривали и отвергли
```
Отметка устаревшего решения (правь существующую запись на месте, не удаляй):
```
**Статус:** Superseded → см. запись «YYYY-MM-DD: Название нового решения» выше в этом файле
```

**01_company/02_team/{person}.md → Коучинг-лог:**
```
### YYYY-MM-DD
{Наблюдение: что заметили, как проявилось, контекст}
```
