# Send Telegram

Канал доставки в Telegram (Bot API). Отправляет сообщение получателю, настроенному в `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`). Общий ресурс: другие скиллы делегируют доставку **агенту** — «отправить через скилл send-telegram», — а транспорт выбирается правилом ниже. Прямой запуск скриптов — путь для контуров, где агента нет.

## Сначала — чем слать

❗️ **Есть MCP-сервер `svaib` — отправляй его инструментом `send_telegram_message`, скрипты этого скилла не нужны.** Проверяется наличием инструмента в сессии; гадать не надо, он либо есть, либо нет.

Почему приоритет именно такой: доставка через шлюз попадает в журнал с исходом, получает ключ идемпотентности (повтор безопасен), ограничена правами твоего ключа и видна в аудите поимённо. Прямой путь этого не даёт ничего: ни журнала, ни защиты от дубля, ни ответа на вопрос «кто отправил».

**Адресатов спрашивай у шлюза — инструментом `list_contacts`.** Он возвращает доступные тебе чаты и личные адреса с назначением и состоянием бота; для отправки берёшь оттуда `alias` (или `binding_id`). Зови его перед отправкой всякий раз, когда получатель назван словами: перечень алиасов в схеме `send_telegram_message` кэшируется клиентом и устаревает, а `list_contacts` читается живьём. Локальный реестр `recipients.yaml` к этому маршруту отношения не имеет и не читается: два реестра адресатов, которые «почти совпадают», однажды разъедутся, и ценой будет сообщение, ушедшее не тому.

**Инструмента нет — работают скрипты ниже**, и они бьют в Bot API напрямую. Второго пути к шлюзу у скриптов нет намеренно: доставка через шлюз делается инструментом MCP, а «ещё один способ попасть туда же» пришлось бы объяснять каждый раз, когда неясно, чем ушло сообщение. Скрипты остаются для контуров, где шлюза не существует, — клиентские установки и аварийная процедура.

Пути ниже — от корня рабочего пространства: рабочая директория не там (например, в Cowork) — сначала `cd` в корень.

Что настроено на этой машине — покажет:

```bash
bash .claude/skills/send-telegram/scripts/send_telegram.sh --check
```

Команда ничего не отправляет: печатает состояние кредов (факт наличия, не значения) и перечень известных адресатов.

Два скрипта в `scripts/` этого скилла:
- **`send_telegram.sh`** — plain (по умолчанию): markdown → HTML → `sendMessage` (parse_mode=HTML), нарезка по строкам ≤4096.
- **`send_telegram_rich.sh`** — rich (структурный): markdown → `sendRichMessage` (Bot API 10.1), при отказе API фолбэк на plain.

## The Iron Law

**Один шаг вместо двух вопросов.** Вопрос «показать превью или сразу отправить?» не задаётся никогда: покажи текст сообщения сразу и одним вопросом уточни недостающее — получателя, если он не назван, или подтверждение, если назван не адресат по умолчанию. Ответ с адресатом — и есть подтверждение отправки. Получатель назван в запросе (или вызывающим скиллом), а текст уже показан — не переспрашивай ничего, отправляй.

**Плоский или rich.** Структурный вывод (таблицы, ≥2 секции, дайджест) → rich-режим (см. [«Rich-режим»](#rich-режим-sendrichmessage-bot-api-101) ниже). Короткое сообщение в 2-3 строки → обычный режим. **Исключение:** если текст уже свёрстан эмодзи-строками (`⭕️`/`✅`) вместо `-` (например сводка встречи из meeting-analysis) — он предформатирован под plain, отправляй plain. В rich пункты списка обязаны начинаться с `-`, иначе строки схлопнутся в абзац (см. правило 3 в «Rich-режим»).

## Кому отправляем

> **Сначала проверь, есть ли рядом со скиллом `scripts/recipients.py`.** Нет файла — реестра адресатов в этой поставке нет: доступен только адресат по умолчанию, `--to` не сработает, и всё ниже не применяется. Скажи об этом прямо, не пытайся обойти. Так же читай упоминание нескольких получателей в описании скилла: оно про возможность канала, а не про гарантию, что она включена здесь.

По умолчанию сообщение уходит в чат из `TELEGRAM_CHAT_ID`. Если пользователь **назвал получателя** — «отправь руководителю», «скинь в общий чат», «пошли обоим» — адресаты указываются по имени:

```bash
bash .claude/skills/send-telegram/scripts/send_telegram.sh --to <алиас>[,<алиас>] "ТЕКСТ"
```

Имена (алиасы) живут в реестре `recipients.yaml`; посмотреть доступные — `python3 .claude/skills/send-telegram/scripts/recipients.py --list`. Реестр хранит **имена ключей** окружения, а не номера чатов.

**Правила, которые нельзя нарушать:**

| Ситуация | Что делать |
|---|---|
| Пользователь назвал адресата, которого нет в реестре | Показать список известных и **спросить**. Не отправлять «пока себе», не подбирать похожего: ошибка адресации — это чужие глаза на содержимом, а не неудобство |
| Отправка не адресату по умолчанию | Рядом с показанным текстом назвать **кому именно** уходит сообщение и получить подтверждение. Не переспрашивать, если пользователь сам назвал получателя в запросе |
| Отправка в групповой чат | Помнить и при необходимости сказать вслух: сообщение увидят **все участники чата**. Поле `members` в реестре — справочное, реальный состав группы может быть шире |
| Часть адресатов не получила | Скрипт вернёт сводку по каждому. Передать её пользователю как есть — там различаются «не доставлено» и «исход неизвестен» |
| Исход неизвестен (код возврата 2) | **Не отправлять повторно** без проверки чата: сообщение могло дойти, и повтор его продублирует |

## Алгоритм

### 1. Получить текст

Текст сообщения — из аргументов (`$ARGUMENTS`) или из контекста разговора. Если неясно что отправлять — спроси.

### 2. Показать текст и уточнить получателя

Покажи текст сообщения (если он ещё не на экране — вызывающий скилл мог показать его сам). Вопросов о превью нет. Получатель не назван — спроси одним вопросом: «Кому отправить?». Назван — ответ пользователя с адресатом или его «отправляй» и есть подтверждение; после правок текста — показать исправленный и к шагу 3.

### 3. Адаптировать формат под Telegram (только обычный режим)

**Сначала развилка:** если выбран **rich-режим** — этот шаг ПРОПУСТИ (rich принимает markdown как есть, см. [«Rich-режим»](#rich-режим-sendrichmessage-bot-api-101)). Адаптация ниже — только для обычного режима.

Перед отправкой — привести текст к формату, который Telegram отобразит корректно:
- `## заголовок` → `📋 **заголовок**` (Telegram не поддерживает markdown-заголовки)
- `- [x] текст` → `- ✅ текст` (скрипт убирает только `[ ]`, не `[x]`)
- `---` → убрать (скрипт убирает, но лучше не полагаться)

### 4. Отправить (обычный режим)

```bash
bash .claude/skills/send-telegram/scripts/send_telegram.sh "ТЕКСТ_СООБЩЕНИЯ"
```

Проверить: ответ содержит `"ok":true`. Скрипт возвращает **ненулевой exit** при недоставке любого чанка. (Rich-режим отправляется скриптом `scripts/send_telegram_rich.sh` — см. [«Rich-режим»](#rich-режим-sendrichmessage-bot-api-101).)

### 5. Подтвердить

Сообщить результат:
- Успех: «Отправлено в Telegram»
- Ошибка: показать ответ API

## Edge Cases

| Ситуация | Действие |
|----------|----------|
| `.env` не найден | Оба скрипта ищут `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` одинаково: env → `./.env` → git-root/.env. Уже заданная переменная окружения побеждает файл — покаждой отдельно, включая `TG_CHAT_*`. Если нигде нет — сообщить: «.env с TELEGRAM_BOT_TOKEN не найден» |
| Текст >4096 символов | Скрипт режет по строкам (теги не рвутся). Предупредить: «Длинное сообщение, Telegram разобьёт на части» |
| Rich: лимиты sendRichMessage | До 32768 символов, 500 блоков, 16 уровней вложенности, 50 медиа, 20 колонок таблицы. Больше — разбей на несколько сообщений по секциям |
| curl вернул ошибку | Скрипт вернёт ненулевой exit. Если 403 — напомнить про Allow network egress (Cowork) |
| Пустой текст | Скрипт вернёт ошибку. Спросить что отправлять |
| Реестр адресатов не найден | `--to` недоступен. Сказать: «реестра адресатов нет, могу отправить только в чат по умолчанию» |
| Неизвестный алиас в `--to` | Ни одному адресату **ничего не ушло** — список разрешается целиком и до отправки. Показать известные и спросить |
| Ключ `TG_CHAT_*` не задан в окружении | То же: не отправлено никому. Назвать недостающий ключ, не подставлять другой |
| Реестр от чужого бота | Отказ до отправки: `chat_id` зависит от пары «бот + получатель», у другого бота те же номера означают другие чаты |
| «bot is not a member» / «not enough rights» | Бота нет в группе или у него нет права писать. Добавить бота в чат; для группы у @BotFather может понадобиться `/setprivacy → Disable` |
| Частичный отказ (код 1) | Кому доставили — доставили, откатить в Telegram нельзя. Показать сводку; повторять только тем, у кого ❌ |
| Исход неизвестен (код 2) | Проверить чат глазами до любого повтора |

## Пример

**Запрос:** «Скинь в тг список задач на завтра»
1. Claude формирует текст из контекста разговора и показывает его
2. Получатель не назван → «Кому отправить?»
3. Пользователь: «мне» → `bash .claude/skills/send-telegram/scripts/send_telegram.sh "Задачи на завтра: ..."`
4. Ответ API `"ok":true` → «Отправлено в Telegram»

**Запрос:** «отправь <имя получателя>: Встреча перенесена на 15:00»
1. Текст и получатель названы → показать текст и отправить без вопросов
2. `bash .claude/skills/send-telegram/scripts/send_telegram.sh --to <алиас> "Встреча перенесена на 15:00"`
3. «Отправлено в Telegram»

## Форматирование

### Структура сообщения (обязательно)

**Никогда не отправляй "портянку"** — сплошной текст без структуры. Любое сообщение длиннее 2-3 строк должно быть структурировано.

**Принципы:**
- Приветствие — отдельная строка
- Суть (о чём сообщение) — отдельная строка
- Каждый смысловой блок — под жирным подзаголовком, текст с новой строки
- Подпись — курсивом (`__текст__`), отделена пустой строкой

**Пример правильного сообщения:**

```
Привет!

Небольшое техническое обновление.
Исправлен баг в скилле обновления рабочих файлов.

**Что за скилл:**
обновляет рабочие файлы (overview, active, progress, team) после обработки встречи.

**Что исправлено:**
в секции «Ограничения» была битая ссылка на несуществующий файл. Удалена.

__— Claude, AI-ассистент__
```

**Антипаттерн (запрещено):**

```
Привет! Небольшое техническое обновление. Исправил баг в скилле обновления рабочих файлов — это скилл, который обновляет твои рабочие файлы (overview, active, progress, team и т.д.) после обработки встречи. В секции «Ограничения» была строка...
```

### Технические возможности скрипта

Скрипт конвертирует markdown → HTML (`parse_mode=HTML`):

| Приём | Что писать | Результат в Telegram |
|-------|-----------|---------------------|
| Жирный | `**текст**` | **текст** |
| Курсив | `__текст__` | __текст__ |
| Заголовок секции | `**Что сделано:**` | **Что сделано:** |
| Эмодзи-маркеры | `📌`, `✅`, `❗️`, `🔧` | Как есть |
| Список | `- Пункт` | - Пункт |
| Чекбокс | `- [ ] Пункт` | - Пункт (скрипт убирает `[ ]`) |
| Разделитель | `---` | Убирается (пустая строка) |

**Правило:** жирным — подзаголовки блоков. Курсивом — подпись. Эмодзи — по ситуации (не больше 2-3 на сообщение). Не перегружать.

> ⚠️ **Курсив — только для подписи, без подчёркиваний внутри.** Конвертер берёт `__текст__` шаблоном «между двумя парами подчёркиваний нет ни одного своего», поэтому `__send_telegram.sh --to <алиас>__` уйдёт сырым: имя файла содержит `_`. У жирного та же граница со звёздочкой. Точный шаблон требует чередования, которое есть в GNU sed и отсутствует в BSD sed на macOS, — то есть починка работала бы у нас и молча ломалась у клиента. Техническую строку оборачивать в курсив не нужно.

## Rich-режим (sendRichMessage, Bot API 10.1)

Для **структурного** вывода — отдельный скрипт. Бот шлёт document-grade сообщение прямо в чат. Контент — GFM-подобный markdown.

**Когда:** читатель — человек и структура реально помогает (таблица, код, ≥2 секции). Короткие сообщения в 2-3 строки — обычный режим, не rich.

**Как:**

```bash
bash .claude/skills/send-telegram/scripts/send_telegram_rich.sh "MARKDOWN"
```

Проверить ответ `"ok":true`. **Фолбэк** срабатывает только при **подтверждённом отказе API** (`ok:false`) — тогда скрипт шлёт обычным `send_telegram.sh`, и только тому адресату, у которого rich не прошёл: остальные уже получили своё, повторный веер продублировал бы им доставку. При сетевом timeout фолбэка НЕТ (исход неизвестен — чтобы не словить двойную доставку), скрипт вернёт ошибку. И фолбэк **теряет rich-форматирование**: таблицы / `<details>` / код уйдут сырой разметкой — это аварийная доставка текста, не замена rich.

### Проверенная палитра элементов

Всё ниже подтверждено на живом рендере (по `rich_message.blocks` в ответе API):

| Элемент | Синтаксис | Примечание |
|---|---|---|
| Заголовок | `## Текст` (число `#` → size 1–6) | |
| Разделитель | `---` | **зазоры между секциями — этим** |
| Таблица | GFM (пайпы + строка-разделитель) | |
| Код | fenced-блок с языком | подсветка синтаксиса |
| Чек-лист | `- [x]` / `- [ ]` | рендерит галочки |
| Сворачивающийся блок | `<details><summary>…</summary>…</details>` | raw-HTML внутри markdown работает |
| Формула | `$…$`, вкл. `\sqrt{}`, `\cdot` | |
| Картинка | `alt` | нужен публичный URL — см. ниже |
| Цитата | `> текст` | |

**Картинки — URL, доступный серверам Telegram по HTTP/HTTPS.** Telegram сам выкачивает картинку по ссылке (на практике кэширует к себе); локальный файл в markdown не вставить. Бери готовый публичный URL; если картинку нужно сначала где-то разместить — согласуй с пользователем, куда её выложить (запрос «отправь в телеграм» сам по себе прав на публикацию файлов не даёт).

### Три правила, которые легко нарушить (проверено)

1. **Зазоры между секциями — разделителем `---`, не пустыми строками.** Пустой блок с неразрывным пробелом (U+00A0) Telegram **схлопывает** (особенно рядом с заголовками) — секции слипаются. `---` — настоящий блок, не исчезает.
2. **Списки: вложение только «хвостом».** Плоские списки — ок. Вложенные буллеты — только под **последним** пунктом. Нельзя продолжать нумерацию после вложенного блока: «2 → вложенные → 3» ломает рендер (пункт 3 съезжает под вложение). Правильно: «1, 2, 3 → вложенные под 3».
3. **Пункты списка — только через `-`.** Строки без маркера (`⭕️ …`, голый текст) с одиночным переносом markdown схлопывает в один абзац (мягкий разрыв GFM). Каждый пункт обязан начинаться с `-`. Проверяй по `rich_message.blocks` в ответе API: каждый пункт — отдельный блок, а не склейка в один `paragraph`.

**Рендер зависит от клиента-получателя:** телефон — чисто, десктоп пока сыровато (фича от июня 2026). Фолбэк тут НЕ помогает — он только на ошибку API, а не на плохой рендер при `ok:true`.

## Скрипты

Оба принимают `[--to alias[,alias...]] [--] "ТЕКСТ"`. Без `--to` поведение прежнее и реестр не нужен. `--` завершает флаги — нужен, если текст начинается с дефиса.

Коды возврата различают **исход доставки** и **отказ до неё**:

| Код | Что случилось | Что делать |
|---|---|---|
| `0` | Доставлено всем | — |
| `1` | Подтверждённый отказ: Telegram разобрал запрос и отверг | Повтор безопасен — сообщение точно не дошло |
| `2` | **Исход неизвестен**: обрыв, 5xx, неразборный ответ | **Не повторять.** Сначала посмотреть чат: сообщение могло дойти |
| `3` | Не отправлено никому: ошибка вызова или предусловия | Починить конфигурацию и запустить заново |

Двойка важнее единицы: если у одного адресата отказ, а у другого неизвестность — вернётся `2`.

- **Реестр адресатов**: [scripts/recipients.py](scripts/recipients.py) — `--resolve` (алиасы → имена ключей), `--list`, `--validate [--strict]`. Значений chat_id не хранит и не печатает: их подставляет shell, у которого резолв `.env` уже есть.
- **Общая часть**: [scripts/_channel_common.sh](scripts/_channel_common.sh) — разбор аргументов, креды, разрешение адресатов. Подключается обоими скриптами, чтобы логика снова не разошлась.
- **Обычный** (по умолчанию): [scripts/send_telegram.sh](scripts/send_telegram.sh) — резолвит `.env` (env → pwd → git-root) → экранирует HTML → конвертирует markdown (`**` → `<b>`) → `sendMessage` (parse_mode=HTML) → режет по строкам ≤4096 → проверяет `ok` (ненулевой exit при недоставке). Конвертация и нарезка выполняются один раз на всех адресатов.
- **Rich** (структурный): [scripts/send_telegram_rich.sh](scripts/send_telegram_rich.sh) — резолвит креды тем же правилом, что обычный (env → pwd → git-root; в кластере креды приходят переменными, файла там нет) → markdown → `sendRichMessage` (Bot API 10.1) → фолбэк на обычный **только при подтверждённом отказе**: ответ 4xx. Ответ 5xx, неразборное тело при 200 и сетевой обрыв фолбэка не дают — исход неизвестен, и вторая отправка продублировала бы уже принятое сообщение.
