# Обновление досье контрагента по выжимке встречи

L2-надстройка над выжимкой встречи. Получает готовую выжимку, делает файл-центричный проход по досье контрагента, предлагает обновления исполнителю.

## Вход

1. **Выжимка** — готовый файл `_summary.md` (результат L1-пайплайна)
2. **Контекст от исполнителя** — ответ на вопрос: "Что за встреча? Кто контрагент? Кто участвовал?"

## Выход

Список обновлений по файлам. Каждое обновление: какой файл → что добавить/изменить → почему (ссылка на выжимку). Применяется ТОЛЬКО после ОК исполнителя.

## Область применения

Встречи с одним контрагентом (клиент, партнёр, подрядчик). Предполагает досье по стандартной структуре клиентского проекта (profile.md, company.md, 01_overview.md и т.д.).

Вне области применения этой версии: встречи с несколькими контрагентами одновременно, внутренние встречи (→ L2-procedure-scaffold-update.md).

---

## Шаг 1: Определи область обновления

По ответу исполнителя определи:
- `{project_dir}` — папка проекта контрагента (содержит profile.md, meetings/ и т.д.)
- Тип встречи (кикофф, регулярная, стратсессия и т.д.)

---

## Шаг 2: Собери контекст

1. Прочитай выжимку
2. Прочитай `README.md` досье, если есть, — карта файлов и маршруты записи
3. Прочитай файлы досье **которые существуют**: profile.md, company.md, 01_overview.md, 02_active.md, 03_backlog.md, delivery-status.md, setup.md, 05_decisions.md, 04_progress.md. Отсутствующий файл не читаем и не создаём «для полноты». `04_progress.md`/`05_decisions.md` разрослись → читай последние ~10-15 записей (свежее сверху, начало файла), не весь файл

---

## Шаг 3: Файл-центричный проход

### Iron Law обновления

После обновления — состояние проекта в файлах актуально. Выжимка остаётся как полная запись встречи. Не всё из выжимки должно попасть в файлы — это нормально.

### Принцип: выжимка щедрая, файлы досье строгие

Выжимка сохраняет всё (Iron Law L1). Файлы досье — только то, что имеет устойчивую ценность: стратегические решения, факты о бизнесе, задачи с `owner`, изменения в целях и структуре. Операционная мелочь, разовые реплики, бытовые просьбы остаются в выжимке и не попадают в файлы.

---

Пройди по каждому прочитанному файлу и спроси по его миссии: "нужно ли обновить этот файл с учётом новой информации из выжимки?"

**НЕ раскидывай сущности из выжимки по файлам.** Проверяй файлы — это принципиально другой алгоритм.

### Чеклист

| Файл | Миссия | Тест-вопрос |
|------|--------|-------------|
| profile.md | КТО этот человек | Узнали новое о человеке (стратегия, предпочтения, боли, принципы, язык)? Тест устойчивости (правило файла): останется верным через год? Событие-иллюстрация уже записанного — не добавлять (мысль есть, эпизод протухнет); наблюдение контрагента о других людях — не его принцип (если за ним его боль → «Боли», иначе остаётся в выжимке) |
| company.md | ГДЕ он работает | Новые факты о бизнесе (цифры, люди, оргструктура, стратегия компании)? Тест: останется при смене руководителя? |
| 01_overview.md | ЧТО мы делаем | Новые запросы на решения? Изменилась модель работы, метрики успеха, программа? |
| 05_decisions.md | ПОЧЕМУ так решили | Были стратегические решения? Тест: через 3 мес спросят "почему так?" — это ответ? Новое решение отменяет/заменяет прежнее → НЕ переписывай старую запись: пометь её `Статус: Superseded` со ссылкой на новую (формат ниже) |
| 02_active.md | ЧТО АКТУАЛЬНО сейчас, НЕ архив | Гейт: попадает только то, что в работе прямо сейчас — тест «исполнитель или контрагент вернётся к этому до следующей встречи». Сначала сопоставь новое с существующим — связанные пункты объединяй, не дублируй; задача, отменённая решением этой встречи, не остаётся и не возвращается. Новые задачи (по `owner`)? Открытые вопросы? Риски? Повестку следующей встречи НЕ вносить (производный нарратив координатора, не факт встречи) — в active только дата/статус следующей встречи, если прозвучали. **Симметрично удаляй неактуальное:** вопрос решён → убрать (решение → decisions); устаревшая повестка → убрать; задача выполнена → `[x]` и сразу удалить (хроника — в 04_progress) |
| 03_backlog.md | БУДУЩАЯ работа | Идея, гипотеза, ожидание или запрос контрагента — важные, но не проходят тест active (никто не вернётся к этому до следующей встречи)? Не дублируй ушедшее в 02_active |
| delivery-status.md | ЧТО РАЗВЁРНУТО у клиента | Изменился статус блока плана доставки (развёрнуто, принято, оплачено, граница блока)? |
| setup.md | КАК настроено | Изменилась конфигурация (инструмент, структура, настройки)? |
| 04_progress.md | КАК двигались | Дописать 2-4 строки о встрече (что сделано, ключевой сдвиг, обратная связь) — **в начало файла**, свежее сверху |

**Обратная проверка active обязательна.** Для каждого уже существующего пункта `02_active.md` отдельно проверь, нет ли в выжимке факта выполнения, отмены или закрытия вопроса. Найденное обязательно оформи отдельной дельтой удаления/переноса — ревью не восстановит пропущенную L2 дельту.

Перед ревью зафиксируй каждую предлагаемую правку во внутреннем формате: `id`, `target_file`, `operation` (`add|update|delete|move|merge|create`), `proposed_text`, `source_evidence` (точная ссылка/цитата из выжимки либо явная правка исполнителя при её согласовании, зафиксированная координатором). Это служебный контракт; ID согласующему не показывается.

## Шаг 3.5: Ревью предлагаемых правок

Обязательный шаг и при самостоятельном запуске (без оркестратора): собранный список обновлений вместе с принятой выжимкой проходит стадию ревью — см. L2-review-procedure.md.

## Шаг 4: Покажи обновления исполнителю

Покажи два компактных раздела по формату L2-review-procedure.md: «Советую обновить» и «Сомневаюсь», внутри сгруппируй итоговые дельты по файлам. Не показывай служебные ID, значения вердиктов и рассуждения.

Применяй ТОЛЬКО после ОК исполнителя. Если исполнитель отклоняет обновление — не спорь, оставь в выжимке как страховку.

## Правила маршрутизации

**Один аспект — одно место.** Одно событие может обновить несколько файлов, если затрагивает разные аспекты. "Перешёл на новый инструмент" → setup (конфигурация) + profile (опыт человека). Разные файлы отвечают на разные вопросы — это не дублирование.

**Страховка.** Не можешь однозначно маршрутизировать — оставь в выжимке. Лучше не разложить, чем разложить неправильно.

**Антипаттерны:**
- Конфигурацию (инструмент, настройка) в profile → setup
- Прогресс ("разобрал 50 файлов") в profile/company → 04_progress или протокол
- Задачи в 01_overview → 02_active
- Решения без контекста в 01_overview → 05_decisions (нужны why + альтернативы)
- Конкретные события/даты в "Кратко" → 04_progress
- Нет данных — не додумывать. Если факт не подтверждён источником (выжимка, транскрипт) — спрашивать исполнителя
- Операционный шум в справочные файлы. company.md = ключевые люди и их роли, НЕ "[сотрудник] попросил фидбэк". Тест: поможет ли это при подготовке к следующей встрече через месяц? Нет → не записывать
- Переписывание принятого решения задним числом → только Superseded-пометка статуса, тело старой записи не редактировать
- Статус доставки/оплаты блока в 01_overview или 02_active → delivery-status.md

**Даты-источники.** Изменчивые данные (цифры, статусы, решения, люди) получают дату в строке `(YYYY-MM-DD)`. Стабильные факты остаются без дат.

## Форматы записей в log-файлах

**04_progress.md** — новая запись **в начало файла** (сразу после H1/аннотации), свежее сверху:
```
## Встреча N (YYYY-MM-DD) — тема
{2-4 строки: что сделано, ключевой сдвиг, обратная связь}
```

**05_decisions.md** — новое решение тоже в начало файла, свежее сверху. Новое решение отменяет/заменяет более раннюю запись → не переписывай старую: пометь её `Статус: Superseded` со ссылкой на новую:
```
## YYYY-MM-DD: Название решения
**Статус:** Актуально
**Решение:** Что решили
**Почему:** Контекст
**Альтернатива:** Что рассматривали и отвергли
```
Отметка устаревшего решения (правь только строку статуса существующей записи, тело не трогай; частичное устаревание — «Superseded в части … → решение YYYY-MM-DD», остальное явно оставить актуальным):
```
**Статус:** Superseded → см. запись «YYYY-MM-DD: Название нового решения» выше в этом файле
```
