# Plugin — деплоимый пакет Second Value AI Brain

## Кратко

Собранный пакет для клиента: наш продуктовый слой поверх scaffold-структуры. Plugin содержит методологию в исполняемом формате и доставляется через внешний runtime / AI-host.

**Статус:** Skills — уже реальные, работающие скиллы (см. [skills/README.md](skills/README.md)). Hooks — три хука под Claude Code (идентичность, ловля отложенных действий, Stop-backstop гейтов meeting-analysis); на Cowork хуков нет — enforcement-слой там выпадает. Agents — по-прежнему скелет, наполнение после обкатки методологии на первых клиентах.

## Компоненты

| Что | Папка | Что делает                                                                                                       |
|-----|-------|------------------------------------------------------------------------------------------------------------------|
| Skills | `skills/` | Методология в исполняемом формате:  channels/telegram (доставка), scaffold (в разработке), email-assistant, meeting-analysis, metrics-analysis |
| Hooks | `hooks/` | Детерминированные правила сессии (только Claude Code): личность пользователя, запрет отложенных действий, Stop-backstop гейтов meeting-analysis |
| Agents | `agents/` | Скелет. Автоматизация: диспетчер задач, обновление документации                                                  |

## Как пакет попадает к клиенту

Собирается сборщиком — dev/plugin-builder/. Он берёт из этой папки то, что перечислено в профиле клиента, чинит пути под установку и проверяет результат. Сам сборщик — инженерная оснастка, частью продукта не является.

Состав под конкретного клиента задаётся профилем; профили живут рядом с клиентом, в `clients/`.

## Связь с моделью подписки

Плагин не хранит данные клиента. Данные — у клиента (в scaffold-структуре). Плагин — интеллектуальный слой поверх.

## Граница с runtime

Plugin и runtime — не одно и то же.

- **Plugin** — наш слой: skills, agents, hooks, то есть методология и автоматизация.
- **Runtime** — внешний слой доставки: AI-host, scheduling, orchestration, интерфейсные коннекторы.

Мы не считаем runtime частью ядра продукта. Текущее решение по этой границе зафиксировано в [../04_decisions.md](../04_decisions.md) (пункт 1 — Выбор runtime).

### Что это значит на практике

- plugin должен оставаться максимально runtime-agnostic;
- нельзя описывать plugin как артефакт только для `Claude Code / Cowork`, если это не часть самой сути;
- конкретный runtime может меняться без пересборки продуктовой логики;
- текущие пилотные кандидаты — Claude Code Scheduled Tasks (приоритетный, cloud-режим) и `HKUDS/nanobot` (запасной), детали в [../04_decisions.md](../04_decisions.md) (пункт 1 — Выбор runtime); plugin не должен быть описан как «nanobot-плагин» или «Scheduled-Tasks-плагин».

## Delivery-модель

Текущая целевая схема:

```
scaffold (данные клиента)
    +
plugin (наш продуктовый слой)
    +
runtime / host (внешняя доставка)
    =
рабочий Second Value AI Brain у клиента
```

Это значит:

- scaffold остаётся у клиента;
- plugin обновляется с нашей стороны;
- runtime выбирается по удобству, безопасности и скорости delivery.

## Текущая реализация (Anthropic Claude)

Первые клиенты используют Anthropic Claude (Claude.ai, Claude Code, Cowork). В этом случае delivery через нативные механизмы платформы:

- **CLAUDE.md** (в корне scaffold) — инструкция агенту: роль, навигация, протокол чтения, ритуалы. Читается платформой автоматически.
- **`.claude/skills/`** — исполняемые навыки (промпты, процедуры). Подключаются Claude автоматически по описанию задачи.

Это **временное решение**, привязанное к Anthropic. При смене runtime: CLAUDE.md → system prompt нового runtime, `.claude/skills/` → native skills mechanism. Продуктовая ценность (методология, промпты) не зависит от runtime — меняется только обёртка.
