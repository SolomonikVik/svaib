# Cowork — агентная платформа для knowledge workers

## Кратко

Cowork — фича Claude Desktop (macOS, Windows), запущена в январе 2026 как research preview; с июля 2026 — также web и mobile (beta). Приносит агентную архитектуру Claude Code (субагенты, параллельная работа) в GUI для не-разработчиков: sales, legal, finance, marketing. Работает в изолированной песочнице (где именно — см. предупреждение ниже). Расширяется через Plugins — тот же формат что Claude Code. Критически важно для продукта SVAIB: плагины = техническая реализация модели подписки "Skills + Agents + Онтология".

❗️ **Среда быстро меняется.** Архитектура исполнения менялась за считанные недели: в начале сентября 2026 плагин и подключённая папка лежали в одной VM, к 19.09 появился облачный режим, где они на разных машинах, и режим стал настройкой. Любой замер ниже верен на свою дату и свой режим — перед решением, которое опирается на устройство Cowork, перепроверяй зондом, а не по этому файлу.

**Главное на 19.09.2026:** у Cowork два режима (Settings → Cowork). В облачном модель, плагин, хуки и скрипты исполняются в контейнере Anthropic, а подключённая папка — на машине пользователя за MCP-мостом `remote-devices`; скрипты скиллов работают над данными, только если скопировать их в саму папку. В «Only on this computer» плагин и папка в одной VM, скрипты работают напрямую. Общее для обоих: скиллы и хуки из `.claude/` папки не подхватываются, работает только плагин. Хуки навигации доставляют контекст пространства только в «Only on this computer», если берут корень из `CLAUDE_CODE_WORKSPACE_HOST_PATHS` (у svaib — с плагина 0.14.5); в облачном хуку данных не видно. Что именно теряет пространство в каждом режиме → [Как деградирует пространство по режимам](#как-деградирует-пространство-по-режимам). → [Архитектура исполнения](#архитектура-исполнения-два-режима-замер-19092026)

## Cowork vs Claude Code

| | Cowork | Claude Code |
|---|---|---|
| **Интерфейс** | Claude Desktop GUI | CLI / VS Code / JetBrains |
| **Аудитория** | Knowledge workers (sales, legal, finance) | Разработчики |
| **Среда** | Два режима (на 19.09.2026): облачный — агент в контейнере Anthropic, папка за RPC-мостом; «Only on this computer» — `bash` в VM рядом с папкой | Прямой доступ к файловой системе |
| **Формат плагинов** | Идентичный | Идентичный |
| **Субагенты** | Task tool (до ~10 параллельных) | Task tool (до ~10 параллельных) |

Формат и харнес общие: тот же Task tool, те же субагенты, тот же формат плагинов. Но предпосылка Claude Code «агент и данные на одной файловой системе» в Cowork с подключённой папкой не выполняется — это главное различие для плагинов, а не интерфейс. Прямая цитата Anthropic: *"Built for Cowork, also compatible with Claude Code."*

## Ключевые возможности

**Plugins.** Система расширения через Skills + Commands + Agents + Hooks + MCP. Всё файловое (Markdown + JSON).

**Hooks — работают, источник только плагин.** Замер 09.09.2026 зондом на все 10 событий ([runtime-probe](https://github.com/JazzShapka/runtime-probe), три сессии Cowork cloud): срабатывают `UserPromptSubmit`, `PreToolUse`, `PostToolUse` (и на Bash, и на Agent), `Notification`, `Stop`, `SubagentStart`, `SubagentStop`; `deny` реально блокирует вызов, `ask` показывает пользователю диалог подтверждения. **Исключение — `SessionStart`: в облачном режиме не эмитится** (0 срабатываний, в том числе при старте сессии сразу с команды). В «Only on this computer» эмитится — и на каждом ходе пользователя: процесс Claude Code перезапускается с `--resume`, `SessionStart` приходит с `source: resume` (замер 19.09.2026). `PreCompact` и `SessionEnd` в прогоне не наблюдались за отсутствием повода.

Сессия живёт в облачном контейнере (`/root`, права root), поэтому `.claude/settings.json` подключённой папки источником хуков не служит — доехать может только установленный плагин. Следствия: enforcement для этого канала упаковывается в плагин, а доставка контекста впрыском строится на `UserPromptSubmit` вместо `SessionStart`.

**Контекст из пространства — только в «Only on this computer» и только по адресу из окружения (19.09.2026).** В облачном режиме хук исполняется в контейнере, где подключённой папки нет. В «Only on this computer» — на машине пользователя с рабочим каталогом в служебной папке сессии: хук, ищущий корень от `cwd` или `CLAUDE_PROJECT_DIR`, его не найдёт, а берущий из `CLAUDE_CODE_WORKSPACE_HOST_PATHS` — найдёт. Хук, решающий по входу вызова (`deny` по имени инструмента или команде), в облачном режиме работает. Детали — в разделе об архитектуре ниже. Сравнение сред и продуктовые следствия → [plugins/!plugins.md](../plugins/!plugins.md).

**Skills.** Три канала установки: встроенный каталог (Customize), загрузка своего скилла (папка/ZIP), и `.claude/skills/` подключённой папки — последнее подтверждено живым прогоном meeting-analysis 30.07.2026, но **19.09.2026 не работает ни в одном режиме**: `SKILL.md` из папки в список скиллов сессии не попадает, харнес собирает скиллы из кэша плагинов и встроенного набора. Skills доступны на всех платных планах.

**Deliverable-first вывод (критично для HITL-скиллов).** Cowork системно склоняет модель к схеме «результат = файл, в чате — краткий статус»: это заявленный дизайн платформы (запросил документ — получил .docx, не текст в чате). Следствие: скилл, требующий показать согласующему полный текст в чате (HITL-экраны), в Cowork молча деградирует до «смотрите файл» — воспроизведено на живом прогоне meeting-analysis 30.07.2026 (выжимка не показана в чате). Инструкция показа должна явно запрещать замену показа ссылкой/превью/пересказом. Отсылка к файлу вдобавок ненадёжна: известный баг пустого превью в панели Cowork ([#33499](https://github.com/anthropics/claude-code/issues/33499)).

**Отчёт агента о собственной среде ненадёжен.** Модель не видит слой разрешений: диалог подтверждения показывается пользователю, а в контекст агента не попадает — он сообщает «подтверждения не запрашивали» и достраивает объяснение. Воспроизведено и в Cowork, и в Desktop. Следствие: UI-эффекты при проверке сред подтверждает человек, а не пересказ агента.

**Scheduled Tasks.** Recurring и on-demand задачи через `/schedule`. Docs: [Anthropic](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-cowork).

**Multi-App.** Claude работает сквозь Excel и PowerPoint, передавая контекст между приложениями (pivot tables, conditional formatting, генерация презентаций из данных). Research preview.

**Enterprise Private Marketplaces.** Компании создают внутренние каталоги плагинов: per-user provisioning, OpenTelemetry для трекинга, корпоративный брендинг.

## Архитектура исполнения: два режима (замер 19.09.2026)

Режим переключается в Settings → Cowork: облачный или «Only on this computer» (папка доступна только на текущей машине). Устройство у них принципиально разное, поэтому любой вывод о Cowork верен только для своего режима. Замеры и живые тесты svaib в тот же день, на одном стенде (плагин svaib, тестовое пространство).

| Наблюдение | Облачный режим | «Only on this computer» |
|---|---|---|
| Хостов исполнения | 3 | 2 |
| Где Claude Code и файловые инструменты | облачный контейнер Anthropic | машина пользователя |
| Где `bash` | контейнер (`Bash`); к папке — `device_bash` в VM | sandbox-VM (`mcp__workspace__bash`) |
| Папка в ФС того, кто исполняет скрипты | нет | есть, rw |
| Плагин рядом с данными | нет | да, ro |
| Скрипты скиллов над пространством | только копией в самой папке | работают напрямую |
| Хуки плагина доставляют контекст из пространства | нет: в контейнере нет данных | да, если корень берётся из `CLAUDE_CODE_WORKSPACE_HOST_PATHS` |
| `SessionStart` | не эмитится (09.09 и 19.09) | эмитится на каждом ходе |
| Адрес папки у хука | нет | `CLAUDE_CODE_WORKSPACE_HOST_PATHS` |
| Признак среды в окружении | `CLAUDE_CODE_ENTRYPOINT=remote_cowork` | `CLAUDE_CODE_ENTRYPOINT=local-agent`, `CLAUDE_CODE_IS_COWORK=1` |
| Хуки и скиллы из `.claude/` подключённой папки | не подхватываются | не подхватываются |
| Перенос файлов между хостами | поштучно через MCP-мост | прямой, двусторонний |

Публично ни одна из схем толком не описана: официальная [architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview) лишь различает облачную сессию («sandbox on Anthropic-managed infrastructure») и локальную («dedicated Linux VM»), реверс-инжиниринг сообщества ([PVIEITO](https://pvieito.com/2026/01/inside-claude-cowork), [Pluto Security](https://pluto.security/blog/inside-claude-cowork-how-anthropics-autonomous-agent-actually-works/)) видит только локальную VM.

### Облачный режим: три хоста

| Хост | Признаки | Что там | Как достижим |
|---|---|---|---|
| Облачный контейнер Anthropic | `hostname: vm`, `HOME=/root`, cwd `/home/claude` | Харнес Claude Code, синк плагина (`/root/.claude/plugins/synced/<org>_<account>/<plugin>/`, его `bin` в `PATH`), хуки, скрипты, скиллы, логи хуков | Инструмент `Bash` |
| Sandbox-VM на машине пользователя | `hostname: claude`, `HOME=/sessions/<сессия>` | Подключённые папки fuse-монтом в `$HOME/mnt/<папка>`; `python3`, базовые утилиты. Плагина нет | Инструмент `device_bash` через MCP-мост |
| Машина пользователя | desktop-приложение Claude | Реальные файлы | Только через desktop-приложение, которое держит VM |

**Одна папка — три адреса:** реальный путь на машине, `/sessions/<сессия>/mnt/<папка>` в VM и никакого в контейнере. `$HOME` в `Bash` и в `device_bash` — разные машины. В контейнере нет ни монта папки, ни переменной с её адресом; есть лишь разовая копия `CLAUDE.md` в `/mnt/user-data/uploads/cowork-folders/`. Механизм удалённого монта в инфраструктуре есть (`/mnt/attach/outputs` через `rclone`), но к папкам пользователя не применяется.

**Мост `remote-devices` — единственный канал к папке.** Это RPC, а не файловая система, и вызывать его может только модель внутри своего хода.

| Инструмент | Ограничения |
|---|---|
| `get_device_info` | имя устройства, `connectedFolders`, статусы локальных MCP |
| `device_list_dir` | глубина до 5, до 2000 записей |
| `device_bash` | 120 с по умолчанию, максимум 180 с; каждый вызов — новый процесс без состояния; удаление — только с отдельного разрешения |
| `device_stage_files` | с устройства в контейнер (`/mnt/user-data/uploads/`); только файлы, ≤ 50 штук, ≤ 400 МБ на файл |
| `device_commit_files` | из контейнера на устройство, **только внутрь подключённых папок**; ≤ 20 МБ на файл; защита по mtime |
| `device_request_folder_access`, `device_request_delete_permission` | подтверждает человек |

**Хуки не видят пространство.** Журнал хука фиксирует запуски, и каждый заканчивается «корень не найден». Хук плагина — голый субпроцесс в контейнере: папки там нет ни по какому пути, MCP-клиента для `device_bash` нет, а бюджет хука (10–15 с) не рассчитан на сетевой round-trip до desktop-приложения, которое может спать. Хуки, положенные в `.claude/hooks/` самой папки, харнес не видит: он читает только локальную ФС контейнера. Решения внутри механизма хуков нет — логика, которой нужны данные, переносится в инструкцию агента (первым ходом прочитать карту через `device_bash`) ценой потери детерминированности.

**Скрипты скиллов: код и данные по разные стороны моста.** Скрипт из плагина в контейнере не находит файлов пространства ни по одному из трёх адресов; в VM, где данные есть, нет скрипта. В отличие от хука, скрипт запускает модель, поэтому рабочий обход есть: скопировать скрипт через `device_commit_files` внутрь подключённой папки и запустить через `device_bash` из её корня — он читает живые файлы (проверено). Цена: код плагина оказывается в данных клиента, и обновление плагина эти копии не обновит — нужен свой механизм версий. В папку уезжает только исполняемая часть: `SKILL.md` из `.claude/skills/` папки автодискавери не подхватит.

**Зонд окружения хука (19.09.2026) подтверждает картину изнутри хука.** Хук исполняется в контейнере (`hostname: vm`, uid 0, firecracker-VM), `cwd` и `CLAUDE_PROJECT_DIR` = `/home/claude`, `CLAUDE_ADDITIONAL_DIRECTORIES` = `/mnt/user-data:/mnt/user-data/outputs`. Признак среды — `CLAUDE_CODE_ENTRYPOINT=remote_cowork`, `CLAUDE_CODE_REMOTE=true`. **Адреса подключённой папки у хука нет ни в окружении, ни во входе, ни в файлах контейнера**; его знает только `get_device_info`, а его вызывает модель (`connectedFolders`). `additionalContext` на `UserPromptSubmit` и `PostToolUse` до модели доходит; `SessionStart` снова не пришёл. Процесс Claude Code один на всю сессию. Хуки ловят и встроенный `Bash` (он здесь есть, в контейнере), и MCP-вызовы моста (`device_bash`, `get_device_info`). В окружении `CLAUDE_CODE_SKIP_PLUGIN_MCP_SERVERS=1` — MCP-серверы из `.mcp.json` плагина, судя по флагу, в этом режиме не поднимаются; сетевые серверы работают как коннекторы аккаунта.

**Похожие issue — другой отказ.** [#27398](https://github.com/anthropics/claude-code/issues/27398) (плагинные хуки отбрасываются из-за `--setting-sources user`) и [#40495](https://github.com/anthropics/claude-code/issues/40495) (игнор user- и managed-settings) — про резолвинг настроек. У нас хуки срабатывают и падают шагом позже, на отсутствии данных.

### «Only on this computer»: два хоста

- **Машина пользователя** — Claude Code и файловые инструменты (`Read`/`Write`/`Edit`/`Glob`/`Grep`). Рабочий каталог сессии — scratch `…/local-agent-mode-sessions/<session>/<id>/outputs`, рядом `uploads` и кэш плагинов `rpm/plugin_<id>/`. Файловые инструменты пускают только в подключённые папки и кэши плагинов и скиллов; остальное, включая `~/.local/state`, отбивается как «outside this session's connected folders».
- **Sandbox-VM** — `bash` (`hostname: claude`, `HOME=/sessions/<сессия>`). Всё с хоста смонтировано под `$HOME/mnt/` отдельными fuse-монтами: подключённая папка (rw), `outputs` (rw), `uploads` (ro), каждый плагин целиком в `.remote-plugins/plugin_<id>/` (ro), встроенные скиллы в `.claude/skills` (ro), знание проекта в `.claude/projects` и `.projects/<uuid>` (ro).

Запись двусторонняя и мгновенная: файл, созданный из `bash` в папке, сразу читается `Read` на хосте, и наоборот.

**Скрипты скиллов работают напрямую.** Скрипт плагина из `mnt/.remote-plugins/…` запускается над `mnt/<папка>` и читает живые файлы; копия скрипта в папку больше не нужна, хотя тоже работает.

**Хуки работают на хосте; корень пространства надо брать из окружения.** До исправления хуки svaib ничего не подавали: ни на `UserPromptSubmit`, ни на `PostToolUse` после чтения и `whoami`, ни на `PreToolUse` перед записью; хук из `.claude/hooks/` папки не подхвачен. Зонд окружения хука (19.09.2026) показал, почему и как чинить:

- Хук исполняется на машине пользователя, дочерним процессом Claude Code, которого запускает desktop-приложение. Все пять событий приходят: `SessionStart` (`startup`, `resume`), `UserPromptSubmit`, `PreToolUse`, `PostToolUse` (на `Read`, `Glob`, `mcp__workspace__bash`, MCP-вызовы), `Stop`.
- `cwd` хука и `CLAUDE_PROJECT_DIR` указывают на служебный scratch сессии `…/local-agent-mode-sessions/<account>/<org>/<id>/outputs`. Хук, который ищет корень через эту переменную или подъёмом от `cwd`, пространство не найдёт.
- **Адрес подключённой папки у хука есть:** переменная `CLAUDE_CODE_WORKSPACE_HOST_PATHS`; несколько папок desktop-приложение склеивает через `|` (`userSelectedFolders.join("|")` в коде приложения). Он же — в `--add-dir` командной строки Claude Code и в метаданных сессии `local_<id>.json` двумя уровнями выше `cwd` (`userSelectedFolders`; совпадение по `cwd`, по `cliSessionId` — со второго события). Признак среды — `CLAUDE_CODE_IS_COWORK=1`, `CLAUDE_CODE_ENTRYPOINT=local-agent`.
- Claude Code запущен с `--setting-sources=user`, папка подключена через `--add-dir`, а не как проект: этим объясняется, почему `.claude/` пространства не служит источником хуков и настроек. `CLAUDE.md` подключённой папки при этом подгружается (`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`).
- Встроенный `Bash` у Claude Code отключён; `bash` — это MCP-инструмент `mcp__workspace__bash` в VM. Хук должен слушать `mcp__workspace__bash` и переводить пути VM `/sessions/<сессия>/mnt/<имя папки>` в пути хоста; агент ходит командами вида `cd /sessions/…/mnt/<папка>/ && cat …`, поэтому нужен и учёт `cd`.
- **`additionalContext` хука доходит до модели** — на `SessionStart`, `UserPromptSubmit` и `PostToolUse` (подтверждено отчётом модели изнутри сессии). Канал доставки исправен, ломается только поиск корня.
- **Процесс Claude Code живёт один ход.** На каждый ход пользователя desktop-приложение поднимает новый процесс с `--resume=<session_id>`: новый PID, снова `SessionStart` (`source: resume`), `session_id` тот же. Состояние хука «уже подал на этой сессии» держать по `session_id`, не по процессу.
- Хук и `bash` на разных машинах: дампы хука на хосте из `bash` не видны, и наоборот. `get_device_info` в этом режиме недоступен. В этом прогоне VM монтировала папку и `outputs` по тем же абсолютным путям, что на хосте (утром того же дня — в `$HOME/mnt/<папка>`): адреса внутри сессии тоже не стабильны.

**Исправлено в плагине svaib 0.14.5 и проверено вживую:** при `CLAUDE_CODE_IS_COWORK=1` корень берётся из `CLAUDE_CODE_WORKSPACE_HOST_PATHS` (из нескольких папок — та, где `.svaib/`; неоднозначно — хук молчит), пути bash VM переводятся в пути хоста. Карта, подкарты узлов (через `Read` и bash) и спецификация перед записью приходят, в том числе с двумя подключёнными папками.

**Скиллы из папки не подхватываются.** Скилл в `.claude/skills/` подключённой папки виден в VM, но в список скиллов сессии не попадает: харнес собирает их из плагинов, переданных через `--plugin-dir`, и встроенного набора.

### Как понять, что перед тобой

`hostname`, `echo $HOME` и `/proc/mounts` из `bash`: `/root` и нет fuse-монта папки — облачный режим; `/sessions/<сессия>` с папкой и `.remote-plugins` в `mnt/` — «Only on this computer». ⚠️ Не ищи через `find / -xdev`: `/sessions` — отдельное блочное устройство, и `-xdev` отсекает его целиком, давая ложный отрицательный результат. Смотри `/proc/mounts` и `find /sessions`.

### Инструкция агента: импорт `@AGENTS.md` не доезжает

Замер 20.09.2026, Claude Code 2.1.278. Конфигурация «Only on this computer» воспроизведена на хосте: cwd — служебный каталог сессии, пространство подключено через `--add-dir`, `--setting-sources user`, `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`.

| Что доезжает до модели | Claude Code в папке | Коворк-конфигурация |
|---|---|---|
| Тело `CLAUDE.md` пространства | ✅ | ✅ дословно |
| Содержимое `AGENTS.md` через `@AGENTS.md` | ✅ | 🔴 импорт не разворачивается |

Причина не в Cowork, а в правиле харнеса: `@path` разворачивается только в `CLAUDE.md`, который лежит в cwd — для файлов выше по дереву тело грузится, а строки импорта молча игнорируются ([issue #79046](https://github.com/anthropics/claude-code/issues/79046), закрыт как not planned). Папка, подключённая через `--add-dir`, в цепочку cwd не входит. Прямое чтение тоже не спасает: по [докам](https://code.claude.com/docs/en/memory) для таких директорий «their `CLAUDE.md` loads, their `AGENTS.md` doesn't load».

**Приводит к инструкции глагол, а не ссылка.** Маркерное правило в `AGENTS.md`, нейтральный вопрос, `Read` доступен, по 3 прогона на вариант:

| `CLAUDE.md` пространства | Правило выполнено |
|---|---|
| `@AGENTS.md` — голая ссылка | 0 / 3 |
| `Рабочая инструкция — @AGENTS.md Прочитай её перед работой` | 3 / 3 |

Голая ссылка — синтаксис импорта и ничего сверх того: когда импорт не сработал, агент видит строку без действия и файл не открывает. Слова о чтении приводят его к инструкции через `Read`. В облачном режиме и этого мало — `AGENTS.md` рядом с агентом нет физически, в контейнере лежит только копия `CLAUDE.md`, а путь к файлу идёт через `device_bash`.

⚠️ **Хук каноном не заменяет `CLAUDE.md`.** Тот же канон, поданный хуком в `additionalContext`, доезжает целиком, но как правило поведения не работает: 0/3 против 3/3 у `CLAUDE.md` на одном и том же тексте. Работает только то, что стоит в начале блока. Замер и следствия — [rule-enforcement.md](../skills/rule-enforcement.md#канал-доставки-текст-доехал--правило-действует).

### Как деградирует пространство по режимам

Эталон — Claude Code, открытый в папке пространства: агент, хуки, скрипты и данные на одной файловой системе, корень пространства = рабочий каталог.

| Возможность | Claude Code в папке | «Only on this computer» | Облачный режим |
|---|---|---|---|
| Инструкция агента (`AGENTS.md`) в контексте | ✅ импортом из `CLAUDE.md` | 🟡 импорт молчит, спасает глагол «прочитай» | 🔴 файла рядом нет, только через мост по инструкции |
| Карта и подкарты пространства от хуков | ✅ | ✅ корень из `CLAUDE_CODE_WORKSPACE_HOST_PATHS` (svaib 0.14.5) | 🔴 хук в контейнере без данных |
| Спецификация файла перед записью (хук) | ✅ | ✅ то же, включая запись через bash VM | 🔴 та же причина |
| Гвард по входу вызова (`deny`/`ask`) | ✅ | ⚪️ не проверялось; на `bash` матчер — `mcp__workspace__bash` | ✅ |
| Впрыск на старте сессии (`SessionStart`) | ✅ | ✅ на каждом ходе (процесс перезапускается) | 🔴 |
| Скрипты скиллов над пространством | ✅ | ✅ напрямую | 🟡 только копией в папке, со своим версионированием |
| Скиллы плагина | ✅ | ✅ | ✅ |
| Скиллы и хуки из `.claude/` пространства | ✅ | 🔴 | 🔴 |
| Чтение и правка пространства моделью | ✅ | ✅ | 🟡 через MCP-мост, поштучно |
| Сетевой MCP-сервер | ✅ | ✅ | ✅ |

**Эталон есть и в десктопе.** Режим Code в Claude Desktop запускает Claude Code прямо в выбранной папке: `cwd` и `CLAUDE_PROJECT_DIR` = папка, `--setting-sources=user,project,local`, `CLAUDE_CODE_ENTRYPOINT=claude-desktop` (замер 19.09.2026). Плагин, установленный через Cowork, доезжает и туда. Для работы в пространстве без деградации это ближайшая к Cowork альтернатива в том же приложении.

**Вывод.** «Only on this computer» возвращается почти к эталону, если хук берёт корень из `CLAUDE_CODE_WORKSPACE_HOST_PATHS` и понимает bash VM (у svaib — с 0.14.5); теряется только `.claude/` пространства. В облачном режиме данных рядом с хуком нет физически, и плагин это не исправит: то, что агент должен знать о пространстве, остаётся в инструкции, которую он выполняет сам (прочитать карту первым ходом).

## Sandbox и сетевые ограничения

> Замеры 31.03 и 07.08.2026, до появления облачного режима; для режимов 19.09 не перепроверялись.

Cowork выполняет все команды в sandboxed VM. Исходящий трафик проходит через MITM-прокси (`localhost:3128`), который фильтрует домены по allowlist.

**Allow network egress** (Settings → Capabilities):
- **OFF (по умолчанию):** прокси блокирует все нестандартные домены (`403 Forbidden`, заголовок `X-Proxy-Error: blocked-by-allowlist`). Доступны только ~23 захардкоженных dev-домена
- **ON:** трафик идёт напрямую через NAT, без прокси

**Domain allowlist:** даже при ON, если выбран не "All domains" — конкретные домены могут быть заблокированы. Есть открытые баги Anthropic с allowlist.

**Важно:** изменение настройки применяется только к **новым сессиям**. Уже запущенные сессии не подхватывают изменение.

**Диагностика:** `env | grep -i proxy` — если в выводе `HTTPS_PROXY=http://localhost:3128`, прокси активен и фильтрует трафик.

При **ON + All domains** произвольный домен вне списка dev-доменов проходит: `curl` к стороннему HTTPS отдаёт `200`, переменных прокси в окружении нет. Обе половины картины сошлись — фильтрация включается вместе с настройкой, а не действует всегда (проверено 07.08.2026).

> Отчёты расследований: `clients/_inbox/cowork-telegram-debug-report.md` (31.03.2026) · `dev/saas/gateway/env-probe.md` (07.08.2026)

## Файловая система: что переживает сессию

> Замеры 07.08.2026 — агент в одной VM с подключённой папкой, как в нынешнем «Only on this computer». В облачном режиме `~` и папка на разных машинах — см. [Архитектура исполнения](#архитектура-исполнения-два-режима-замер-19092026).

`~` внутри песочницы разворачивается в **`/sessions/<имя-сессии>/`, и имя своё у каждой сессии**: файл, созданный в предыдущей, в следующей недоступен. Реальная домашняя директория машины из песочницы **не видна вовсе** — примонтирована только приложенная рабочая папка.

Практическое следствие: единственное персистентное и записываемое место в Cowork — рабочая папка (обычно синхронизируемая через облачный диск). Любая схема «положить конфиг или секрет в `~/.config/...`» здесь не работает конструктивно, а не «ненадёжна». Ранее это описывал только сторонний реверс-инжиниринг; подтверждено прогоном 07.08.2026.

## Скиллы и их скрипты в песочнице (проверено живьём 02.09.2026)

> Картина совпадает с режимом «Only on this computer» (19.09 подтверждено: плагин в `mnt/.remote-plugins/`, скрипты работают над папкой напрямую). В облачном режиме скрипты плагина исполняются в контейнере и папки не видят, см. [Архитектура исполнения](#архитектура-исполнения-два-режима-замер-19092026).

Диагностика в сессии Cowork на копии базы клиента (Linux-VM, Claude Code внутри с `--plugin-dir`):

- В `/sessions/<сессия>/mnt/` лежат `.claude`, `.remote-plugins`, рабочая папка, `outputs`, `uploads`. Скрытые каталоги `ls` без `-a` не показывает — агент легко делает ложный вывод «плагин не смонтирован».
- **Установленный скилл** лежит в `/sessions/<сессия>/mnt/.remote-plugins/plugin_<id>/skills/<скилл>/`, его `scripts/` **из bash доступны и исполняются**. Копия тех же файлов из рабочей папки `.claude/skills/<скилл>/` смонтирована тоже.
- **`${CLAUDE_SKILL_DIR}` в Cowork бесполезен**: в одном прогоне остался строкой, в другом подставился в путь **хоста**, в третьем — в `/sessions/<сессия>/mnt/.claude/skills/<скилл>` (смонтированная `~/.claude` хоста, скилла там нет) (`~/.config/Claude/local-agent-mode-sessions/<session>/<id>/rpm/plugin_<id>/skills/<скилл>/`), которого из VM нет. Найти папку установленного скилла можно так: `find /sessions -path '*/skills/<скилл>/scripts/<файл>' -not -path '*/.claude/*' | head -1` — но это приём диагностики: как скиллы адресуют свои файлы, решает спецификация скилла, раздел 4; проверяет сборщик поставки (гейт 7.7a).
- Проверка версии (`skill_version.py`, маркер `.skill-version.json` в базе) осмысленна только из копии плагина: она несёт штамп установленного архива. Копия из рабочей папки всегда равна маркеру и молчит. Гейт spine v2 на этой же механике отрабатывал в бою.
- Путь к архиву `.skill` внутри смонтированной папки, выведенный агентом отдельной строкой, Cowork показывает карточкой с кнопкой обновления. ❗️ 03.09: кнопка сообщает «установилось», но скилл после этого не работает; в v2 (июль) тот же путь обновления работал. Надёжная установка — только Customize → Skills.
- `TMPDIR` в bash-песочнице — `/sessions/<сессия>/tmp`, свой у каждой сессии: кэш, положенный «в /tmp на сутки», в следующей сессии не виден (выгрузка канона scaffold-align качает архив заново каждую сессию, 3–9 с).
- Слэш-команда установленного скилла регистрируется только после рестарта приложения (dev/plugin-builder/_issues.md №8); длина `description` меряется в символах (744 символа / 1270 байт приняты).

## Коннекторы: только OAuth

Свой MCP-сервер подключить можно — `Customize → Connectors → Add → Add custom connector`. Поля: `Name`, `Remote MCP server URL` (HTTPS-адрес, где сервер принимает MCP-запросы), в Advanced — `OAuth Client ID` и `OAuth Client Secret`, **оба опциональны**.

- **Поля для статического заголовка `Authorization: Bearer` нет.** Приём, которым живёт `claude mcp add --header` в CLI, в десктопе и Cowork недоступен: стороннему серверу нужен настоящий OAuth-контур.
- Опциональность `Client ID` / `Secret` означает, что динамическая регистрация клиента (RFC 7591) не обязательна — пару можно выдать вручную.
- Коннекторы имеют тип **Web** и живут в аккаунте claude.ai, а не на машине. Отсюда их главное свойство: Google Drive одновременно виден в `claude mcp list` в терминале и в десктопном приложении, **при этом его токена на диске нет вовсе** — в `~/.claude/.credentials.json` лежит только собственный OAuth аккаунта Claude. Для стороннего сервиса это готовая модель «авторизовал один раз в аккаунте — работает во всех средах, секрета на диске не остаётся».
