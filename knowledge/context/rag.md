# RAG — Retrieval-Augmented Generation

## Кратко

Паттерн подачи AI релевантной информации из внешнего хранилища: нарезать документы на куски (чанкинг) → превратить в числовые представления (эмбеддинги) → сохранить в базу → при запросе найти похожие куски → подать LLM для генерации ответа. К 2026 году это перестало быть единственным способом: агентные системы всё чаще не индексируют корпус заранее, а отдают агенту инструменты поиска и дают ему решать, что и когда доставать. Вопрос сместился с «RAG или длинный контекст» на «кто принимает решение о поиске — пайплайн или агент».

Этот файл — про выбор архитектуры и её реализации. Инженерия стека (чанкинг, эмбеддинги, базы, метаданные, реранкинг) — [retrieval-stack.md](retrieval-stack.md); измерение качества — [../evals/retrieval-evaluation.md](../evals/retrieval-evaluation.md).

## Три способа дать агенту знание

| | Длинный контекст | RAG-пайплайн | Агентный поиск |
|---|---|---|---|
| Кто решает, что подать | разработчик (всё сразу) | пайплайн (top-k по запросу) | агент (по ходу задачи) |
| Подготовка корпуса | нет | индексация, переиндексация | нет или лёгкий индекс |
| Свежесть данных | на момент сборки контекста | на момент индексации | на момент чтения |
| Стоимость запроса | высокая, растёт с корпусом | низкая, 50–200× меньше токенов | средняя, зависит от числа итераций |
| Слабое место | «потерялось в середине» при >100K токенов | один выстрел: retrieval либо попал, либо нет | латентность и непредсказуемое число шагов |
| Где уместен | небольшой стабильный корпус | большой статичный корпус, один запрос — один ответ | задача из нескольких шагов, живые данные, права доступа |

Это не взаимоисключающие варианты: агентный поиск может вызывать RAG как один из инструментов, а найденное — читаться длинным контекстом.

## Сдвиг 2026: агентный поиск вместо предварительного индекса

Главное изменение последнего года — агентные системы отказались от векторного индекса как обязательного слоя.

**Практика кодовых агентов.** Boris Cherny, автор Claude Code: ранние версии использовали RAG с локальной векторной базой, но агентный поиск «в целом работает лучше — он проще и не имеет тех же проблем с безопасностью, приватностью, устареванием и надёжностью». Claude Code, Cursor, Windsurf, Cline, Sourcegraph Amp не индексируют целевой корпус в векторную базу: retrieval отдан набором инструментов, а модель решает, какой вызвать, когда и сколько раз.

**Названный паттерн.** Anthropic формализовала подход как *just-in-time context loading*: агент держит лёгкие идентификаторы (пути к файлам, сохранённые запросы, ссылки) и подгружает данные в контекст на лету инструментами. Предрассчитанные эмбеддинги заменяются агентом, который достаёт по требованию — так, как читает код человек, а не так, как его индексирует поисковик.

**Корпоративная сторона.** Здесь тот же сдвиг называют переходом от RAG к *context architecture*: агенты генерируют на порядки больше обращений к данным, чем люди, и retrieval-слой, построенный под человеческий масштаб, этого не выдерживает. Цифры Q1 2026: намерение перейти на гибридный retrieval выросло с 10.3% до 33.3%, доля собственных retrieval-стеков — с 24.1% до 35.6%, вложения в оптимизацию retrieval (19% → 28.9%) впервые обогнали вложения в оценку. Семантический слой — сущности, связи, правила доступа — становится версионируемой производственной инфраструктурой.

**Что это значит на практике.** «RAG умер» — неверное прочтение. Умерла конкретная конфигурация: один запрос → одна векторная выдача → ответ. Подготовка корпуса никуда не делась, изменилось только то, кто принимает решение о поиске.

## Когда предварительный индекс всё ещё нужен

- **Корпус не лежит под рукой агента.** Файловая система даёт grep и чтение; база тикетов, почта или 10 млн PDF — нет.
- **Запросов много, а латентность критична.** Агентный цикл из пяти инструментальных вызовов дороже и медленнее одного поиска по индексу.
- **Нужен смысловой поиск там, где нет ключевых слов.** Агент с grep компенсирует это перебором синонимов, но на большом корпусе это дороже эмбеддингов.
- **Права доступа обязаны применяться до поиска.** Фильтр по метаданным в индексе — контролируемая граница; агент, сам решающий, что прочитать, такой границей не является (→ [permission-aware-retrieval.md](permission-aware-retrieval.md)).

Общее правило: агентный поиск выигрывает там, где корпус — это файлы, которые агент может открыть сам; индекс выигрывает там, где корпус — это данные, к которым нужен отдельный доступ.

## Как устроен рабочий пайплайн

Гибридный поиск как отраслевой минимум: BM25 (точные совпадения) параллельно с векторным поиском (смысловая близость) → объединение через RRF → реранкинг top-N. Одного векторного поиска недостаточно ни на одном серьёзном корпусе.

Ключевое свойство порядка: качество определяется препроцессингом, а не поиском. Чанк, в который попали три темы, даёт усреднённый вектор, и никакой реранкер этого не исправляет. Детали каждого звена — чанкинг по смысловым границам, выбор модели эмбеддингов, квантизация, метаданные и стратегии фильтрации, выбор реранкера — в [retrieval-stack.md](retrieval-stack.md).

## Направления эволюции

### Agentic RAG

Агент сам решает: что искать, какие инструменты вызвать, когда проверить результат, нужен ли повторный поиск. Не фиксированный пайплайн, а цикл решений.

Паттерны: reflection (агент оценивает качество найденного), planning (разбивает сложный вопрос на подзапросы), tool use (выбирает между grep, векторным поиском, API), multi-agent (разные агенты для разных задач).

Инструментарий агента на практике: семантический поиск для тематических запросов, структурные запросы (SQL, ES|QL) для аналитики, shell для файловой системы, точечные lookup по идентификатору. Рабочий совет по проектированию набора: начинать с универсальных инструментов, логировать провалы и специализировать по ним; сочетать «низкий порог» (простые надёжные инструменты) с «высоким потолком» (сложные escape hatch). Основные вложения — в описания инструментов и системный промпт: агент чаще ошибается не в поиске, а в решении искать.

**Для SVAIB:** это и есть наша архитектура — агент-координатор поверх файлового пространства. Структурированный режим (скилл → маршрут) и неструктурированный (агент ищет сам) вместе дают Agentic RAG без отдельного индекса.

### GraphRAG (Microsoft)

Извлекает сущности и связи из документов → строит граф знаний → создаёт иерархические community summaries. При запросе ищет не по чанкам, а по графу связей.

- Comprehensiveness 72–83% против baseline RAG на вопросах, требующих связей
- 97% меньше токенов для сводок верхнего уровня
- Open source, доступен через Azure; GraphRAG-Bench принят на ICLR 2026

**Для SVAIB:** потенциально ценен для связей между знаниями руководителя (решения → люди → направления → встречи). Но сложен в поддержке. Присмотреться, не внедрять сейчас.

**LightRAG** — облегчённая open-source реализация той же идеи (HKUDS, EMNLP 2025): entity-граф через LLM-экстракцию, без иерархических community summaries. Собственное эмпирическое исследование (экономика, дефекты, позиционирование) → [lightrag.md](lightrag.md).

### Подход Karpathy (LLM Wiki)

LLM читает сырые материалы → пишет wiki-статьи (человекочитаемые) → при запросе читает индекс → подтягивает нужные статьи. Обходит проблему чанкинга: статья сохраняет полный контекст и является естественной единицей поиска. Подробнее → [llm-wiki.md](llm-wiki.md)

## Конкретные реализации

### QMD (приоритетный кандидат)

Локальный семантический поиск по markdown-файлам. Автор — Tobi Lütke (основатель Shopify). Рекомендован Karpathy в гисте LLM Wiki. Репо: [github.com/tobi/qmd](https://github.com/tobi/qmd).

**Как работает:** гибридный пайплайн в 4 шага — query expansion (LLM расширяет запрос) → BM25 + векторный поиск параллельно → RRF fusion → LLM reranking. Три режима: `search` (ключевые слова), `vsearch` (семантика), `query` (гибрид, лучшее качество).

**Всё локально:** три GGUF-модели (~2 ГБ суммарно) — embeddinggemma-300M (эмбеддинги), qwen3-reranker-0.6b (реранкинг), qmd-query-expansion-1.7B (расширение запросов). Никаких облачных API.

**Интеграция с Claude Code:** MCP-сервер даёт инструменты `query`, `get`, `multi_get`, `status`. Работает поверх файловой системы — отдельная база данных не нужна, индексируются markdown-файлы напрямую. Инкрементальный update обновляет только изменённые файлы.

**Чанкинг:** ~900 токенов, разрыв по markdown-структуре (заголовки, блоки кода). Код не разрывается.

**Контексты:** описания папок возвращаются вместе с результатами — агент сразу понимает, что за файл перед ним.

**Экосистема:** OpenClaw Engram (persistent memory для AI на базе QMD), ghost (захват сессий Claude Code + индексация), Rust-порт (qntx-labs/qmd).

**Почему приоритетный для SVAIB:** проверенный автор, полный гибридный пайплайн, работает поверх существующих файлов, MCP-интеграция. Занимает ровно ту нишу, которую агентный поиск не закрывает: смысловой поиск там, где grep бессилен, без обязательств отдельной векторной базы.

### MemPalace (хайп-проект, исследован 2026-04-09)

Open source (MIT), заявлено 96.6% на LongMemEval. Verbatim storage в ChromaDB + метадатная фильтрация («дворец»: wings/halls/rooms).

**Что в коде против того, что заявлено:** hybrid scoring и reranking существуют только в бенчмарк-скриптах, не в продукте. Продукт — голый векторный поиск ChromaDB. Независимый тест дал 17% accuracy в реальном использовании; при добавлении системного промпта accuracy падает с 89.8% до 1.0%.

**Инсайт верный:** verbatim storage плюс хороший поиск конкурентоспособен с LLM-экстракцией. Реализация ненадёжная. Полезен как напоминание: заявленный бенчмарк и продукт — разные артефакты.

### Другие

- **Graphiti (Zep)** — temporal knowledge graph на Neo4j. Зрелый, облачный → [temporal-graphs.md](temporal-graphs.md)
- **LlamaIndex** — фреймворк для RAG-пайплайнов; много интеграций, тяжёлый
- **LangChain** — оркестрация; широко используется, критикуется за overengineering
- **ChromaDB** — простейшая векторная БД: хороша для прототипов, слаба для production
- **Weaviate, Qdrant, Pinecone, pgvector** — production-уровень; выбор по масштабу → [retrieval-stack.md](retrieval-stack.md)

## Связь с архитектурой SVAIB

В контекстной архитектуре Second Value AI Brain RAG занимает позицию **неструктурированного поиска** — когда агент не знает маршрут и ищет по смыслу. Два режима:

1. **Структурированный** (ICM) — задача понятна, маршрут известен, агент идёт по рельсам. RAG не нужен.
2. **Неструктурированный** — вопрос открытый, агент ищет. Здесь работает либо агентный поиск по файлам, либо смысловой индекс поверх них.

Наш паттерн — Agentic RAG в чистом виде, и сдвиг 2026 года подтверждает выбор: агенты в продакшене отказываются от предварительного индекса в пользу инструментального поиска ровно по тем причинам, по которым пространство изначально построено на файлах — прозрачность, свежесть, права, отсутствие рассинхронизации индекса с содержанием.

Открытая ниша — смысловой поиск там, где не работают маршрут и grep. Приоритетная реализация для тестирования: QMD.
