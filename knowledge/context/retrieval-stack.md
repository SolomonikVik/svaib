# Retrieval-стек

## Кратко

Инженерный слой RAG: как нарезать документы на чанки, какой моделью считать эмбеддинги, в какой базе их хранить, какие метаданные прикреплять и как фильтровать по ним, чем переупорядочивать найденное — включая LLM-судью в роли реранкера и его ограничения. Решения принимаются в этом порядке — каждое следующее звено работает с тем, что дало предыдущее, и не исправляет его ошибок. Центральная развилка чанкинга — размечен текст заголовками или нет: у размеченного границы тем уже проведены автором, и резать его по длине значит выбрасывать готовую разметку. Про выбор между RAG, длинным контекстом и агентным поиском — [rag.md](rag.md); про измерение качества выдачи — [../evals/retrieval-evaluation.md](../evals/retrieval-evaluation.md).

## Главный принцип: дефекты препроцессинга не чинятся ниже по потоку

Порядок сборки стека — не произвольный: чанкинг → эмбеддинги → индекс и метаданные → поиск → реранкинг. Если на первом шаге в один чанк попали три темы, вектор этого чанка уже усреднён, и ни реранкер, ни более сильная модель эмбеддингов не восстановят потерянное. То же с метаданными: поле, не собранное при ingest, нельзя отфильтровать на запросе.

Отсюда практическое следствие: когда retrieval плохо работает, сначала смотрят на препроцессинг, а не докупают реранкер.

## Чанкинг

### Развилка первая: размечен ли текст

Главный вопрос чанкинга — не «сколько токенов», а «провёл ли автор границы тем сам». Ответ определяет всё остальное, и два случая почти не пересекаются.

**Размеченный текст** — markdown с заголовками, документация, вики, структурированные протоколы. Заголовок H2/H3 — это уже проведённая человеком граница темы, причём проведённая осмысленно. Нарезать такой текст по количеству символов — значит выбросить готовую разметку и заново угадывать то, что уже известно.

**Неразмеченный текст** — транскрипт разговора, скан PDF, письмо, веб-страница, поток без структуры. Здесь границ нет, и их приходится восстанавливать: по длине, по семантическому разрыву или моделью.

### Чанкинг размеченного текста: по заголовкам, по темам

Правило: **один чанк = один раздел = одна тема**. Разбиение идёт по дереву заголовков, а не по длине.

- **Перекрытие не нужно и вредно.** Перекрытие существует, чтобы починить разрыв мысли на произвольной границе. У границы по заголовку разрыва мысли нет: следующий раздел не продолжает предыдущий, а начинает новую тему. Перекрытие здесь только размывает вектор соседней темой — то есть своими руками создаёт то самое смешение, от которого чанкинг и защищает.
- **Заголовочный путь дописывается в тело чанка.** `Документ → Раздел → Подраздел` в начале текста чанка — бесплатный заменитель contextual retrieval: чанк становится самодостаточным без вызова LLM на каждый фрагмент.
- **Слишком длинный раздел** дробится по абзацам внутри себя, и каждый кусок наследует тот же заголовочный путь. Тема при этом не меняется — меняется только гранулярность.
- **Слишком короткие подразделы** склеиваются с соседними в пределах одного родителя: пять строк под H3 — не самостоятельный вектор, а часть родительской темы.
- **Атомарные блоки не разрываются** — таблица, блок кода, список остаются целыми даже ценой превышения целевого размера. Разрезанная пополам таблица не ищется ни одной, ни другой половиной.

Численное подтверждение: структурный чанкинг по заголовкам обходит семантический — 70.5% против 63.8% (консолидированное исследование, → [markdown-for-llm.md](markdown-for-llm.md)). То есть восстановление границ алгоритмом проигрывает границам, которые автор уже провёл.

Следствие для авторов документов: осмысленные H2/H3 и правило «один файл = одна тема» — не вопрос стиля, а конфигурация retrieval. Текст, написанный с внятной структурой заголовков, уже нарезан на смысловые чанки; текст, написанный сплошняком, придётся нарезать угадыванием.

### Чанкинг неразмеченного текста: тут и появляется длина

Отраслевая точка старта — recursive character splitting на 400–512 токенов с перекрытием 10–20%. В исследовании Chroma этот подход даёт 85.4–89.5% recall с пиком на 400 токенах (88.1–89.5%).

Размер зависит от типа запроса:

| Тип запроса | Размер чанка | Почему |
|---|---|---|
| Фактологический (дата, число, имя) | 256–512 токенов | нужна точность попадания |
| Аналитический (объяснение, обзор) | 1024+ токенов | нужен связный контекст |
| Смешанный поток | 400–512 токенов | компромисс по умолчанию |

Перекрытие и здесь не безусловная догма: анализ января 2026 на Natural Questions со SPLADE-поиском показал, что перекрытие не дало измеримого выигрыша и только увеличило стоимость индексации. Проверять на своём корпусе.

Частный случай — пагинированные документы: постраничная нарезка выиграла бенчмарки NVIDIA 2024 (accuracy 0.648) с наименьшей дисперсией (σ 0.107), но только там, где страница действительно является смысловой единицей.

### Семантический чанкинг

Способ восстановить границы там, где их нет. Границы ставятся в точках падения косинусной близости соседних предложений (Kamradt-подобные сплиттеры): сегментация по предложениям → эмбеддинги скользящих окон → разрыв в точке семантического разрыва.

Даёт до +9% recall против фиксированной нарезки, но работа NAACL 2025 показала, что вычислительная цена систематически не окупается: фиксированные 200-словные чанки сопоставимы или лучше. Вывод: это инструмент для плотного неструктурированного текста, а не общий дефолт. На размеченном тексте он избыточен — заголовки уже дают те же границы бесплатно и точнее.

### Late chunking и contextual retrieval

Два разных ответа на одну проблему — чанк, вырванный из документа, теряет смысл («он» без указания, на кого).

- **Late chunking** — сначала эмбеддинг всего документа, потом нарезка уже по токенным эмбеддингам. Каждый токен успел «посмотреть» на остальной документ через attention, поэтому вектор чанка несёт контекст целого. Дёшево, +6.5 пункта nDCG@10 на длинных документах. Ограничение — длина контекста модели эмбеддингов.
- **Contextual retrieval** (Anthropic) — перед эмбеддингом к каждому чанку дописывается сгенерированное LLM объяснение его места в документе. Дороже (LLM-проход по каждому чанку), но семантическую когерентность сохраняет лучше.

Прямое сравнение (arXiv 2504.19754): contextual retrieval выигрывает по релевантности и полноте, late chunking — по эффективности. Выбор по бюджету, а не по «правильности». На размеченном тексте оба приёма частично обесцениваются: заголовочный путь в теле чанка закрывает ту же потребность почти даром.

### Parent-child (small-to-big)

Индексируются маленькие чанки — ради точности попадания; в LLM отдаётся родительский документ или крупный блок — ради полноты контекста. Разводит две разные величины: гранулярность поиска и гранулярность генерации. В дереве заголовков это ложится естественно: ищем по H3, отдаём раздел H2 или файл целиком.

## Когда в одном чанке несколько тем

У этого дефекта в 2026 появилось имя и измеримая метрика — **semantic entanglement** (arXiv 2604.17677).

**Механика.** Модель эмбеддингов сжимает пассаж в один вектор, то есть по сути усредняет. Если чанк покрывает три темы, а запрос касается одной, вектор окажется умеренно похож на запрос — но не сильно, потому что две нерелевантные темы разбавляют сходство. Результат: многотемный чанк проигрывает однотемному даже тогда, когда содержит точный ответ. В векторном пространстве кластеры разных тем начинают перекрываться.

**Метрика.** Entanglement Index (EI) — мера межтемного перекрытия в пространстве эмбеддингов, относительная к модели. Чем выше EI, тем ниже достижимый потолок Top-K точности при косинусном поиске. То есть EI ограничивает качество сверху: никакая настройка поиска выше этого потолка не поднимет.

**Величина эффекта.** На корпусе 2000+ медицинских документов: Top-K precision 32% при фиксированной токенной нарезке → 82% после реструктуризации документов перед эмбеддингом; средний EI 0.71 → 0.14. Авторы подчёркивают ключевое: это отдельная проблема препроцессинга, и после того как смешение закодировано в векторы, downstream-оптимизация его не чинит.

**Что делать:**

1. Резать по смысловым границам, а не по длине — заголовки в markdown, темы в транскрипте, разделы в договоре. Один чанк = одно утверждение о мире. На размеченном тексте это бесплатно, и именно поэтому заголовочный чанкинг — не оптимизация, а профилактика.
2. Отказаться от перекрытия там, где границы смысловые: перекрытие втягивает в вектор соседнюю тему и повышает EI ровно тем механизмом, от которого лечатся.
3. Проверять корпус на entanglement до того, как жаловаться на поиск: измерить перекрытие тем в пространстве эмбеддингов, найти чанки с высоким EI.
4. Для смешанного текста, который нельзя разрезать без потерь (диалог, где обсуждают три вопроса подряд), — реструктуризация перед эмбеддингом: разложить на пропозиции или QA-пары и индексировать их, а не сырой фрагмент.
5. Parent-child как страховка: индексируем однотемные куски, отдаём общий контекст.

Адаптивная нарезка по логическим границам темы даёт 87% точности против 13% у фиксированной на корпусах с чёткой тематической структурой. Разрыв такого порядка означает, что на тематически разнородном корпусе выбор границы — не тюнинг, а вопрос работоспособности.

## Эмбеддинги

### Выбор модели

Открытые модели догнали закрытые по качеству retrieval в большинстве доменов. Ориентиры по состоянию на 2026 (MTEB Multilingual):

| Модель | MTEB | Контекст | Размерность | Лицензия / цена |
|---|---|---|---|---|
| Qwen3-Embedding-8B | 70.58 | 32K | до 7168, матрёшка | Apache 2.0, self-host |
| NV-Embed-v2 | 69.32 | 32K | 4096 | CC-BY-NC, некоммерческая |
| Gemini embedding-001 | 68.32 | 2K | до 3072, матрёшка | закрытая, ~$0.15/1M |
| voyage-3-large | ~67 | 32K | до 2048, матрёшка | закрытая, ~$0.06/1M |
| Cohere embed-v4 | 65.2 | 128K | 1024 | закрытая, ~$0.10/1M |
| text-embedding-3-large | 64.6 | 8K | до 3072, матрёшка | закрытая, ~$0.13/1M |
| BGE-M3 | 63.0 | 8K | 1024 | MIT, dense+sparse+multi-vector в одном проходе |

Критерии выбора важнее позиции в таблице: суверенность данных (данные не покидают контур → self-host), язык (многоязычие → Qwen3 или Gemini), длина документа (128K умеет только Cohere), нужен ли гибрид из одной модели (BGE-M3).

Доменный fine-tuning даёт 10–30% прироста и требует 500–1000 размеченных примеров — самый недооценённый рычаг, если домен узкий.

### Матрёшка и квантизация

Matryoshka-обучение сделало размерность вектора настраиваемым параметром, а не константой модели: вектор можно обрезать до 512 или 256 измерений с контролируемой потерей качества. Показательная цифра: voyage-3-large в int8 на 512 измерениях обгоняет полный float-вектор OpenAI на 3072 измерениях на 1.16% при 200× меньшей стоимости хранения.

Квантизация векторов в индексе:

| Метод | Сжатие | Потеря recall | Когда |
|---|---|---|---|
| Scalar (SQ) | 4× | <1% | почти всегда оправдана |
| Product (PQ) | 8–64× | 2–5% | агрессивное сжатие, отбор кандидатов перед точным этапом |
| Binary (BQ) | 32× | 5–15% | экстремальная скорость через hamming/SIMD (~1.7× RPS) |
| RaBitQ | ~32× | ниже, чем у BQ | текущий баланс качество/сжатие |

Практика: матрёшка + scalar-квантизация снимают проблему стоимости хранения раньше, чем понадобится переезжать на более дорогую базу.

### Миграция

Смена модели эмбеддингов = переиндексация всего корпуса. Цена самой переиндексации невелика (порядка $6–15 на 100M токенов), дорого обходится другое — несовместимость старых и новых векторов, то есть необходимость держать два индекса на время перехода. Планировать как миграцию схемы БД, а не как смену параметра.

## Векторные базы и индексы

### Развилка нулевая: нужна ли база вообще

Выбору базы предшествует выбор уровня, и до третьего уровня доходят реже, чем принято думать.

| Уровень | Как устроено | Когда достаточно |
|---|---|---|
| **1. Без индекса** | агент ищет инструментами по корпусу: grep, чтение файла, структура каталогов | корпус лежит в файлах, которые агент может открыть сам; свежесть важнее полноты смыслового поиска |
| **2. Индекс поверх файлов** | локальный смысловой индекс по тем же файлам, инкрементальное обновление, отдельного хранилища нет | нужен поиск по смыслу там, где не работают ключевые слова, но заводить и синхронизировать базу не хочется |
| **3. Векторная база** | отдельное хранилище векторов и метаданных со своим жизненным циклом | корпус агенту напрямую недоступен (тикеты, почта, архив документов); запросов много и латентность критична; права обязаны применяться фильтром до поиска |

Разница между уровнями 1–2 и уровнем 3 не в качестве поиска, а в появлении второго источника правды. База — это копия корпуса, которая живёт своей жизнью: её надо наполнять, переиндексировать при смене модели эмбеддингов, синхронизировать при изменении оригинала и защищать отдельно от него. Пока корпус — это файлы под рукой у агента, эта цена не окупается.

Практическое следствие: на корпусе в тысячи документов разговор о выборе между Qdrant и Pinecone обычно преждевременен — реальная развилка проходит между первым и вторым уровнем.

### Развилка по масштабу

| Масштаб | Выбор | Замечание |
|---|---|---|
| < 10M векторов | pgvector в Postgres | p50 ~18ms, отдельную систему администрировать не нужно |
| 10M–50M | Qdrant (фильтрованный поиск) или pgvectorscale | Qdrant интегрирует фильтрацию на уровне архитектуры; pgvectorscale держит p95 < 50ms |
| 50M–100M | Qdrant Cloud, Pinecone Serverless | Pinecone — 8ms p50 / 45ms p99 без тюнинга |
| 100M–1B | Milvus (распределённый), DiskANN | нужна горизонтальная шкала и координация |
| > 1B | Milvus + GPU (CAGRA) | построение индекса на 4.8B векторов: 28.4 дня → 1.4 дня на четырёх GPU |

Ключевой вывод для команды без миллиарда векторов: **специализированная векторная база в большинстве случаев не нужна**, Postgres с pgvector закрывает реальный масштаб при нулевом операционном оверхеде.

### Индексы

- **HNSW** — многослойный граф, полилогарифмический поиск; дефолт в Qdrant, Weaviate, pgvector. Параметры: `M` (связность), `ef_construction` / `ef_search` (ширина луча).
- **IVF** — разбиение пространства через k-means, поиск по ближайшим ячейкам. Лучше HNSW масштабируется на миллиардах, но требует настройки `nlist`/`nprobe`.
- **DiskANN** — векторы на диске, навигация графа в памяти. Открывает миллиардный масштаб на одном сервере.
- **GPU CAGRA** — построение и поиск на GPU, когда индекс перестраивается часто.

### Цена

Прежде чем менять базу ради стоимости хранения, стоит применить более дешёвый рычаг: матрёшка плюс scalar-квантизация дают четырёхкратное сжатие при потере recall меньше процента (→ «Матрёшка и квантизация» выше).

Реальные счета облачных векторных БД в 2.5–4× выше оценки по прайс-листу: компьют, egress и перестроение индекса в прайсе не видны. На 100M векторов self-hosted Qdrant — порядка $350/мес против $700+ у Pinecone; S3-подложка (Turbopuffer) заявляет десятикратную экономию на большом масштабе за счёт объектного хранилища.

## Метаданные

### Что собирать

Метаданные — то, что позволяет отфильтровать корпус до семантического поиска, и то, что делает найденный чанк интерпретируемым для агента. Рабочий минимум:

| Группа | Поля | Зачем |
|---|---|---|
| Происхождение | source, путь, автор, дата создания и изменения | датировать факт, оценить достоверность, показать ссылку |
| Структура | parent_id, заголовок раздела, уровень вложенности, позиция в документе | собрать parent-child, вернуть чанк в контекст документа |
| Классификация | тип документа, тема, язык, версия | сузить корпус до релевантного среза |
| Доступ | tenant, владелец, уровень доступа | жёсткая фильтрация по правам |
| Актуальность | статус (draft/final/archived), срок пересмотра | отсечь устаревшее |

Поле `parent_id` и глубина раздела — не бюрократия: именно они позволяют вернуть чанк в контекст документа, из которого он вырезан.

### Как собирать

- **Детерминированно при ingest** — всё, что выводится из файла и файловой системы: путь, даты, заголовок раздела, позиция. Дёшево, надёжно, не требует модели.
- **Из фронтматтера/разметки** — если формат его несёт (YAML в markdown). Приоритетный источник: автор уже сказал, что это за файл.
- **LLM-экстракцией** — то, чего в файле нет явно: тема, сущности, тип содержания. Автоматическая экстракция даёт консистентность, недостижимую при ручной разметке на большом корпусе, но вносит собственную ошибку — её нужно измерять, а не предполагать.

Метаданные хранятся рядом с вектором в самой базе (payload у Qdrant, properties у Weaviate, колонки у pgvector), а не в отдельном хранилище: фильтр должен применяться внутри поиска, а не после него.

### Четыре стратегии фильтрации

| Стратегия | Как | Когда | Отказ |
|---|---|---|---|
| **Prefilter** | условия применяются до поиска, сужая кандидатов | категориальные и неторгуемые: tenant, тип, регион | пустая выдача при слишком узком фильтре |
| **Postfilter** | поиск по всему индексу, правила — к top-k | фильтр как предпочтение, а не жёсткое условие | ноль результатов, если весь top-k не прошёл; лечится раздуванием k |
| **Hybrid pre+post** | prefilter даёт жёсткую границу, postfilter формирует состав выдачи | продакшн-дефолт | — |
| **Structured only** | без векторного поиска, детерминированный запрос по полям | точное совпадение, где приблизительность недопустима: версия, идентификатор, норма права | не работает на исследовательских запросах |

Принцип раскладки: категориальное, высококардинальное и неторгуемое — в prefilter; ранжируемое, нечёткое, контекстно-зависимое — в postfilter.

**Права доступа — всегда hard prefilter, никогда postfilter.** Изоляция арендаторов, entitlement и ограничения по PII — граница безопасности, а не предпочтение в ранжировании: пайплайн не должен иметь технической возможности выполнить запрос без фильтра авторизации. Изоляция через отдельные namespace/коллекции надёжнее фильтрации по полю. Подробнее о том, как права доезжают до выдачи, — [permission-aware-retrieval.md](permission-aware-retrieval.md).

### Фильтры из запроса

Self-query retrieval: вторичная LLM разбирает запрос пользователя и строит из него фильтр («что решили по маркетингу в августе» → `тема=маркетинг, дата≥2026-08-01`). Даёт заметный прирост на multi-hop вопросах, где нужного чанка в top-k семантически просто нет. Цена — лишний вызов модели и риск, что модель построит слишком узкий фильтр и обнулит выдачу; страховка — откат к поиску без фильтра при пустом результате.

### Что не стоит хранить

Проверка на нужность поля одна: по нему фильтруют, ранжируют или его показывают в выдаче. Если ни одного из трёх — поле не работает, а стоит места и усложняет ingest. Практический вывод из опыта фильтрации (не цитата исследования): под нож обычно идут поля, дублирующие содержание чанка, метрики, которые никто не запрашивает, и вычислимые на лету производные. Отсюда же требование регулярного аудита схемы по логам реальных запросов — какие фильтры действительно вызывались за квартал.

## Гибридный поиск и реранкинг

### Гибридный поиск

Устоявшийся пайплайн: BM25 (точные совпадения, редкие термины, имена) параллельно с векторным поиском (смысловая близость) → объединение через RRF (k=60, не требует нормализации скоров) → реранкинг top-N.

### Три класса реранкеров

Выбор реранкера — это выбор бюджета латентности:

| Реранкер | Цена на кандидата | 100 кандидатов | Когда |
|---|---|---|---|
| Cross-encoder (pointwise) | ~8 мс | ~800 мс | лучшая точность на миллисекунду; локально, без API-счёта; даёт калиброванный балл |
| Late interaction (ColBERT-типа) | ~0.3 мс | ~30 мс | тяжёлая часть предрассчитана; 500 кандидатов за время, которое cross-encoder тратит на 50 — ценой большего индекса |
| LLM-реранкер (listwise) | — | 600 мс – 2 с на пачку из 50 | нужна релевантность с рассуждением: инструкции, многокритериальность, домен без готового реранкера |

Cross-encoder не масштабируется линейно: вчетверо больше кандидатов — вчетверо больше латентности. У late interaction рост сублинейный.

### LLM-судья в роли реранкера

Та же техника, что LLM-as-judge в оценке, только вердикт не записывается в отчёт, а меняет порядок выдачи. Четыре режима — по тому, сколько документов судья видит за раз:

| Режим | Как | Вызовов на N кандидатов | Свойство |
|---|---|---|---|
| **Pointwise** | каждый документ оценивается независимо | N | дёшево, тривиально параллелится, даёт балл; не видит относительной релевантности |
| **Pairwise** | судья сравнивает два документа | до N² | самый тонкий сигнал, непрактичная цена |
| **Listwise** (RankGPT) | судья получает список и выдаёт перестановку | N/размер окна | видит кросс-документный контекст — то, чего pointwise лишён |
| **Setwise** | из набора выбирается только лучший | меньше, чем listwise | компромисс: сравнительный сигнал при меньшем числе вызовов и токенов |

**Как работает listwise на практике.** Кандидатов обычно больше, чем влезает в окно, поэтому применяется скользящее окно: реранжировать 30 документов, сдвинуться, перенеся верх предыдущего окна в следующее. Отсюда изъян: документы из разных окон никогда не сравниваются напрямую — пятый в одном окне может объективно превосходить первого в следующем. «Пузырьковый» проход RankGPT протаскивает лучших через все окна, но это несколько вызовов LLM и всё равно приближённый глобальный порядок.

**Четыре причины, по которым судья-реранкер не является бесплатным апгрейдом:**

1. **Цена на три порядка выше.** Frontier-модель против ~$0.025 за 1M токенов у специализированного реранкера. На продакшн-бенчмарках RAG калиброванный pointwise cross-encoder догоняет или обходит listwise LLM при стоимости и латентности в 100–1000× ниже. По FLOPs та же картина: listwise даёт лучшее качество ценой в 2–3× больше вычислений (метрика EER-FLOPs), setwise — посередине.
2. **На выходе перестановка, а не балл.** Нельзя поставить порог «ниже 0.6 — нерелевантно»: калиброванных оценок просто нет. Это ломает всё, что ниже по потоку ожидает числа — гибридную фузию, отсечение по порогу, бюджетирование контекста.
3. **Position bias, который не лечится настройкой.** Перестановка тех же кандидатов меняет и баллы, и попарные предпочтения, и итоговый порядок. Работа RecSys 2026 проверила три уровня согласованности и показала: улучшение релевантности и выравнивание экспозиции по позициям не восстанавливают ни устойчивых попарных предпочтений, ни согласованной выдачи. Больше того, порядок подачи — управляемый вход: показана атака, меняющая выдачу одной лишь перестановкой кандидатов без правки их содержания.
4. **Лексические шорткаты вместо понимания.** Эмпирический анализ LLM-реранкеров: модели опираются на поверхностные совпадения, деградируют при сдвиге распределения и меняют ранжирование от мелких правок запроса; на held-out-доменах иногда уходят ниже baseline. То, что судья умеет объяснить свой выбор, не означает, что выбор сделан по объяснённой причине.

**Чем гасят:**

- **Permutation self-consistency** — несколько прогонов со случайно перемешанным списком и агрегация ранжирований. Работает, но умножает и без того высокую цену.
- **FIRST** — вместо генерации всей перестановки читаются логиты первого выданного идентификатора, обучение — взвешенным RankNet-лоссом под «top-heavy» природу поиска. Ускорение инференса около 50% (в независимой репродукции 21–42% на трёх моделях) при nDCG@10 54.3 на BEIR против 53.7 у прежнего SOTA. Самый практичный способ оставить listwise в бюджете.
- **Архитектурная инвариантность к перестановке** (InvariRank-подобные) — снимает position bias по построению, за один проход.
- **Дистилляция.** Самое выгодное применение судьи: не гонять его в проде, а разметить им обучающие данные и дообучить cross-encoder. LLM-реранкер даёт более сильный сигнал дистилляции, чем cross-encoder-учитель, и заметно поднимает recall ретривера. Цена судьи платится один раз офлайн.

**Где судья-реранкер оправдан:** малый поток и высокая цена ошибки — юридический поиск, медицинская литература, отбор под решение. Плюс случаи, где кандидаты почти идентичны и нужно рассуждение о тонких различиях, и домены, где готового реранкера просто нет. Для потокового RAG — не оправдан.

### Типизированная решающая модель как реранкер

Отдельная ветка, появившаяся в сентябре 2026: **System One models** — модели, которые не генерируют текст, а выбирают из заданного набора и возвращают вероятности (первая публичная реализация — Jev, TypeSafe AI). В реранкинге применяются как типизированный вопрос о релевантности на каждый кандидат; запросы параллелятся, отклик десятки–сотни миллисекунд, вход дешевле LLM на два порядка.

По измерениям это закрывает разрыв между cross-encoder и LLM-реранкером: сравнительные прогоны дают результат на уровне ведущих коммерческих реранкеров при цене и латентности ближе к специализированным моделям, а отдельные практики сообщают о превосходстве над ними — разброс объясняется тем, насколько выточены формулировка вопроса и описания вариантов. В отличие от listwise LLM, на выходе есть калиброванная вероятность, то есть порог отсечения поставить можно.

Оговорки те же, что у любого судьи: качество зависит от промпта сильнее, чем у готового реранкера; калиброванные пороги не переносятся между доменами; на неанглийских языках вопрос нужно формулировать как выбор, а не как проверку утверждения. Устройство класса, примитивы и измеренные границы → [../agents/system-one-models.md](../agents/system-one-models.md).

### Готовые модели реранкеров

Специализированные реранкеры за 2026 год подтянулись настолько, что LLM в этой роли нужен всё реже:

| Модель | Профиль |
|---|---|
| jina-reranker-v3 | листвайз-архитектура на late interaction, до 64 документов за проход; сильнейший результат BEIR среди сопоставимых при меньшем размере, лучший выбор в бюджете до 200 мс |
| bge-reranker-v2-m3 | открытая лицензия, многоязычный, дефолт для self-host |
| Cohere Rerank | управляемый сервис с наименьшим порогом входа |
| mxbai-rerank-large-v2, gte-reranker-modernbert-base, nemotron-rerank-1b | выше качество ценой латентности, когда бюджет времени не жмёт |

Точные позиции в таблицах лидеров меняются от релиза к релизу — смотреть актуальный BEIR/лидерборд на момент выбора, а не эти строки.

## Что из этого работает на markdown-пространстве

Для базы знаний из markdown-файлов (управленческое пространство, документация, вики) стек упрощается:

- **Чанкинг — по дереву заголовков, без перекрытия.** H2/H3 уже разделили текст по темам; чанк = раздел, заголовочный путь дописывается в тело. Длина остаётся ограничителем (дробить длинный раздел, склеивать короткие подразделы), но не критерием нарезки. Код и таблицы не разрывать.
- **Эмбеддинг считается с однотемного раздела** — это и есть условие, при котором вектор представляет одну тему, а не среднее трёх. Всё остальное в стеке работает лучше по этой причине, а не благодаря настройкам поиска.
- **Метаданные** — YAML-фронтматтер уже является схемой метаданных, собирать заново не нужно; путь в дереве папок несёт классификацию, заголовочный путь даёт parent-child без отдельного поля. Требования к полям и антипаттерны — [markdown-for-llm.md](markdown-for-llm.md).
- **«Один файл = одна тема» и осмысленные заголовки** — не стилистическое требование к документации, а прямая профилактика semantic entanglement на этапе письма. Документ, написанный сплошняком, придётся чинить дорогими приёмами на этапе индексации.
- **База** — от pgvector и ниже: на корпусе в тысячи файлов отдельная векторная БД не окупается; для локального сценария индекс поверх файлов (QMD-подобный) снимает вопрос синхронизации вовсе.
