# LightRAG — лёгкий GraphRAG

## Кратко

LightRAG (HKUDS, принят на EMNLP 2025) — open-source облегчённая реализация GraphRAG-подхода: извлекает сущности и связи между ними из текста через LLM, строит entity-граф (не backlink-граф файлов), хранит эмбеддинги сущностей/связей/чанков в векторной БД. Дешевле и проще полного Microsoft GraphRAG (нет иерархических community summaries), но индексация всё ещё LLM-heavy — не query-time-only, в отличие от LazyGraphRAG. Ниже — первое собственное эмпирическое исследование (svaib, июль 2026): реальная экономика, найденные дефекты и фиксы, позиционирование против альтернатив.

## Как работает

1. **Чанкинг** — документ режется на куски (по умолчанию ~1200 токенов, overlap).
2. **LLM-экстракция** — на каждый чанк отдельный LLM-вызов: извлекает сущности (тип + описание) и связи между ними.
3. **Merge/резолюция** — при повторном упоминании уже известной сущности (в другом чанке/документе) — ещё один LLM-вызов на слияние/сверку описаний. В плотно связанном корпусе (одни и те же люди/проекты/решения фигурируют везде) это может давать *больше* вызовов, чем сама экстракция.
4. **Эмбеддинги** — сущности, связи и чанки эмбеддятся отдельно (по умолчанию nano-vectordb).
5. **Query modes:** `naive` (обычный vector RAG по чанкам, без графа) → `local` (LLM достаёт low-level keywords/сущности из запроса, top_k = число сущностей) → `global` (high-level keywords/концепты, top_k = число связей) → `hybrid` (local+global) → `mix` (**дефолтный режим** — local+global+naive вместе, самый полный).
6. **Язык вывода** — управляется через `addon_params={"language": "..."}`. Не самоочевидно, но критично (см. дефекты).

## Найденные дефекты (эмпирически, версия lightrag-hku 1.5.4)

**1. RU/EN дублирование сущностей.** `DEFAULT_SUMMARY_LANGUAGE = "English"` — если не передать `addon_params={"language": "Russian"}` явно, экстракция на русском корпусе всё равно уходит в английский вывод, и одни и те же люди/понятия дублируются под русским и транслитерированным именем («Сергей Шагин» рядом с «Sergey Shagin»). Подтверждено численно: до фикса 192/286 (67%) сущностей латиницей, после — 32/252 (13%), и это уже легитимные термины/имена файлов (iiko, MRR, `02_active.md`), не дубли. **Фикс — одна строка в конфиге.**

**2. Транзиентный баг мержа.** `NanoVectorDBStorage[relationships] index flush failed: 'NoneType' object is not iterable` — падает на отдельном документе при мерже, библиотека сама сбрасывает его в PENDING и продолжает. Не блокер, но искажает статистику ошибок при беглом просмотре лога.

**3. Дедупликация по голому имени файла (критично).** `normalize_document_file_path()` делает `basename = Path(file_path).name` — сверяет документы **только по имени файла, без учёта пути**, задокументировано в коде как осознанное поведение («same basename always treated as duplicate»). У любого корпуса со scaffold-структурой (одинаковые `README.md`/`02_active.md`/`05_decisions.md` в каждой папке направления — обычный паттерн для персональных/командных баз знаний) это **молча теряет** каждый файл после первого с таким именем — не ошибка, а тихий пропуск. На тестовом прогоне (229 файлов, много повторяющихся имён) реально проиндексировалось только 119 уникальных basename; важный файл-реестр решений одного направления был полностью потерян, потому что другой файл с тем же именем из другой папки успел проиндексироваться первым.
- По GitHub-истории репозитория (issues/PR #3000, #3006, #3013) — это активная, недавно и всё ещё дорабатываемая область кода, не забытый угол; поведение может меняться в новых версиях.
- **Фикс:** передавать в `file_paths=` не относительный путь как есть, а «сплющенную» уникальную строку (заменить `/` на, например, `__`), чтобы `Path(...).name` совпадал с ней целиком.
- **Почему не поймали на малом пилоте:** коллизия физически не может проявиться, если тестовая выборка — это одна папка (внутри одной папки имена не повторяются). Нужно калибровать минимум на 2+ папках с пересекающимися именами, иначе класс дефекта невидим.

## Экономика (реальный замер, не оценка из документации)

Модель DeepSeek V4 Flash (extraction) + baai/bge-m3 (эмбеддинги) через OpenRouter, корпус ~4M байт / 229 markdown-файлов, обычная конкурентность (`max_async=8`, `max_parallel_insert=4` — официально рекомендованный tier для «medium system», 16GB/8 cores).

- **Деньги:** дёшево. Пилот на 11 файлах (83 KB) — $0.05 реально; полный корпус — около $1-2.5. Экстраполяция по объёму работает достаточно точно.
- **Время — узкое место, не деньги.** ~0.25-0.4 файла/мин даже на рекомендованной конкурентности. Индексация — не векторно-эмбеддинговая операция (как у большинства «лёгких» memory-инструментов), а LLM-генеративная: на каждый чанк — LLM-вызов с длинным структурированным выводом (тысячи токенов completion), плюс доп. вызовы на мерж пересекающихся сущностей. ~75% времени — extraction+merge вызовы.
- **Не исключение, а норма для класса инструментов.** Microsoft GraphRAG на книге в 200K токенов — ~35 минут и ~4000 LLM-вызовов; extraction = ~75% стоимости индексации везде в GraphRAG-семье. Наш прогон (в разы больше 200K токенов) укладывается в ту же логику: часы, не минуты.
- Self-hosted vLLM с батчингом по опыту сообщества заметно быстрее вызовов через провайдера вроде OpenRouter — рычаг для продакшена, не проверялся нами напрямую.

## Когда использовать vs альтернативы

- **vs Basic Memory** (backlink-граф файлов `[[wikilink]]` + локальные эмбеддинги,  BM — бесплатно и быстро (нет LLM на индексации), но видит только явно прописанные связи. LightRAG видит смысловые связи, которых в тексте нет как явной ссылки (граф сущностей, извлечённый LLM), но на порядки дороже и медленнее на входе. Разные механики графа — файловый backlink (BM) и entity-граф (LightRAG) — не взаимозаменяемы вопрос-в-вопрос при сравнении.
- **vs полный Microsoft GraphRAG:** LightRAG — упрощённая версия той же идеи (нет иерархических community summaries), компромисс между Zep/Graphiti-уровнем сложности и голым vector RAG. Подробнее про GraphRAG — [rag.md](rag.md#graphrag-microsoft).
- **vs LazyGraphRAG / FastGraphRAG:** откладывают LLM-вызовы на момент запроса, граф на этапе индексации строят NLP-инструментами (spaCy/NLTK) — на порядки дешевле и быстрее индексация, но это другая архитектура целиком, не тюнинг параметров LightRAG.
