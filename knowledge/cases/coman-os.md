# CoMan OS — управленческая ОС и поставка «Иван»

## Кратко

CoMan OS (Cognitive Management Operating System) — авторская архитектура управления от Максима О.: три слоя переиспользуемой инфраструктуры (Knowledge → Intelligence Strategy Core → Cognitive Digital Twin) поверх причинной иерархии Advanced OKR. «Иван» — публичная поставка верхнего слоя: помощник руководителя, упакованный плагином под Claude Code / Cowork и под Codex / ChatGPT Work, с 18 правилами поведения и обвязкой качества из 11 хуков. Главная ценность материала не в идеях архитектуры, а в том, что известные управленческие рамки доведены до исполняемого кода с честно названной ценой каждого правила.

## Архитектура: три слоя поверх connecting tree

Слои строятся снизу вверх, каждый самоценен и даёт результат до появления следующего.

| Слой | Что это | Содержание |
|---|---|---|
| **Layer 0** | Raw Data | Расшифровки встреч, сканы. Не часть системы — «garbage in» |
| **Layer 1** | Knowledge | Универсальные онтологии (переиспользуются любой компанией) + Knowledge Hub компании. Внутри Hub деление на **Core** (переиспользуемое знание: методология, Vision) и **Operations** (разовое: выжимки встреч) |
| **Layer 2** | ISC — Intelligence Strategy Core | Skills как единицы управленческого знания + механизм согласования: вертикальный (Skills ↔ Knowledge Core) и горизонтальный (Skills ↔ Skills). Исполнитель проверки — «стюард» |
| **Layer 3** | CDT — Cognitive Digital Twin | AI-агенты применения поверх Skills |

**Connecting tree.** Скрепляющий элемент Layer 1 — Advanced OKR: причинная иерархия `Aim → Strategy Goal → Strategic Objective → Objective → Key Result → Initiative → Task`. Доменные онтологии (HR, Sales, Product, Finance) подвешены к ней — каждый объект домена явно знает, какому KR служит. Разница с плоским OKR: плоский — список, из которого агент читает «KR1: 10M, факт 7M»; connecting tree — граф, где на запрос «что у нас по выручке» собирается всё, что служит этому узлу: задачи из разных доменов, метрики воронки, встречи, где это обсуждалось.

**Зависимость слоёв названа жёстко:** Skill без Knowledge Core — просто текст, его нельзя проверить на согласованность; агент без Skills — просто LLM с промптом, его поведение невоспроизводимо.

**Технологическая нейтральность.** Инвариантны онтология и Skills, адаптируется только формат хранения и слой агентов. Платформа = runtime, CoMan OS = интеллект. При смене платформы теряется настройка Layer 3.

## Парадигма: «Garbage in, order out»

Переворот GIGO и главный тезис системы: **дисциплина формируется в процессе, а не требуется до начала работы.** Традиционные управленческие системы требуют высокой дисциплины на входе; здесь система принимает хаотичные входы и структурирует их через онтологии и агентов. Каждый слой описан через эту рамку: Layer 1 принимает хаотичные формулировки целей → выдаёт структурированные OKR; Layer 3 принимает хаотичные мысли руководителя → выдаёт структурированные решения.

## Конвейер Project Sync — гейты между шагами

Рабочий конвейер обработки клиентских данных: Google Drive → выжимки → рекомендации → трекеры задач → отчёты. Изначально один большой сценарий, который ломался предсказуемо: перегружал контекст модели (шаги терялись) и каскадом валил цепочку от одной ошибки. Перестроен в 7 атомарных шагов: скан → обработка → сопоставление → рекомендации → обновление → экспорт → коммит.

**Главная механика — гейты.** Каждый шаг пишет json с результатом: `passed`/`failed`, артефакты, блокеры. Следующий шаг отказывается стартовать, если предыдущий не `passed`. Упало — открыл блокеры, починил причину, перезапустил **с этого шага, а не с нуля**. Все гейты коммитятся в git, по каждому прогону остаётся полный след.

Мульти-клиентность: логика общая, клиентское — в yaml-конфиге. Два режима (лёгкий: только выжимки; полный: с трекерами и выгрузкой). Шаги гоняются по отдельности — часть локально, где нужен доступ к диску, часть в облаке по расписанию.

## Поставка «Иван» — Layer 3 в публичном доступе

Помощник руководителя, две сборки из одного исходника с идентичным содержимым: под Claude Code / Cowork и под Codex / ChatGPT Work. Различаются установка и подтверждение хуков (Codex требует `/hooks` на каждый, подтверждение слетает после любой правки скрипта).

Позиционирование строится не на исполнительности, а на **сопротивлении**: «обычный помощник соглашается; этот называет, что вы сказали, а что он додумал; останавливает опасное; требует назвать цену идеи; идёт к первоисточнику вместо пересказа». Прямо сказано: если нужно молчаливое исполнение — не подойдёт.

Состав: 18 правил поведения (один SKILL.md на ~75 КБ) · 6 навыков · 11 хуков · 8 файлов принципов · шаблон договора пары.

### Три опоры поведения

**§26а — уместные уточнения.** При неоднозначном входе (короткое сообщение, ≥2 разумных интерпретаций, уверенность <80%) — один короткий вопрос **до** большого анализа. Граница: если все прочтения дёшевы и обратимы — сделать все и сказать что и почему, вопрос задаётся, когда прочтения ведут к разной работе или одно из них необратимо. Незаданные пользователем числа помечаются «придумано, подтверди».

**§28 — светофор автономности.** Воронка перед каждым вопросом человеку: (0) расщепить составную развилку — вычислимые компоненты закрыть самому, наверх нести только неустранимый остаток; (1) компетенция — основание вычислимо из репо или это чужое знание; (2) обратимость — двухдверное решение делается само; (3) гранулярность — классифицируется единица работы, а не каждый шаг, наружу один ранжированный свод, не поток вопросов. Свёртка трёх осей — класс петли `in/on/out`.

Ключевое различение: **decision-record** («сделал X, потому что Y — скажи, если не так») против **вопроса-на-подтверждение** («сделать X?»). При вычислимом основании дефолт — именно decision-record, иначе автономия деградирует в вежливый вопрос. Отдельным правилом закрыта маскировка: глагол будущего времени о вычислимой работе в последнем абзаце («делаю X», «дописываю») — это пауза, а не отчёт; та же пауза в форме существительного («остаётся X», «ждёт вашего слова») — тот же ход, замаскированный сильнее.

**§26 — анти-сикофантия.** Сикофантия объявлена дефектом, а не вежливостью: система, которая соглашается, автоматизирует ошибку быстрее, чем человек успевает её заметить. Ценность — сопротивление, не «второе мнение».

### Навык dialectic-partner

Критический разбор идеи в режиме «субъект–субъект → объект»: цель диалога — новый объект, которого не существовало до взаимодействия. Шаг 0 (понять замысел) + четыре обязательных шага: индукция (какие факты поддерживают и опровергают) → дедукция (какие следствия неизбежны) → диалектика (тезис → антитезис → противоречие) → категорический императив (что станет недопустимым, если это станет нормой).

Каждый шаг обязан оставить строку-вердикт **с основанием**: голое «сопротивления нет» считается неисполненным шагом, потому что неотличимо от пропуска. Обязательны два выхода: **цена идеи** (когнитивная — какие убеждения придётся оставить; операционная — какие действия станут невозможны) и **новый объект** (уточнённая модель / принцип / карта различий / ограничение применимости). Анализ без нового объекта считается провалом.

Два калибра вывода по обратимости: короткая форма для локальной идеи, полный Resistance Report для стратегической гипотезы. Названы границы неприменимости, включая точную: **план с получателем, сроком и ресурсами идёт не в диалектику, а в премортем** — «следствия из идеи и механика провала — разный улов».

### Договор пары вместо анкеты

Настройка разговором из четырёх вопросов, файл пишет сам помощник. Обязателен один вопрос — что нельзя отправить и вернуть обратно; общее правило (письма, публикации, отправка клиенту) помощник знает сам, нужны исключения, которых он не угадает. До заполнения поведение по умолчанию — «сделает и покажет, никуда не отправляя»: безопасно, но осторожнее, чем нужно.

Сильные поля договора:
- **Потолок внимания** — сколько единиц в день (вопросов, записей о решении, возражений) человек прочтёт. Сверх потолка помощник не просит даже за хорошее, остаток кладёт в журнал одной строкой. Над потолком всегда необратимое и то, что нельзя экономить.
- **Как вы читаете** — например «первый абзац и замысел, остальное на совести помощника» → вердикт идёт первыми двумя строками, сделанное без сомнения — строкой внизу.
- **Чего не делать** — заполняется только по факту ошибки: «заранее это не угадать, вы ещё не видели, как он ошибается».

Диагностический тезис договора: **почти всегда ошибка значит, что чего-то нет в договоре, а не что помощник «не понял»**. Разница операционная — во втором случае объясняешь одно и то же каждую неделю, в первом дописываешь строку один раз.

## Откуда взяты рамки

Почти все мыслительные рамки заимствованы и переименованы. Ценность — в сборке и доведении до кода, не в изобретении.

| В системе | Первоисточник |
|---|---|
| «верхние уровни пирамиды Грэма» | Paul Graham, *How to Disagree* (2008): DH0 name-calling → DH6 refuting the central point |
| ось обратимости, «two-door → делаю сам» | Bezos, письмо акционерам 2015: Type 1 (one-way door) / Type 2 (two-way door). Там же названа болезнь, которую лечит §28: организации гоняют обратимые решения по тяжёлому процессу необратимых |
| класс петли `in / on / out` | supervisory control: human-in / on / out-of-the-loop, из авиации и автономных систем |
| шаг «категорический императив» | Кант, универсализуемость максимы |
| §26 анти-сикофантия | Anthropic, *Towards Understanding Sycophancy in Language Models* (arXiv 2310.13548): преференс-модели предпочитают сикофантный ответ правдивому |
| «план → премортем, не диалектика» | Gary Klein, *Performing a Project Premortem*, HBR 2007: prospective hindsight, +30% к выявлению рисков |
| Layer 3 «Cognitive Digital Twin» | академический термин Industry 4.0 (~2021): цифровой двойник + онтологии и графы знаний |
| «оракул полный / детерминированный» | test oracle из тестирования ПО |
| «Garbage in, order out» | переворот GIGO |
| «субъект–субъект → объект» | русская методологическая традиция: субъектность возникает только в интерсубъектном взаимодействии |

Своим остаётся то, что не находится в первоисточниках: **класс правила по режиму enforcement**, замер до заведения правила, независимый судья без общего слепого пятна, ловля позиции вместо грамматики. Разбор — [../skills/rule-enforcement.md](../skills/rule-enforcement.md).

## Разрыв: обвязка не работает в Cowork

Правила доставляются `SessionStart`-хуком, который безусловно впрыскивает их тело в контекст — так обходится ограничение платформы «плагин не доставляет CLAUDE.md как контекст проекта».

**А `SessionStart` — единственное событие, которое в Cowork не эмитится** (замер — [../plugins/!plugins.md](../plugins/!plugins.md), раздел «Claude Code ↔ Cowork»). Остальные хуки поставки там работают, проверки качества на `PreToolUse`/`Stop` в том числе; молчит именно канал доставки правил. Следствие цепочкой: правила в контекст не приезжают → остаётся навык, активируемый по описанию, с базовой надёжностью автоактивации порядка 20%. При этом поставка ставит Cowork первой колонкой и обещает, что хуки «едут исполняемыми и запускаются сразу после установки».

Цена решения точечная и типовая: доставка держится на единственном событии, наличие которого на целевом канале не проверялось замером.

## Что забирать, а что нет

**Забирать:** дисциплину гейтов между шагами конвейера (json `passed`/`failed`, перезапуск с упавшего шага, след в git) · класс правила и три критерия поддерживаемости · потолок внимания в договоре · decision-record вместо вопроса-на-подтверждение · паспорт сборки для поставки.

**Не забирать вслепую:** доставку правил одним файлом на ~75 КБ каждую сессию — прямой контр-паттерн к progressive disclosure, где в контекст едут только описания навыков. Решение осознанное со стороны автора (надёжность важнее бюджета), но развилка должна быть выбрана явно, а не унаследована.

**Названная цена системы:** конструкция дорогая. Судья-модель внутри хука добавляет до 8 секунд к ходу и отдельный вызов модели; вердикт судьи невоспроизводим в точности. Автор поставки называет эти цены прямо в коде — это часть дисциплины, а не оговорка.
