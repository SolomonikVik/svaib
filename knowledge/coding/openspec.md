# OpenSpec

## Кратко

OpenSpec (Fission-AI, MIT, крупный и активно развиваемый open-source проект) — лёгкий фреймворк Spec-Driven Development для AI-кодинг ассистентов: слой договорённости между человеком и агентом до написания кода. Два слоя: `specs/` — как система ведёт себя сейчас (источник истины), `changes/` — папка на каждое изменение с proposal, дельта-спеками, design и tasks; при архивации дельта вливается в спеки. Ключевые отличия от Spec Kit и Kiro: brownfield-first за счёт дельта-спек (ADDED/MODIFIED/REMOVED), артефакты без фазовых ворот, спеки растут от реальных изменений, а не пишутся задним числом. Работает через slash-команды в 30+ ассистентах (Claude Code, Codex, Cursor, Copilot и др.) и CLI с JSON-выводом для агентов. Документация: [docs/](https://github.com/Fission-AI/OpenSpec/tree/main/docs).

## Модель: состояние и изменения

- **`openspec/specs/`** — текущее поведение системы, разложенное по доменам (`auth/`, `payments/`…). Домены режут по функциональным областям, компонентам или bounded context.
- **`openspec/changes/<имя>/`** — одно изменение = одна папка. Несколько изменений живут параллельно.
- **Archive** — дельта изменения вливается в основные спеки, папка уезжает в `changes/archive/YYYY-MM-DD-<имя>/` со всеми артефактами. Спеки описывают новую реальность, архив хранит «почему».

Идея закрывает старую развилку документации: либо патчить описание состояния (теряется история), либо копить частные ТЗ слоями (нет источника истины). Агенту доступны оба: актуальное состояние и история решений.

## Артефакты изменения

| Артефакт | Что внутри | Зависит от |
|---|---|---|
| `proposal.md` | намерение (зачем), границы (in/out of scope), подход верхнего уровня | — |
| `specs/**` (дельта) | какие требования добавляются, меняются, удаляются | proposal |
| `design.md` | техническое решение, архитектурные выборы с обоснованием, поток данных, затронутые файлы | proposal |
| `tasks.md` | чек-лист реализации, иерархическая нумерация, задачи размером в одну сессию | specs + design |
| `.openspec.yaml` | метаданные изменения: схема, `skip_specs` (техническое изменение без правки спек), `retire_capabilities` | — |

`tasks.md` работает как переносимое состояние работы: сессию можно потерять или продолжить в другом агенте — контекст лежит в папке изменения.

## Спека: формат и граница

- **Требование** — `### Requirement:` с ключевыми словами RFC 2119 (SHALL/MUST — обязательно, SHOULD — рекомендовано, MAY — опционально).
- **Сценарий** — `#### Scenario:` в GIVEN/WHEN/THEN; должен быть тестируемым, покрывать happy path и краевые случаи. Формат напрямую трассируется в автотесты.
- **Спека — контракт поведения, не план реализации.** Внутрь: наблюдаемое поведение, входы/выходы/ошибки, внешние ограничения (безопасность, совместимость). Наружу (в design/tasks): имена классов, выбор библиотек, пошаговая реализация. Тест: если реализацию можно поменять без изменения видимого поведения — это не спека.

**Дельта-спека** описывает разницу, а не конечное состояние: `## ADDED Requirements`, `## MODIFIED Requirements` (заменяет требование целиком), `## REMOVED Requirements`. Плюсы: ревьюер видит только изменение; два изменения одного файла спеки не конфликтуют, если трогают разные требования; можно специфицировать правку в большом приложении, не описав его целиком.

## Принципы работы

- **Enablers, not gates.** Зависимости артефактов показывают, что *можно* создать, а не что *обязан*. Править design или сужать proposal во время реализации — норма. Цена свободы — дисциплина: самому держать изменение узким.
- **Progressive rigor.** По умолчанию lite: короткие поведенческие требования, границы и non-goals, пара приёмочных проверок. Full — для изменений контрактов/API, миграций, безопасности, кросс-командных и кросс-репо изменений.
- **Не бэкфиллить.** На существующем проекте спеки пишутся только для того, что меняется сейчас; спеки на нетронутый код устаревают, потому что их ничто не держит. Существующие PRD/ТЗ — сырьё для explore, а не документы для массовой конвертации.
- **Update или новое изменение.** Три вопроса: то же намерение? перекрытие скоупа больше половины? можно ли закрыть исходное без этих правок? Формула: обновление сохраняет контекст, новое изменение даёт ясность. Аналогия — ветки git: коммитишь в фичу, пока это та же фича.
- **Мелочь — без процесса.** Для однострочного фикса церемония не окупается.

## Цикл и команды

Базовый профиль: `/opsx:explore` (опционально: агент читает код, раскладывает варианты, превращает сырую идею в план) → `/opsx:propose <имя>` (все артефакты сразу) → человек читает план → `/opsx:apply` (реализация с отметкой задач) → `/opsx:archive`. Расширенный профиль добавляет пошаговое создание артефактов (`new`, `continue`, `ff`), `verify` (сверка реализации со спеками), `sync`, `bulk-archive`, `onboard` (обучающий проход на своём коде). Имя команды зависит от ассистента (`/opsx:propose`, `/opsx-propose`, `$openspec-propose` в Codex) — `openspec init` печатает нужную форму. Установка — npm-пакет `@fission-ai/openspec`.

## Настройка под проект

- **`openspec/config.yaml`** — `context` (стек, конвенции; подставляется в инструкции каждого артефакта) и `rules` по артефактам (например, «в proposal — план отката»).
- **Схемы (`schema.yaml`)** — свой набор артефактов, зависимости, инструкции и шаблоны: можно добавить `research` перед proposal, артефакт ревью или выкинуть specs/design для быстрого потока. Инструкции не зашиты в пакет — их правят и проверяют без релиза.
- **CLI для агентов** — `status`, `instructions`, `validate`, `archive` с `--json`: агент детерминированно получает следующий шаг, недостающие артефакты и прогресс задач.
- **Stores** — планы в отдельном репозитории, общем для нескольких кодовых (фронт и бэк в разных репо, общие требования платформенной команды). Функция новая, зрелость проверять по документации.

## Когда выбирать

- **Против Spec Kit:** OpenSpec легче — меньше markdown, нет фазовых ворот и Python-окружения; Spec Kit строже и чаще советуют для greenfield. Против Kiro: не привязан к IDE и моделям.
- **Хорошо ложится:** существующая кодовая база, команда, где требования и реализация у разных людей (proposal у продукта/аналитика, design у разработчика), нужна трассировка «требование → сценарий → тест».
- **Хуже ложится:** соло-проекты с редкими изменениями поведения (церемония выше пользы), продукт не из кода — сценарии на недетерминированный выход LLM проверяются евалами, а не тестами.
- **Риски:** быстрая эволюция — workflow уже переписывался (legacy `/openspec:*` → OPSX), кастомные доработки команд со временем приходится выкидывать; без дисциплины архивации копятся открытые изменения и конфликты между ними; словарь доменов агент без справочника называет по-разному.

Кейс внедрения в компании-интеграторе (~150 человек, аналитики + разработка + QA, мета-репозиторий, доработки поверх OpenSpec) → [spec-driven-dev.md](spec-driven-dev.md#кейс-интегратора-sdd-на-openspec-для-150-человек).
