# Orca IDE

## Кратко

Orca IDE от Stably объединяет CLI кодинг-агентов, рабочие копии Git, терминалы и просмотр изменений. Для долгой автономной работы нужно отдельно выбрать координацию задач, изоляцию процесса и хранение состояния. Worktree разделяет изменения Git; границу доступа к файлам и сети задаёт sandbox, контейнер или VM.

## Когда выбирать

Orca полезна, когда несколько сессий Claude Code или Codex нужно вести из одного интерфейса: давать задания, видеть ожидание ответа, проверять изменения и продолжать работу. Запуск отдельных агентов вручную и работа координатора — разные сценарии. Для одной сессии может хватить CLI и tmux; координатор нужен, когда важны зависимости задач, вопросы исполнителей и учёт результатов. Возможности интерфейса — в [репозитории](https://github.com/stablyai/orca) и [документации](https://www.onorca.dev/docs/model/agents-sessions).

Параллельность выбирается по способности проверить результаты. Начальный сценарий — независимые задачи с явными границами правок и отдельным ревью; число терминалов само по себе не увеличивает пропускную способность.

## Координация и полномочия

Run хранит пространство задач и входящие сообщения координатора; сам он не планирует и не размещает исполнителей. Task описывает работу, Dispatch — одну попытку её исполнения. Координатор запускает исполнителей, отвечает на вопросы и принимает результаты. Успешная постановка сообщения в очередь не доказывает его прочтение; потеря соединения не доказывает завершение процесса. См. [руководство оркестрации](https://github.com/stablyai/orca/blob/main/skill-guides/orchestration.md).

Перед запуском нужно загрузить руководство из выбранного бинаря через `skills get orchestration`: инструкции соответствуют именно установленной Orca. При выборе бинаря сначала учитывают `ORCA_CLI_COMMAND` и dev-режим. На Linux вне управляемого терминала Orca обычное имя CLI — `orca-ide`; команда `orca` может оказаться экранным диктором GNOME. Порядок определения бинаря — в [скилле Orca](https://github.com/stablyai/orca/blob/main/skills/orchestration/SKILL.md).

## Среда на задачу

Orca вызывает lifecycle-скрипты рецепта из `orca.yaml` локально из корня репозитория; среда исполнения агента при этом может быть удалённой. `create` обязателен, `suspend` и `resume` опциональны; `destroy` задаётся командой либо явно отключается через `destroy: none`. Подключение идёт по SSH либо к Orca Server внутри среды. Рецепт отвечает за ресурсы провайдера и их очистку; успешный ответ Orca не заменяет проверку фактического состояния. Контракт реализован в [runner](https://github.com/stablyai/orca/blob/main/src/shared/ephemeral-vm-recipe-runner.ts); порядок настройки — в [руководстве рецептов](https://github.com/stablyai/orca/blob/main/skill-guides/orca-per-workspace-env.md). Перед настройкой нужно получить `skills get orca-per-workspace-env` из того же выбранного бинаря Orca и загрузить нужные references для Docker, SSH или другого провайдера.

Практический вариант для локальной работы — контейнер на независимую задачу, с собственными репозиторием и состоянием агента. Базовый образ содержит инструменты; рабочие данные и история живут отдельно от заменяемого образа. Для Docker-рецепта Orca документирует SSH на localhost и авторизацию агента внутри контейнера; полную домашнюю папку агента с хоста переносить не следует. Образ с авторизацией содержит секреты и требует соответствующего доступа. См. [Docker over SSH](https://github.com/stablyai/orca/blob/main/skill-guides/orca-per-workspace-env/references/docker-ssh.md).

В рецепт входит решение, что сохраняется при остановке и удалении: Git-изменения, история CLI, состояние Orca и данные тестовых сервисов. Именованный Docker volume переживает удаление контейнера, пока сам volume не удалён; это отдельное хранилище, а не резервная копия. См. [Docker volumes](https://docs.docker.com/engine/storage/volumes/).

## Долгая работа и восстановление

Различаются три состояния: раскладка и вывод терминалов, живой процесс агента, история и результаты задачи. Фоновый daemon Orca может сохранять процессы после закрытия приложения, но перезагрузка хоста завершает их. Для ночной работы выбирается постоянно включённый хост; сохранённая история позволяет продолжить чат после завершения процесса. См. [session restore](https://www.onorca.dev/docs/model/session-restore) и [Remote Orca Servers](https://www.onorca.dev/docs/remote-servers).

Проверка выбранной сборки должна охватывать запуск задачи, отключение клиента, повторное подключение, остановку и запуск среды, продолжение чата и сохранение изменений перед удалением. Статический `doctor` проверяет настройку рецепта; проверка с `--provision` выполняет создание, проверку результата и вызов `destroy`, если он предусмотрен. При `destroy: none` очистка пропускается. Авторизацию, восстановление и отсутствие оставшихся ресурсов проверяют отдельно.

## Разрешения и границы знания

Orca документирует запуск Codex с флагом отключения approvals и внутреннего sandbox. Поэтому права и mounts контейнера становятся частью контракта задачи; доступ к Docker socket или широким папкам хоста расширяет эту границу. Full Access не устраняет требования организации и самостоятельные разрешения подключённых инструментов. См. [режимы запуска агентов](https://www.onorca.dev/docs/model/agents-sessions) и [разрешения Codex](codex.md).

Материал основан на документации и чтении кода. Он не подтверждает рабочий цикл конкретной установки. Критерий приёмки — [контракт агентного харнесса](agent-runtime-contract.md).
