# Контракт агентного харнесса

## Кратко

Харнесс управляет модельными запросами, инструментами, ресурсами, разрешениями и историей сессии. Совместимость плагина проверяется по этим контрактам, а не по способности модели ответить или установщика склонировать репозиторий. Качество модели, лицензия CLI, условия провайдера и полная приёмка рабочего цикла — отдельные вопросы.

## Уровни подтверждения

| Уровень | Что доказано | Что ещё не доказано |
|---|---|---|
| Источник получен | Файлы пакета доступны | Их поддерживает загрузчик |
| Ресурсы обнаружены | Скилл, агент, хук или MCP есть в каталоге | Они активны и разрешены |
| Native-поведение исполнено | Контекст доставлен, инструмент вызван, отказ остановил запись | Весь комплект сохраняет поведение во всех событиях |
| Рабочий цикл принят | Полезный сценарий проходит с чтением, записью, продолжением и восстановлением | Другая конфигурация и следующий релиз ведут себя так же |

Уровни не заменяют друг друга. Фикстура транспорта позволяет проверить реальный движок и инструменты с предсказуемыми ответами; она не измеряет качество LLM. Реальный короткий ответ проверяет endpoint, но не все семантики провайдера. См. [провайдеры и протоколы](third-party-models.md).

## Модель и пределы

Окно контекста, доступный вход и максимум выхода описывают реальный endpoint и тариф, а не рекламный максимум семейства модели. Эти значения нужно применять и к основным, и к вспомогательным запросам: сжатию, памяти, заголовкам, дочерним агентам. Параметр в файле конфигурации считается подтверждённым после проверки его применения runtime либо фактического запроса.

Если харнесс требует больше контекста, чем даёт endpoint, завышать число ради старта нельзя. Нужен совместимый backend, тариф или другой runtime. Если метаданные неизвестны, предупреждение о fallback нельзя считать доказательством корректного лимита.

Сторонний провайдер должен поддерживать именно протокол харнесса, включая tool calls, результаты, роли сообщений, поток завершения и продолжение. Один успешный текстовый ответ не подтверждает эти возможности. См. [Codex configuration](https://learn.chatgpt.com/docs/config-file/config-reference) и [Qwen configuration](https://github.com/QwenLM/qwen-code/blob/main/docs/users/configuration/settings.md).

## Ресурсы, хуки и согласие

У скилла, агентного профиля, hook registry и MCP отдельные загрузчики. Совместимость Markdown-скилла не делает совместимым весь marketplace. Общий адаптер может сохранить Python и исходные ресурсы, но обязан перевести событие, полезную нагрузку, результат, timeout и состояние сессии. См. [контракты хуков](../plugins/cross-harness-hooks.md).

До диагностики хука нужно проверить три факта: он обнаружен, включён и разрешён. Ручное подтверждение текущего определения хука или команды может быть штатной политикой. Exit code подтверждает завершение процесса; доставку контекста доказывает запрос модели, блокировку — решение движка вместе с отсутствием изменения на диске, продолжение Stop — следующий ход движка.

MCP проверяется последовательно: объявление сервера, соединение, обнаружение инструментов, OAuth и вызов рабочего инструмента. Пользовательский вход при OAuth не следует заменять токеном или объявлять несовместимостью пакета.

## Контекст и файлы

Обрезанный результат инструмента — ограниченное представление для модели. Он не равен утрате исходного файла. При сжатии модельная история и сохранённый журнал также могут расходиться: старые сведения остаются в журнале или на диске, но требуют повторного чтения. См. [Pi compaction](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/compaction.md).

Для работы с точными документами проверка должна охватывать две последовательные компакции, продолжение незавершённой задачи, восстановление сессии и повторную загрузку действующих инструкций. После правки проверяются реальные байты файла, включая неизменённый хвост; сообщение инструмента об успехе само по себе недостаточно. Дочерний агент проверяется отдельно: контекст, инструменты, права, чтение источника и результат задания.

Рабочая директория, доверие к проекту и policy-хук не обязательно ограничивают права процесса на уровне ОС. Подключение через оболочку не усиливает эту границу автоматически. Нужно проверить выбранную модель разрешений, исполнение запросов подтверждения и filesystem/network isolation. См. [Pi security](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/security.md), [BB](../tools/bb.md) и [Orca](orca.md) — пример разделения координации, рабочих копий Git и среды исполнения.

## Обновления и отзывы

Обновление харнесса, источника плагина, установленной копии и активных ресурсов — разные переходы. Для TUI, CLI, ACP и SDK путь проверки может различаться. Политика обновления должна определять источник версии, проверку пакета, согласованную активацию и откат; наличие кнопки update не доказывает все переходы.

Публичная жалоба описывает свою конфигурацию и версию. Для вывода о текущем дефекте нужны применимый механизм, статус исправления, комментарии сопровождающих и по возможности воспроизведение. Закрытый issue не всегда означает исправление, открытый — не всегда подтверждённый дефект. Исторический баг нельзя переносить на новый runtime без проверки.

Открытая лицензия разрешает использование кода в своих пределах; она не выдаёт доступ к модельному сервису. [Региональная доступность](harness-regional-availability.md) проверяется отдельно от технической совместимости.
