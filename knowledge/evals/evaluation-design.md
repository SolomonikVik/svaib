# Evaluation design

## Кратко

Как проектировать eval AI-системы от нуля: выбор цели и типа, единица оценки, устройство датасета с holdout, статистический аппарат для малых выборок, требования к воспроизводимости прогона. Применимо к генеративным и детерминированным системам независимо от конкретной реализации.

## Цель определяет тип, не наоборот

Цель (зачем меряем) и тип (каким механизмом) — разные оси; одна цель может требовать нескольких типов одновременно.

| Цель | Тип | Baseline | Гейт |
|---|---|---|---|
| Регрессия при смене версии | regression | прошлая версия | не хуже baseline |
| Оценка улучшения новой версии | capability-delta (+ pairwise) | прошлая версия | значимая дельта |
| Выбор лучшего из кандидатов | pairwise / multi-candidate | текущий инструмент/подход | победитель по категориям |

Capability-eval стартует с низким pass-rate; дойдя до потолка, кейс выпускается в regression-suite с baseline ~100% — дальше он охраняет от отката, а не измеряет рост.

## Единица оценки

Первый вопрос, который решает scope всего остального: что именно оценивается — финальный output, промежуточный trace рассуждений, отдельный tool call, состояние среды после выполнения, или end-to-end исход задачи. Для детерминированных артефактов (правила, gate-функции) единица — предсказуемый вывод: exit-code, точная строка, блокировка. Для генеративных артефактов с открытым выводом единица шире и обычно требует rubric/judge. Смешанные артефакты (часть логики детерминирована, часть — генеративна) раскладываются на две части и оцениваются раздельно, а не одним общим грейдером.

## Датасеты и golden-set

- **Происхождение:** кейсы берутся из error analysis реальных провалов (open coding → axial coding → failure taxonomy), не из воображаемых сценариев. Набор растёт из пойманных прод-фейлов, не полируется upfront.
- **Валидность кейса:** однозначность (два независимых эксперта сходятся в вердикте — спорный вердикт означает плохой кейс, не плохой артефакт), passability (есть reference-решение, доказывающее решаемость — 0% pass на сильной модели = сломанный кейс), баланс positive/negative (тестируется и где поведение должно сработать, и где не должно), неэксплуатируемость (нет лазеек-читов в грейдере).
- **Silver → gold построение:** LLM может сгенерировать черновик эталона (silver), после чего человек или заранее валидированная процедура проверяет его перед переводом в gold. Согласие двух моделей полезно для приоритизации ручного ревью, но само по себе не доказывает правильность эталона.
- **Версионирование и holdout:** датасет — immutable snapshot с content-hash, привязанный к прогону (при добавлении кейсов — новый снапшот; сравнения на пересечении снапшотов валидны). Golden-set — часть контракта артефакта: правка артефакта и правка eval видны в одном диффе. Рабочая часть набора (на которой крутится итерация) отделена от holdout, который не трогают до финальной приёмки — иначе оптимизация подстраивается под артефакты сета (Goodhart). На малых наборах (20-50 кейсов) фиксированный holdout из ~10 кейсов статистически бесполезен (CI ±30 п.п.) — практичнее темпоральный holdout: свежие провалы из реальной эксплуатации, которых промпт не видел.
- **Проверка потолка:** pass-rate 100% не различает сильную систему и слишком лёгкий набор; нужно проверить покрытие, сложность и adversarial-кейсы.
- **Санитизация:** реальные персональные и конфиденциальные данные защищаются согласно политике доступа; открыто версионируют только синтетические или надёжно обезличенные фикстуры.

## Метрики по типу

Форма итоговой оценки зависит от решения: бинарный pass/fail удобен для неторгуемых требований и regression-гейтов; шкала, partial credit или несколько отдельных метрик — для качества с несколькими измерениями. Выбор фиксируется до прогона вместе с правилом агрегации.

| Тип | Метрика | Как читать |
|---|---|---|
| capability | pass-rate, rubric-score | рост оценивается статистически; низкий старт — норма, не тревога |
| regression | дельта к baseline + число регрессий | любой спад — повод для разбора, не усреднения |
| pairwise | win-rate / preference по категориям | победитель по категориям, не по общему среднему — средний балл маскирует, что одна версия сильнее на одном классе задач, другая — на другом |

Рядом с корректностью измеряется эффорт: число ходов, tool-calls, токены, латентность — версия может быть «правее», но заметно дороже, и таблица должна показывать оба измерения.

## Статистический аппарат для малых выборок

При n меньше нескольких сотен нормальное приближение (CLT, t-тест, Wald-CI) даёт систематически слишком узкие доверительные интервалы — источник ложных «значимых» улучшений.

**Оценка одной версии:**
- Bootstrap-CI (percentile, ~1000 ресемплов) — универсально для любой метрики.
- Wilson score или Clopper-Pearson — биномиальный CI для одиночной pass-rate (не Wald).

**Сравнение двух версий на одном наборе (paired):**
- McNemar — бинарный pass/fail; при малом числе дискордантных пар (b+c < 25) — точный биномиальный вариант, не χ².
- Wilcoxon signed-rank — если метрика не бинарная, а rubric-балл с partial credit.
- Permutation / bootstrap на разнице — универсальный запасной вариант для малых n.

**Сравнение 3+ кандидатов:**
- Cochran's Q — бинарный вердикт по нескольким кандидатам на одном наборе (обобщение McNemar).
- Friedman — rubric-баллы, несколько кандидатов.
- Значимый общий тест → парные post-hoc с поправкой на множественность (Bonferroni/Holm), иначе возникают ложные «победители».

**Правда мощности:** paired McNemar при разумных n (α=0.05, power=0.8) требует несколько десятков дискордантных пар для детекции эффекта ~4-5 п.п. — это достижимо только с сотнями кейсов. На 20-50 кейсах статистически надёжно ловятся только крупные сдвиги (десятки п.п.); мелкие улучшения версий доказать нельзя — не выдавать шум за победу.

**Шум измерения судьи:** когда оценку даёт LLM-судья, его собственная ошибка измерения систематическая, не усредняется повторными прогонами — закладывается в неопределённость сравнения версий, наивные CI без этой поправки оказываются ещё уже, чем кажется.

**Оценка, а не автоматический вердикт, для малых n:** при малом наборе NHST не должен подменять разбор эффекта. Решение читают по дельте, доверительному интервалу, цене ошибки и разбивке по категориям; формальный статистический гейт оправдан только при достаточной мощности, которую нужно обосновать для конкретного дизайна.

## Воспроизводимость: манифест прогона

Сравнение версий действительно только при зафиксированной полной связке переменных:

- версия артефакта (git SHA или явная версия),
- версия модели-генератора и среды исполнения — первоклассная переменная: чаще пайплайн ломает не правка артефакта, а смена движка под ним,
- снапшот датасета и его content-hash,
- промпт-шаблон судьи и версия модели-судьи,
- конфиг грейдера, окружение и зависимости.

Любое незафиксированное расхождение (тихо сменившийся судья, изменённый датасет, другая модель-генератор) между прогонами аннулирует сравнение. Изоляция окружения обязательна: каждый прогон — чистый идентичный state, различается только измеряемая переменная; грязное окружение (оставшиеся файлы, кэш) даёт коррелированные провалы от инфраструктуры, а не от артефакта.

## Надёжность через повторные прогоны

LLM варьирует ответ от прогона к прогону — единичный сэмпл не показатель. Многократные прогоны одного кейса сворачиваются в один вердикт кейса: `pass^N` (все N прогонов успешны) — для артефактов без права на повторную попытку; majority — для остальных. В статистические тесты входит вердикт кейса, а не сырые прогоны (они коррелированы внутри одного кейса). `pass@k` (хотя бы один успех из k) — отдельная от `pass^N` метрика, применимая только там, где достаточно одного успеха; путать эти два понятия — методологическая ошибка.
